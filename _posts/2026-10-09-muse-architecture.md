## 1. 从会话服务到持久任务

### 1.1 三个新问题

一个助手帮你查资料，只需要交付正确的内容。让它读邮件、改文件、提交表单，等你确认后发送结果，问题的性质就变了：它操作的是一个持续变化的账户和环境，一次错误可能在对话结束后继续产生影响。

常见的会话型架构可以抽象成：客户端提交消息，服务端读会话和外部信息，模型决定是否调工具，执行框架把结果送回模型。这套东西已经支持多轮交互甚至代码执行——"会话型"不等于"没有数据库"。真正的新问题出现在任务跨越几小时、需要多个外部系统配合的时候：

**连接断开以后，谁拥有任务？** 浏览器连接不能成为唯一的任务容器，用户关页面不应自动抹掉待执行的工作。

**进程退出以后，什么必须保留？** 运行到哪个动作、用户批准过什么、外部操作是否完成，这些不能只放在线程栈和内存变量里。

**任务之间可以共享什么？** 工作文件和长期偏好可能需要共享，临时脚本、凭据和某次操作的授权却不应自然扩散到所有任务。

不同产品在这件事上取舍不同。Anthropic 把 claude.ai 的代码执行描述为按会话使用的临时容器；Managed Agents 把 session、harness、sandbox 拆成独立接口，并报告按需创建执行环境后中位 TTFT 下降约 60%、p95 下降超过 90%；Muse 选择用户级持久工作环境。三者强调的是执行环境寿命、组件替换边界和用户数据归属，不是简单的版本高低。

| 架构组织方式 | 主要保留什么 | 独立分析时最重要的问题 |
|------|------|------|
| 会话服务 + 临时执行环境 | 会话记录；执行目录可能临时存在 | 结果能否导出，执行失败是否影响对话 |
| 持久会话 + 可替换执行框架/沙箱 | 外置事件与任务状态 | 怎样重建进程，哪些节点允许重跑 |
| 用户级持久工作环境 | 工作空间及跨任务状态 | 数据隔离、权限管理、备份与资源利用率 |

### 1.2 持久性首先带来状态管理成本

长期助手会积累文件、任务、技能、会话和派生记忆。一次成功操作留下的不只是回答，还有以后会被反复读取的环境变化。

举个例子：助手为了完成任务装了个依赖、改了脚本，又把结论写进长期记忆。下次执行失败，问题可能来自当前的模型，也可能来自一个月前留下的状态。只有保存版本和来源，才能区分"本次推理错误"和"环境已经变了"。

所以分析一个持久 Agent，先看它的**状态归属和写入边界**，而不是先数它有几个子 Agent。

## 2. Muse Secure VM：两个安全域

### 2.1 公开组件的最小地图

Meta 的公开说明给出了一条清楚的边界：每个用户拥有专属 VM；Hatch 执行框架和工作空间放在 runtime cell（运行时隔离单元）里，安全相关服务放在 cell 外。注意这里的"宿主侧"指**该用户 VM 内、cell 外的 Linux 环境**，不是物理宿主机。

| 位置 | 公开组件 | 职责 |
|------|------|------|
| runtime cell 内 | Hatch、文件、工具程序 | 模型驱动的执行 |
| cell 外 | `privsep` workers | 内置连接器的受限执行 |
| cell 外 | `hatch-authd` | 凭据保管与替身令牌 |
| cell 外 | Sentinel | 连接器行为与网络出口授权 |
| cell 外 | `hatch-safety` | 独立安全检查 |
| cell 外 | PostgreSQL、推理/遥测代理 | 持久应用状态及外部服务通路 |

![用户 VM 内的两个安全域](/assets/img/posts/muse-architecture/fig-02-two-security-domains.svg)

这个布局最重要的含义：执行框架会接触不可信的网页、文件和工具结果，但它不应因此获得重写自身权限边界的能力。

### 2.2 容器里的 root 为什么不等于 VM 的 root

Muse 用 `systemd-nspawn` 构造 cell，配合用户映射、系统调用过滤和能力限制。

理解这层机制要把文件系统视图和权限身份分开。进程看到自己的根目录 `/`，只说明路径视图受限，不等于它对宿主资源没有特权。Linux User Namespace 允许命名空间内外使用不同的 UID 映射——里面的 root 可以映射到外面一个普通用户；Capabilities 再决定允许哪些管理操作。`systemd-nspawn` 的手册自己也强调：运行不可信代码必须用用户命名空间。这是容器权限模型的结论，不是哪个模型特有的安全技巧。

还有一点值得单独说：语言模型是否"理解规则"和 Linux 是否"允许这个系统调用"是两个独立判断。前者降低误操作概率，后者限制误操作能碰到什么。两层都要有。

### 2.3 三种边界不能互相替代

用户之间的隔离限制另一个租户能看到什么；cell 与安全服务之间的隔离限制当前 Agent 能改什么；运行服务商能否读取数据是第三个问题。2026 年 9 月的公开说明把 Confidential VM 列为后续能力，和当时的 Secure VM 明确区分开——普通 VM 隔离不等于"服务商不可访问数据"的密码学保证。对存储系统来说，这三个问题分别落到租户身份、访问控制、加密与证明上，"数据存在个人 VM 里"这一句话回答不了全部。

## 3. 一次跨应用任务的执行链路

用一个说明性任务贯穿全文：

> 读取几封邮件和相关网页，生成一份整理好的文件，确认收件人与内容后发送出去。

这不是 Muse 的运行日志，下图按公开的调用边界组织逻辑步骤。

![一次任务的逻辑执行路径](/assets/img/posts/muse-architecture/fig-03-execution-path.svg)

### 3.1 读取与生成

用户输入进入执行框架，框架组织模型输入，模型选择下一步行动。读邮件走连接器，读网页走浏览器或受控网络通路，生成文件写入工作空间。模型调用通过推理代理到外部推理基础设施——专属 VM 不代表模型权重和 GPU 必须部署在这台 VM 里。

这一步已经出现多种状态：原始邮件是外部数据，下载内容是本地副本，生成文件是新产物，模型上下文只是其中一部分信息的组合。

### 3.2 从"建议发送"到"允许发送"

模型生成发送动作只是**提出**请求。一个可靠的执行系统还要确定执行主体、目标账户、收件人、附件版本和授权范围。

Muse 的公开机制把批准权放在 Sentinel，用户确认通过专门界面直接回到这个权限服务——聊天内容本身不应充当最终授权记录。由此可以推出一个接口要求：**批准的对象必须和真正执行的动作绑定**。用户看过文件 A，不应在确认之后被静默换成文件 B。这个绑定问题第 7 章展开。

### 3.3 执行成功之后仍有一个提交窗口

外部邮件服务可能已经接收了请求，但执行进程还没把成功结果写进任务状态。此时进程退出，系统只知道"动作被派发过"，不知道"邮件发没发出去"。

这是本文后半段的核心故障：**本地任务状态与远端副作用之间，通常不存在一个共同事务**。换模型、改提示词、恢复 VM 快照，都不会自动补上这个事务边界。

## 4. 任务、文件、记忆和缓存分别存什么

### 4.1 从部署位置转向数据语义

知道"用了数据库"之后，还要知道数据库里的对象分别承诺什么。下面是一个用于分析持久 Agent 的数据模型，不对应 Muse 公开的表定义：

| 对象 | 最小身份 | 为什么要持久化 | 恢复时检查什么 |
|------|------|------|------|
| 任务与动作记录 | `task_id / action_id` | 判断进度和外部操作结果 | 动作是否已提交、是否需要对账 |
| 原始事件 | `event_id / sequence` | 保存输入、工具结果与状态变化 | 事件缺失、重复和来源 |
| 文件与结果产物 | `artifact_id / revision` | 恢复任务输入和已完成工作 | 内容完整性、版本与可见权限 |
| 摘要与记忆 | `source_ids / producer_version` | 减少后续上下文读取成本 | 来源是否有效、是否需要重建 |
| 授权 | `grant_id / permission_epoch` | 约束未来可以执行的动作 | 到期、撤销、作用域是否匹配 |
| KV Cache | 模型身份、输入前缀、缓存格式 | 减少重复 Prefill | 输入、表示兼容性与隔离策略 |

前三类记录已发生的事实和工作进度；摘要是派生结果；授权限制未来行为；KV 保存可复用的计算中间状态。它们可以互相关联，但不能用一份"会话摘要"替代所有对象。

![持久 Agent 的状态对象](/assets/img/posts/muse-architecture/fig-04-state-objects.svg)

### 4.2 原始事件与上下文分别管理

同一份工具结果可能很长。在线推理只需要若干结论，排错时需要完整输入，重训摘要模型时又要重新读原始内容。

合理的设计是：保存不可变的原始事件，读取时再生成当前上下文。摘要记录自己覆盖了哪些事件、由哪个版本生成。这样更新压缩逻辑时可以重新产生摘要，而不改写历史事实。LangGraph 的公开接口也体现了同样的拆分——线程内检查点和跨线程 store 是两个东西。**持久历史、执行状态和模型输入可以分别管理。**

另外两个容易踩的坑：追加写事件不等于所有用户内容永久保留，合规删除和保留期仍要定义；摘要来源可追溯不等于摘要内容可信——一个恶意网页经过摘要之后，仍然是来自不可信来源的信息。

### 4.3 文件与数据库怎样一起发布

假设子任务生成了报告：文件写入对象存储，任务记录保存在数据库。两者未必能放进同一个事务。

一种可实现的发布顺序：**先写不可变文件并取得内容摘要，再在数据库事务里同时写产物引用和任务完成事件，最后让其他任务读取该引用。** 文件写成功但数据库提交失败，只产生待回收的孤立对象；数据库宣告完成但文件没写成功，就会在读路径上留下断裂。

```sql
-- 示意数据模型，不是 Muse schema。
CREATE TABLE task_events (
    task_id TEXT NOT NULL,
    sequence BIGINT NOT NULL,
    event_id TEXT NOT NULL UNIQUE,
    event_type TEXT NOT NULL,
    artifact_ref TEXT,
    PRIMARY KEY (task_id, sequence)
);

CREATE TABLE artifacts (
    artifact_id TEXT NOT NULL,
    revision BIGINT NOT NULL,
    content_digest TEXT NOT NULL,
    object_uri TEXT NOT NULL,
    visibility_epoch BIGINT NOT NULL,
    PRIMARY KEY (artifact_id, revision)
);

CREATE TABLE derived_views (
    view_id TEXT PRIMARY KEY,
    source_manifest TEXT NOT NULL,
    producer_version TEXT NOT NULL,
    input_visibility_epoch BIGINT NOT NULL,
    output_artifact_ref TEXT NOT NULL
);
```

`source_manifest` 列出事件范围、文件版本和其他依赖，`producer_version` 说明是哪一版摘要逻辑产生的结果。两者结合，才能回答"这个结论从哪来"和"哪些派生对象需要重建"。

### 4.4 删除记忆为什么是跨层失效问题

一封邮件被用户删除或撤销访问后，留下的派生对象有：搜索索引、摘要、长期记忆、已拼装的上下文，以及由这些上下文算出来的 KV。只删向量索引里的一个条目，其他副本照样能被读到。

一种工程方案是 `visibility_epoch`（可见性代次）：删除先更新权威可见状态；后续读取必须按最新代次检查；已进入上下文或在途输出的数据要取消执行或在输出边界再校验；然后异步清理派生索引、文件副本和缓存。**逻辑不可见先完成，物理回收随后收敛。** 粒度也有取舍：按用户整体提升代次容易实现，但会让大量无关缓存失效；按对象记录血缘更精确，但要维护依赖图和反向索引。

备份是另一个坑：从旧备份恢复数据，不能顺带把后来发生的权限撤销也回滚掉。PostgreSQL 的 PITR 能用基础备份和 WAL 恢复数据库，但它不会自动协调文件、外部账户和独立权限服务。恢复完成后先做权限与删除标记对账、再开放读取，应该是一个单独定义的恢复步骤。

### 4.5 什么负载真正需要向量引擎

个人记忆往往带很强的用户和时间约束。过滤后只剩几十条候选时，普通数据库读取或 CPU 距离计算可能就够；完整邮件归档、共享文档库才可能形成更大的稠密检索负载。从"个人助手架构"推不出"记忆必须用 GPU 向量检索"——先测过滤后候选规模、并发、维度和更新比例，再决定执行后端。

## 5. privsep、authd 与 Sentinel 的分工

### 5.1 三个不同的问题

部署图里这三个组件都和权限有关，但回答的问题不同：`privsep` 限定连接器代码在哪执行、有什么权限；`authd` 管理经认证的调用方能用哪些凭据；Sentinel 判断当前行为是否允许。

从接口设计角度可以再拆细一点：**执行身份**回答"是谁发起调用"，**凭据访问**回答"这个身份能用哪个服务账户"，**动作授权**回答"在这个任务和参数下，允许哪项外部操作"。三者分开之后，连接器名称就不能充当身份凭证——调用方在 JSON 参数里把 `calendar` 改成 `mail`，不应因此获得邮件账户权限。

### 5.2 Unix Socket 解决什么，不解决什么

Muse 公开使用 Unix Domain Socket 加 `SO_PEERCRED`、调用方 ACL 建立 cell 与宿主服务的通信边界。`SO_PEERCRED` 返回内核提供的对端进程凭据，服务端不需要相信请求体里自报的 UID；`SCM_RIGHTS` 可以把已打开的文件描述符传给对方，接收方拿到自己的 fd 编号。

这比"发一个本地端口，再带一个万能 API Key"少了一个可被复制的秘密。但限制也很明确：**知道哪个进程在调用，不等于知道这个进程没被诱导。** 身份检查之后，仍要校验请求语义和具体操作范围。

### 5.3 传文件描述符，也要考虑内容变化

连接器要上传附件时，让低权限调用方打开自己有权读的文件，再把 FD 传给受限执行进程，能减少高权限服务替调用方任意打开路径的机会。

但 FD 固定的是"已打开的对象"，不保证内容以后不变——另一个进程仍可能改同一个对象。用户审批时检查的是旧内容，真正发送的是新内容，就是一个 TOCTOU 竞态。对策是让审批绑定的文件先形成不可变产物，把 `artifact_id + revision + digest` 纳入动作参数；适用场景也可以用 Linux `memfd` 的文件封印机制限制后续修改。**工程重点是固定审批对象，而不是指望模型保证"之后不再编辑"。**

![连接器授权与凭据使用](/assets/img/posts/muse-architecture/fig-05-credentials.svg)

### 5.4 凭据替身缩小了什么风险

Muse 的公开设计让执行侧使用替身令牌，在受控网络出口经过授权后替换成真实凭据。安全语义上，这把"复制一个长期秘密即可任意使用账户"缩减成"只能经过代理申请一项受约束操作"。

但替身仍然是一种能力：只要它能触发代理使用真实凭据，就需要绑定服务、账户、目标和有效期，避免被复用到其他操作。还有一个容易遗漏的风险——秘密没泄露，代理也可能被诱导发出一封不该发的邮件。秘密不可见只减少一类泄漏途径，替代不了内容检查和行为授权。

### 5.5 授权决定如何强制生效

Sentinel 独立于主 Agent，不意味着每次判断都是纯规则、绝不误判。要分别看**判断质量**和**强制执行位置**：判断可以包含策略、模型和用户确认；强制执行则要求不存在能绕过这条检查路径的网络或连接器出口。把规则移出提示词，解决的是"主 Agent 能直接改写规则"，没有证明系统不再有判断错误——误放行、误拦截和用户审批负担仍需要独立评测。

## 6. 网络出口与浏览器的受控执行

### 6.1 允许访问某个域名，不等于允许执行任意 API

一个外部服务往往同时支持查询、上传、删除和发消息。只检查域名，会把同一站点下不同风险等级的操作混在一起。合理的出口判断至少要理解目标服务、实际连接地址、协议、账户、操作类别和发送内容——DNS 解析后的地址也要纳入检查，否则"看起来公开"的域名可能最终指向内部网络。

Muse 的公开出口设计检查具体网络请求，并用数据流标记辅助决定是否需要审批。Anthropic 有一个公开复盘正好是反面教材：允许域名上的 API 曾被用于把文件提交到另一个账户，修复需要检查调用身份和具体请求，而不是维持域名白名单。设计原则可以总结成一句话：网络白名单授予的是一组**可达能力**，评审时应问"这里有哪些方法能被调用"，而不是"这个域名是否可信"。

### 6.2 Tainted Egress：污染标记是一种保守信号

公开机制把读取过用户数据的执行过程标记为"受污染"，失去原本可能适用的自动放行条件；无法确认状态的过程也回到常规审批。实现上借助 eBPF 和 LSM 钩子把数据流和出口关联起来。

这不需要理解成"eBPF 自动读懂了每段文本"，也不是"受污染就一定恶意"。它记录的是一个更粗的事实：**这个执行过程可能携带用户数据，之后的外发需要更严格判断。** 设计这种机制时要分别考虑文件读取、进程派生、管道、共享内存和长驻进程的传播——重启一个子进程就能自动恢复"干净"，标记就失去意义；整个长进程读过一次数据就永久触发审批，又会产生太多干扰。执行粒度的取舍也在这里：小执行单元利于归因和回收，共享进程便宜但会让数据来源混合。

### 6.3 浏览器代理控制可执行动作

Muse 公开把 CDP（Chrome 调试协议）交给 cell 外的代理管理；浏览器子 Agent 使用无障碍树快照和受限操作接口，不能通过这个接口执行任意页面 JavaScript。人工接管或安全凭据填充期间，Agent 暂停操作。

注意：**不向 Agent 暴露脚本执行接口，不等于网页本身不执行 JavaScript。** 约束的是自动化控制方能发出哪些指令。窄接口的价值是可监督性——定位元素、填字段、点按钮比一段任意脚本更容易映射成明确操作；代价是复杂页面可能需要更多轮交互。

### 6.4 浏览器状态也有提交边界

页面显示"发送成功"是判断的证据，但不必然等于外部系统已给出可查询的稳定事务标识；页面超时或跳转失败，也不必然说明操作没发生。浏览器自动化比直接 API 更难做可靠恢复：往往没有服务端幂等键，成败只能靠页面和后续查询判定。这种情况下系统应允许进入"结果未知"，而不是用一次自动刷新掩盖不确定性。

## 7. 授权也是需要恢复的状态

从这章开始进入设计分析：Muse 公开了审批能力和作用域，但没有公开任务表、状态机或恢复协议。

### 7.1 从一个弹窗到一个状态对象

用户批准发送一份报告，系统要记录的不只是 `approved=true`，还有：批准的是哪个任务、哪个动作、哪个目标、哪份附件，以及授权能用几次、持续多久。可以把一项授权抽象成：

```python
# 机制示意；主体身份和 grant 必须来自可信服务，不能来自模型自报。
@dataclass(frozen=True)
class Grant:
    principal_id: str
    task_id: str
    action_digest: str        # 目标、参数与不可变附件版本的规范化摘要
    permission_epoch: int    # 撤销 / 策略更新后递增
    expires_at: int


def validate_before_dispatch(action, grant, authority, now):
    if action.principal_id != grant.principal_id:
        raise Denied("principal mismatch")
    if action.task_id != grant.task_id:
        raise Denied("task mismatch")
    if action.canonical_digest != grant.action_digest:
        raise Denied("approved payload changed")
    if grant.permission_epoch != authority.current_epoch:
        raise Denied("grant revoked or policy changed")
    if now >= grant.expires_at:
        raise Denied("grant expired")
    # 一次性授权还需在权威存储中原子保留 / 消费，不能靠本地计数。
```

摘要要在规范化参数后计算，至少覆盖目标账户、接收对象、动作类型和产物版本。哈希本身不提供授权真实性——能不能信这份 grant，取决于它从哪个可信服务取得、能否被修改、执行时如何校验。

### 7.2 等待期间哪些变化会使授权失效

**参数变化**：收件人、正文或附件改了，旧授权不能默认延续，要么重新确认，要么按明确的授权范围判定。**任务变化**：用户改了目标后旧 Worker 可能还在跑，任务需要 `execution_epoch`（执行代次），由接收写入的服务拒绝旧代次结果——只在 Worker 本地自查挡不住晚到写回。**权限变化**：用户断开连接器或撤销权限后，旧检查点里的批准记录不能重新获得执行力，恢复时必须咨询当前权威状态。**外部事实变化**：未提交的表单可能因库存、时间或报价变化需要重新检查——这是业务前置条件，和授权是否有效是两项检查。

![带未知结果的动作状态机](/assets/img/posts/muse-architecture/fig-06-action-state-machine.svg)

### 7.3 一次性授权不能简单等于一次网络请求

发送前先把授权次数减一，再碰上网络失败，用户可能要再批一次；发送后才减一，两个并发执行者又可能都看到授权未使用。更可靠的语义是让授权绑定一个稳定的 `action_id`，系统原子保留这项动作的执行权，恢复后继续处理同一个动作；网络重试是否允许，再取决于外部接口的幂等与查询能力。

这里仍然没有跨系统事务。如果远端没有幂等键、也无法查询结果，一次性授权和网络不确定性之间就必须保留 UNKNOWN 状态——安全性优先的代价是部分任务需要人工确认才能继续。

### 7.4 撤销必须定义生效时刻

"立刻撤销"需要可操作的语义。一个合理约定：权威出口在派发前检查当前权限；已被外部服务提交的操作不承诺撤回；已进入网络但结果不明的操作进入对账流程。撤销至少区分**尚未派发、正在执行、已经完成**三种状态，跨进程恢复时还要明确谁拥有当前租约、哪个代次可以提交结果、旧连接上的晚到返回怎么处理。这些细节决定系统是否可控，一句"每次调用都检查权限"概括不了。

## 8. 外部操作为什么不能直接重放

### 8.1 最危险的窗口：远端已提交，本地未记录

![外部提交与本地记录之间的窗口](/assets/img/posts/muse-architecture/fig-07-commit-window.svg)

从持久日志恢复执行框架，只能让程序知道以前**记录了什么**。没被记录的外部成功，仍然可能真实存在。LangGraph 的公开文档给了一个容易被误解的细节：从 `interrupt()` 恢复时，相关节点会从头重新执行，不能假设像暂停线程那样从下一行继续——放在中断前的副作用尤其需要幂等。即使把发送动作放在中断之后，依然存在"发送成功、节点结果尚未持久化"的故障窗口。

所以要分别判断两件事：**节点能不能重跑，节点里的外部动作能不能重试。** 这是两个问题。

### 8.2 四种恢复路径

| 外部系统能力 | 恢复策略 | 能够保证什么 |
|------|------|------|
| 支持服务端幂等键 | 用同一个动作键重试 | 在服务承诺范围内避免重复效果 |
| 支持可靠的操作查询 | 先按稳定业务标识对账 | 发现已完成结果后补记本地状态 |
| 只支持普通写入 | 不能因本地超时直接重发 | 保留 UNKNOWN，等人工或其他证据 |
| 支持补偿操作 | 对已确认结果单独补偿 | 补偿是新动作，不等于原动作未发生 |

Stripe 的幂等 API 是第一类的公开实例：客户端传幂等键，服务端记录键对应的结果，相同键返回相同结果。**幂等键的关键是稳定**——重启后新生成一个 UUID，外部服务会当成新动作；相同键配不同参数，也不能被静默解释成同一请求。查询对账也有条件：服务只是最终一致时，暂时查不到不代表操作没发生。只有查到相符的完成结果才能补记成功，否则保留未知。

### 8.3 Fencing 保护哪一侧

Fencing Token 适合防止旧 Worker 覆盖新任务状态，前提是**真正接收写入的服务会检查令牌**。第 7 代 Worker 超时、第 8 代接管后，本地任务服务拒绝第 7 代的结果可以避免状态倒退；但普通邮件服务不知道任务代次，它仍可能接受旧 Worker 已经发出的邮件。

状态写回栅栏、出口处的执行权检查、服务端幂等、外部结果对账，各解决不同的问题。不能用一个 generation 字段概括端到端恰好执行一次。

### 8.4 最小故障注入实验

为了把这件事变成可验证的行为，我写了一个只用 Python 标准库的实验 `recovery_lab.py`：两份独立 SQLite 文件分别模拟 Agent 控制存储和外部服务，子进程在外部提交前后用 `os._exit()` 退出，再启动新进程做恢复。没有网络、没有真实账户，测的是**控制存储与外部副作用之间的语义差异**。恢复核心可以概括为：

```python
# 实验的恢复逻辑摘要。
if state == "SUBMITTED":
    if service.supports_idempotency:
        result = service.execute(payload, key=stable_action_id)
    elif service.supports_reliable_lookup:
        result = service.lookup(stable_action_id)
        if not result.matches(payload):
            return mark_unknown()
    else:
        return mark_unknown()

mark_completed(result)
```

派发前还有一组 dispatcher 级检查：授权是否被撤销（`revoked`）、任务代次是否匹配（`task_generation`）、权限代次是否匹配（`permission_epoch`）、动作摘要是否和批准时一致（`approved_digest`）。实测 8 个场景全部符合预期：

| 场景 | 恢复后的状态 | 外部效果次数 | 说明 |
|------|------|:---:|------|
| 普通重试；外部提交后崩溃 | COMPLETED | 2 | 本地看似完成，重复效果已产生 |
| 相同动作键；服务端去重 | COMPLETED | 1 | 重试取回已有结果 |
| 按业务标识可靠查询 | COMPLETED | 1 | 不重发，补记成功 |
| 无去重/查询；外部提交后崩溃 | UNKNOWN | 1 | 保守停止，不猜测失败 |
| 无去重/查询；派发前崩溃 | UNKNOWN | 0 | 安全策略牺牲部分自动完成能力 |
| 派发前权限被撤销 | DENIED | 0 | 旧授权不能继续使用 |
| 批准后修改参数 | DENIED | 0 | 动作摘要不匹配 |
| 旧代次执行者尝试派发 | DENIED | 0 | 当前任务代次不匹配 |

第一个场景是**故意复现重复执行**——本地状态显示 COMPLETED，独立的外部库里效果却发生了两次。实验没覆盖真实并发、撤销与派发之间的竞态、数据库断电这些情况，不能从这里外推生产结论。它的价值是把系统的承诺从"可以恢复任务"收敛到一个更明确的问题：恢复之后，有没有重复改变外部世界。

## 9. 持久工作空间与可替换执行进程

### 9.1 用户级隔离不要求所有组件同寿命

个人 VM 强调数据和权限的归属；执行框架、工具进程、浏览器、模型请求可以各有各的寿命。一个任务持续一周，不意味着这周必须有一个线程和一块 GPU 为它常驻。Managed Agents 把事件记录、执行框架和沙箱解耦后，按需创建执行环境，中位 TTFT 降约 60%、p95 降超过 90%——这反映的是移除前置环境初始化的收益，不是产品间排名。

从设计上可以同时拥有**用户级稳定身份与存储**、**可丢弃可重建的执行进程**。用每用户 VM、共享沙箱池还是每任务容器是部署层的选择，恢复接口不应完全绑定其中某一种。

![任务、执行和推理的独立生命周期](/assets/img/posts/muse-architecture/fig-08-lifecycles.svg)

### 9.2 从"始终运行"拆出四种资源

持久存储（任务、文件、记忆、授权）需要独立的耐久性和备份；待触发工作（定时任务、订阅事件、待确认动作）需要可靠触发、去重和取消语义；执行资源（进程、文件句柄、浏览器连接、依赖环境）需要配额和失败回收；推理资源（权重、正在计算的批次、KV 缓存）由推理服务维护，不应由长期任务数量直接决定 GPU 预留。

四者分开之后，容量规划才有可解释的单位：存储按数据量，调度按就绪任务，浏览器按并发执行，GPU 按活跃推理负载及缓存需求。

### 9.3 子 Agent 增加的是独立执行上下文

一次模型调用可以派出多个子任务。需要单独限制的是就绪数量、并发、深度、工具预算和总截止时间——不能因为每个子 Agent 都"遵守单次限额"，就假设父任务没有放大成本。结果返回也不宜把全部子轨迹拼回主上下文，更合理的是带来源和版本的产物引用，加上回答下一步问题所必需的摘要，原始观察放独立存储按需读取。

还有一点：摘要由子 Agent 生成，不会自动提高可信等级。它仍可能受网页或文件内容影响，跨 Agent 传递时应保留来源属性，而不是统一升级成系统指令。

### 9.4 观察恢复过程，而不是只记录错误日志

观测至少关联任务、动作、权限版本、执行代次、产物版本和模型请求标识；时间指标拆成就绪排队、环境准备、推理、工具、审批等待与恢复。审批等待 20 分钟不等于系统算了 20 分钟——把用户等待计入模型性能统计，首字延迟和恢复延迟就都失去意义；只看 CPU/GPU 时间，又会漏掉工具限流、环境准备和队列阻塞。对长期 Agent，最有用的观测应该能回答：这段时间它在计算、等待、被授权阻塞，还是已经失去执行者。

## 10. 长任务中的上下文与 KV Cache

### 10.1 先区分三种"恢复"

**任务恢复**需要知道目标、进度和外部动作结果；**上下文恢复**需要重新组织本轮模型应看到的输入；**KV 恢复**尝试复用这些输入曾经算出的中间状态。三者成功条件不同：任务可以在没有 KV 的情况下重新 Prefill 后继续；反过来，找到一份 KV 也不能证明当前任务有权使用其中包含的信息。Muse 没有公开 KV 存储与调度实现，以下都是推理系统层面的设计分析。

### 10.2 复用身份拆成三层

| 层次 | 需要判断的内容 | 常见错误 |
|------|------|------|
| 计算等价 | 实际 token 前缀、权重/adapter、位置等模型输入 | 只看文本、任务 ID 或摘要语义相似 |
| 表示兼容 | 层、张量布局、精度、量化 scale、分片拓扑 | 字节可读就认为能装进引擎 |
| 访问允许 | 租户、共享域、当前可见权限 | 本地 VM 隔离了，远端缓存就无需隔离 |

三项全部成立，才有可复用的 KV。"同一个任务"这个名称没有特殊地位——任务可能重组输入，完全不同的任务也可能共享相同前缀。反过来说，**工具版本变化不必然使未变化前缀的 KV 在数学上失效**：权重、实际输入和位置都没变，这段计算仍等价；任务是否允许继续用旧工具结果，是数据权限层另行判断的事。把所有业务版本机械加进全局缓存键会牺牲不必要的复用，只看 token 又会漏掉权限与表示边界。

### 10.3 前缀稳定性怎样被压缩和记忆更新影响

vLLM 的公开前缀缓存以块为单位建立哈希链：当前块的身份依赖前缀和块内 token，并提供 `cache_salt` 让不同共享域的请求不能直接复用同一组缓存块。

![上下文修改与前缀复用](/assets/img/posts/muse-architecture/fig-09-prefix-reuse.svg)

假设模型输入由稳定说明、工具契约、历史摘要、相关记忆和当前消息组成：当前消息变化，前面的前缀仍可能复用；历史摘要被重写，从第一处变化开始后面的缓存就不能直接沿用了。所以上下文压缩降低 token 数，并不保证本轮延迟也下降——它可能省掉了后续读取的历史，却改变了一段原本命中的前缀。需要联合观察压缩耗时、实际输入 token、最长公共前缀、缓存命中和任务质量，而不是只报一个压缩率。

稳定布局的做法包括固定工具定义顺序、减少不必要的序列化变化、让高频变化的内容不要无故提前到输入开头。但不能为了缓存命中改变指令层级，也不能把低可信记忆提升成高可信系统指令。

### 10.4 应用隔离与物理共享可以不同

主 Agent 和子 Agent 需要独立的应用上下文，不代表它们不能共享相同的公共系统前缀；私人文件需要严格隔离，不代表所有公开工具定义都得重复计算。一个可分析的设计是把公共前缀和私有前缀分为不同共享域，由认证网关注入可信的隔离标识——不能靠终端自己填一个可猜测的用户 ID，也不能把 `cache_salt` 当完整鉴权系统，它负责缓存分区，不负责证明请求者有权读某段数据。

另外，权限代次提升使旧缓存失效，通常只代表旧条目不能继续命中，不等于旧字节已从 GPU、Host 或远端存储物理清除。需要严格删除语义时，应把"不可访问""清理完成""备份回收"分开记录。

### 10.5 长期任务为何不适合一直占用 HBM

一个纯容量例子。假设普通注意力缓存有 32 层、8 个 KV head、每 head 128 维，K/V 各 2 字节：

```text
每 token KV = 2(K 和 V) × 32 × 8 × 128 × 2 bytes = 128 KiB
16,384 tokens 的 KV = 2 GiB
```

这只是一个逻辑载荷的算术示例，还没算分页、对齐和并行布局差异。一批任务如果只是在等用户确认，让这些前缀持续占着 HBM，就压缩了正在计算请求的容量。[SGLang HiCache](/posts/sglang-hicache/) 的 GPU/Host/Storage 分层加异步搬运，可以作为这类问题的实现参照——但它解决的是数据如何跨层保存与回填，不自动决定每个 Agent 的等待阶段该用什么保留策略。

### 10.6 先定义策略边界，再测收益

短工具调用期间保留本地 KV 可能省掉搬运；长审批等待期间下沉或淘汰可能更划算；工作空间已改写、可复用前缀很短时，重新计算可能比恢复更简单。评测至少保留三个对照：**本地缓存策略、远端恢复、直接重算**，记录恢复前缀长度、等待时长、命中层级、队列延迟、传输、安装和首字时间，以及等待期间的显存驻留量和对其他请求吞吐的影响。

不要只报告"远端读带宽很高"——查找、排队、Host staging、H2D、多分片就绪和调度安装都可能进关键路径。某份缓存恢复不完整时，允许安全回退到重算，通常比把残缺状态暴露给 Attention 更重要。

### 10.7 量化改变的是表示层

KV 从高精度压到低精度，改的是字节数，也改了误差和格式兼容性。权重相同、token 相同只说明计算输入相同，不代表不同量化 scale 的缓存可以混用。一个量化缓存对象应该连同格式、scale 和必要元数据一起管理；跨节点恢复时要确认接收端内核消费的是哪种表示、是否需要重排或反量化——传输前后多做几次转换，理论省下的带宽未必变成延迟收益。文本摘要减少输入信息，KV 量化改变中间表示，两者可以组合，但不应共用一项"压缩率"作结论。

## 11. 从执行轨迹到 Agentic RL

### 11.1 能回看，不代表能训练

Meta 说明了执行轨迹对模型训练的用途，但公开材料没有给出优化算法、采样调度或数据协议。这章讨论的是这类个人 Agent 给 Agentic RL 带来的数据要求。

一段人类可读的活动日志适合解释"做了什么"；训练还需要知道"模型当时究竟采样了哪些 token"。中间经过工具解析、文本清洗、摘要和再次编码后，可读文本可能已不再对应原始采样序列。verl 的 Agent Loop 文档明确讨论了这种差异，提供 `prompt_ids`、`response_ids` 和 `response_mask`，用 mask 区分模型生成部分和工具返回部分，并说明把最终 messages 重新编码不一定能恢复原始生成 token。

### 11.2 先保留来源，再构造训练样本

![执行事件与训练轨迹分层](/assets/img/posts/muse-architecture/fig-10-trajectory-layers.svg)

一条训练分段记录的示意（不是 Muse 或 verl 的实际消息格式）：

```json
{
  "trajectory_id": "trajectory-demo",
  "branch_id": "worker-1",
  "segment_id": 3,
  "policy_version": "policy-v7",
  "tokenizer_version": "tokenizer-v2",
  "context_manifest": "manifest-018",
  "tool_environment_version": "sandbox-v4",
  "origin": "model_sample",
  "prompt_token_ids_ref": "blob/prompt-003",
  "sampled_token_ids_ref": "blob/response-003",
  "sampling_logprobs_ref": "blob/logprob-003",
  "result_artifact_ref": "artifact/report/revision-2"
}
```

`origin` 标识内容来源：模型输出是策略动作，工具观察是环境反馈，用户确认是外部控制信号——它们共同影响后续决策，但不能不加区分地当成同一种策略采样数据。工具返回 token 被排除出 policy loss，不等于从 Attention 里删掉，也不等于整个工具交互没有奖励贡献；屏蔽的只是"把外部文本当成模型动作"这一件事。

### 11.3 脱敏之后，旧 logprob 还能不能用

假设脱敏器把上下文里的邮箱地址换成占位符。修改后的文本适合做监督数据，但它已经是一个新的条件上下文——原始采样 logprob 对应的是原始 token 和原始上下文，不能直接贴到脱敏、重写或重新编码后的序列上继续用。这是概率对象的对应关系：`log π(a | s)` 里的动作 `a` 或条件 `s` 变了，原数值描述的事件就变了。

工程上要按训练方法选路径：受控环境里保留原始采样记录做校验；对脱敏数据重新构造适用的训练目标；或在可公开的模拟环境重新采样。检查"JSON 字段齐全"不等于一条轨迹能进强化学习。

### 11.4 权重陈旧、环境变化与 KV 兼容分别检查

一次长轨迹可能跨越多次权重发布，外部工具和环境也在变化。至少有三道不同的检查：**KV 兼容性**决定缓存能否安装复用；**轨迹新鲜度**决定采样策略相对当前训练策略是否过旧；**token/logprob 一致性**决定保存的概率是否仍对应真正采样出的动作。三者不能互相替代——缓存因权重变化不可用，历史轨迹仍可能在允许的 off-policy 规则下被消费；KV 恢复得再对，也证明不了经过文本变换的轨迹还有合法的采样概率记录。给所有对象统一加"版本号"，不如先说清各版本究竟约束了哪一种等价关系。

### 11.5 多 Agent 轨迹通常是偏序关系

两个 Worker 并行执行时，日志时间戳只给出观察顺序，不代表因果关系。把原始轨迹全拼成一个长字符串，容易制造不存在的先后关系：Worker A 不一定看过 Worker B 的工具结果，主 Agent 也未必看过 Worker 的全部历史。训练或回放数据应保留父任务、分支、依赖结果、工具调用和返回之间的关联，再在每个策略执行主体内部组织线性序列——`context_manifest` 的价值就在于记录**这一次生成实际消费了哪些可见输入**。

### 11.6 回放环境比保存轨迹更难

用昨天保存的工具输出可以诊断模型当时为什么那样决策；但模型今天改查另一条条件，旧录制结果就没有对应响应了。Replay 至少分三类：按旧观察复查执行框架；允许有限查询变化的模拟服务；有明确初始状态和状态转移的交互环境——它们支持的评测问题不同，不能统称"可复现"。

τ-bench 提供了一个有价值的公开基线：不只看最终文字，还比较交互结束后的数据库状态和任务目标，并用多次试验衡量行为可靠性。对持久个人 Agent，可以进一步加入第 8 章实验里的故障点、权限撤销、重复提交和等待输入；验收分别记录任务是否完成、外部状态是否正确、有没有未授权动作、恢复有没有产生重复效果。单一的成功分数描述不了全部质量。

## 12. 系统设计的三个落点

Muse 的公开结构给了一个具体案例：把处理不可信内容的执行环境，和持有权限、凭据、持久应用状态的服务分开。继续向存储、推理和训练下钻，最有价值的是三项能力。

**可恢复的状态协议。** 优先定义任务事件、动作、产物与授权之间的关系。检查点保存之后，系统要能说明从哪里恢复、哪些输入仍可见、哪些副作用必须对账。验证方式不是在正常路径重启一次，而是在产物写入、授权确认、动作派发、外部提交、本地落盘之间逐点注入失败——第 8 章的实验只是最小起点。

**跨层的数据身份与失效。** 消息、摘要、检索索引和 KV 有不同的派生关系，版本模型应同时考虑计算等价、存储表示和可见权限，而不是把所有变化塞进一个全局 generation。好的接口应允许两件事同时成立：权限撤销后旧数据不能再被读取；无关的公开前缀和已验证产物仍能复用。先定义细粒度身份与失效传播，再谈保留和调度策略，性能优化才有可靠边界。

**与执行语义一致的性能优化。** 长期任务的成本不只发生在生成阶段——环境准备、工具限流、审批等待、数据搬运和任务恢复共同影响用户看到的完成时间。推理优化应放回整条链路：KV 命中减少了多少重复 Prefill，是否付出了更高显存驻留；下沉是否真为其他任务释放了容量；量化是否降低了端到端传输时延；轨迹数据面是否提高了有效训练样本的产出。

回到一个长期运行的个人助手，系统最终要回答三个问题：**工作停下来以后，留下了哪些可信状态？下一次动作执行前，重新确认了哪些权限和外部事实？恢复计算时，哪些数据能被安全且划算地复用？** 这三条线分别连接持久存储、受控执行和 AI 推理，也决定一个个人助手能否从一次演示走向长期运行。
