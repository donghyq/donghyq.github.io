00 · 全局架构总览

从上层多轮 Agent 负载到底层存储、推理与百卡异步 RL 训练的全栈架构

以下四个工程项目围绕同一套业务体系展开：高并发主搜与多轮搜索智能体（AI Search Agent）。贯穿各项目的核心技术主线是分布式状态存储、GPU 显存生命周期调度与异构计算加速。

上层 AI Search Agent 具有两个显著的运行特征。第一，单次会话需要融合长期记忆、近期对话、实体商品检索与知识库 RAG，上下文长度中位数达到 12.5K Token，且每轮工具调用存在约 2 秒的外部等待窗口。第二，不同复杂度的用户请求需要执行 1 至 6 轮不等的工具调用，轨迹生成长度跨度极大。这两个业务特征直接决定了底层基础设施的技术问题：在线推理侧需要解决工具等待期的 KV Cache 分层存储与跨节点恢复（32×H20 集群），后训练侧需要解决多轮长尾轨迹在训推混部切换时的状态持久化与跨副本接管（128×H20 集群），而检索与算子侧则需要解决底表高频更新与 GPU 扫描长尾（6400 节点检索集群与 SuperOpt 自动优化）。

01 · 业务负载架构 · 多轮搜索 Agent

AI Search Agent 全链路架构与基础设施协同设计

底层推理缓存与强化学习系统的架构设计，直接取决于上层业务负载的数据访问特征。搜索智能体服务（search-agent-server）采用多轮 ReAct 架构，用于处理包含多维约束与跨轮次指代的复杂本地生活查询。当用户提出带有多维约束与跨轮指代的需求（例如：“周六带父母 6 人在国贸聚餐，预算 800 元以内，要上次收藏那家店类似的安静清淡菜，另外查一下黑珍珠套餐周末能否退改”）时，系统需要在一次多轮会话中协同调度长短期记忆（Memory）、结构化实体与内容检索（Entity & Content Search）以及规则知识库检索（RAG）。

1. 端到端请求执行链路与三类检索分工

整个执行流程分为会话初始化加载与 ReAct 多轮工具循环两个阶段。在会话初始化阶段，RecActSearchTool.loadAllMemory() 通过三个异步线程池任务并发拉取用户长期画像、跨会话历史事实与当前会话历史消息。进入 ReAct 循环后，主模型根据每一轮的推理状态输出工具调用指令，由底层执行引擎完成检索并将结果追加回上下文。

2. 上层设计细节：RAG、Memory 与底层 KV Cache 的协同约束

在多轮 Agent 系统中，上层检索与上下文组织方式直接决定了底层推理引擎的 KV Cache 命中率。我们在工程实现中明确了以下三项设计准则：

  • 第一，区分三类检索的语义边界与冲突优先级：实体检索（SqlTransBsRequestTool）负责筛选满足地理位置、营业时间、实时价格等硬约束的商户与商品，文本召回路与 GPU 向量召回路必须执行相同的业务范围过滤；内容检索通过倒数名次融合（RRF，score = Σ 1/(k + rank_i)）合并不同分数量纲的候选；知识库 RAG（RagPipeline + KnowledgeRequestBuilder）用于检索团购退改规则等文档，采用细粒度 Child Chunk 保证向量召回率，命中后根据文档生效版本号（docVersion）和切分标识（splitId / parentId）回读完整 Parent 段落，防止漏掉规则前提或例外条款。对于用户记忆，当本轮显式条件（如“今天吃清淡”）与长期偏好属性（如“平时嗜辣”）发生冲突时，本轮硬约束立即优先生效，长期偏好仅通过后台异步累积证据更新。
  • 第二，采用前缀稳定（Prefix-Stable）的五段式 Context 布局保护 RadixCache 命中：SGLang 的 RadixCache 基于块级 Token 序列前缀哈希进行匹配。如果在 SystemPrompt 或消息头部插入动态时间戳、每轮重新生成的全文摘要或实时变化的检索结果，会导致从变动位置往后的所有 KV 页哈希全部失效，8K 历史上下文被迫全量重算 Prefill。因此，我们在 RecActSearchTool 中将模型可见输入严格固定为五段：SystemPrompt（静态工具定义）→ 会话内冻结的 Memory 快照 → HistoryMessage（历史轮次）→ CurrentMessage（本轮 Query 与历次追加的 Tool Call / Observation）→ AssistantRemindPrompt（动态轮次提示置底）。在同一个多轮会话生命周期内，前四段严格遵循只追加（Append-Only）原则，动态提示永远放在最末尾，从而保证前序 8K～12K Token 的 KV 页在多轮工具调用之间 100% 保持前缀哈希一致。
  • 第三，原始对话持久化与读取侧按需裁剪（MessageClipping）分离：完整原始消息写入消息中心用于离线评测与回溯；送入模型的上下文仅在超过 Token 预算阈值时触发 MessageClipping.clippingMessageList()，优先裁剪早期轮次中冗长的工具原始 JSON 字段并保留结构化结论。该机制在保持前序主干稳定的前提下，将多轮会话平均输入 Token 消耗降低了 48%。

02 · 百卡异步 RL 训练 · VeRL / SGLang / Mooncake / FSDP2

异步 RL Rollout 存储与跨副本 KV 状态恢复

1. STAR 结构化速览与职责边界

Situation（背景与规模）

面向 AI Search 多轮工具调用 Agent 的后训练需求，模型为 Qwen3.5-35B-A3B（30 层 GDN 线性注意力 + 10 层 Full Attention 的混合 MoE 架构，BF16 权重 71.9GB）。生产集群规模为 128 张 H20（16 台 8 卡节点），采用 VeRL 的 Hybrid + Standalone 动态资源调度架构：64 张常驻 Standalone 推理卡（32 个 TP2 SGLang 副本）持续生成样本；另外 64 张 Trainer/Hybrid 混部卡在样本不足时拉起 32 个 TP2 SGLang 副本参与 Rollout，样本水位达到阈值后切回 FSDP2 执行 GRPO 参数更新。

Task（核心技术问题）

多轮搜索 Agent 单条轨迹需执行 1～6 轮外部工具调用，生成长度达 8K～16K Token，长尾效应显著。每当 Hybrid 副本切回 Trainer 模式时面临三个问题：① SGLang 停用副本时未拒绝在途迟到请求，导致客户端协程阻塞阻塞超时；② Hybrid 副本上约 25%～30% 尚未跑完的多轮轨迹若等待自然排空需耗时 50s 以上，若直接 abort 丢弃则浪费已执行的工具调用与数千 Token 的历史状态；③ Qwen3.5-35B 的 30 层 GDN/Mamba 状态为原地递推覆盖，无法按标准 KV 前缀切片补算。

Action（方案选型与核心实现）

从分布式存储与推理引擎状态管理切入，完成四项改造：① 设计 Ray 单写者元数据（Lease + generation）与 Mooncake 大载荷分离存储，持久化 TrajectorySnapshot 并通过 HandoffManifest 保证 n=8 的 GRPO 组完整性后交付 TransferQueue；② 扩展 SGLang 支持活跃请求原地中断与跨 TP Rank 同步导出 Attention KV + Mamba Conv/SSM State（SGLang #45572）；③ 修复 SGLang 停用副本准入阻塞（VeRL #8387），实现源卡落盘后立即 sleep 归还显存、Standalone 经 Conductor 缓存目录路由并行续跑的两阶段回收机制；④ 在训练端补齐跨权重更新轨迹的分段 weight_version 记录、Staleness 过滤、Decoupled PPO 重要性采样及 FSDP2/NCCL 稳定性修复。

Result（全链路量化指标）

① 存储与引擎恢复指标：Mooncake 组快照（约 3.68 MB/group）写/读中位延迟为 21.0ms / 20.2ms；单请求状态捕获耗时 0.1s～1.1s；35B TP2 跨实例恢复实现 0 历史重算 Token，续写 128 Token 与连续生成完全一致（max |Δlogprob| < 0.004）。
② 集群端到端训练收益：Hybrid 切换显存回收等待由 50s+ 压降至 15s 以内，切换边界重复计算 Token 减少 65%，单步训练周期均值由 205s 缩短至 178s，128×H20 集群有效训练吞吐（完整 GRPO Group / GPU·h）提升 15.2%。

2. 架构现状、Profiling 方法与瓶颈定位

在优化前，我们对 128×H20 集群上的单步 GRPO 训练（单步 Global Batch 为 64 Prompts × 8 = 512 条多轮轨迹）进行了全阶段埋点剖析。通过在 VeRL 主循环与 Rollout 管理器中采集 timing_s/gen、timing_s/trajectory_reclaim、timing_s/old_log_prob、timing_s/update_actor 和 timing_s/weight_sync，结合 Prometheus 副本活跃请求监控，定位出以下三处核心瓶颈：

  • 瓶颈一（长尾分布与模式切换冲突）：在多轮搜索场景下，简单查询 1 轮工具调用（约 15～20s）即可结束，而复杂对比查询需要连续调用 5～6 轮工具并生成上万 Token（耗时 60～90s）。监控显示，Rollout 阶段超过 50% 的时间花在等待最后 15%～20% 的长尾样本上。当样本池达到 deactivate_ratio 触发 Hybrid 副本下线时，32 个 Hybrid 副本上仍有大量处于第 3～4 轮工具交互的半截轨迹。
  • 瓶颈二（源卡回收等待与丢弃重跑的两难）：原生 DynamicResourceController 在停用 Hybrid 副本时，如果等待在途长尾请求自然跑完，64 张 Trainer 卡会被迫空等 50s+ 才能拿到显存；如果直接调用 abort_replicas 强制中止（Abort）在途请求并交由 Standalone 重试，前几轮已经完成的外部搜索 RPC 和数千 Token 的 Prefill 全部作废，Standalone 瞬间涌入大量从第 0 轮重跑的请求，造成单步收尾时间进一步拉长。
  • 瓶颈三（副本停用时的迟到请求集合通信阻塞）：在 remove_replicas 到负载均衡器生效的微小时间窗内，或者异步客户端并发派发子轮次请求时，仍有少量请求落到正在下线的 Hybrid 副本上。原生 SGLangHttpServer.abort_all_requests 忽略了 reject_request=True 参数，仅将内部状态置为暂停等待，导致这些迟到请求永久卡在 _resume_event.wait() 上，进而拖住整个 GRPO Group 无法凑齐 n=8 提交训练。

在方案设计阶段，我们结合训练团队学城文档（Fully Async 方案 2733349254、动态资源调度 2774983061、Staleness 控制 2771059299）与开源社区演进（VeRL 26Q4 Roadmap #8186、Mooncake RL 拆分 RFC），在三个技术维度上进行了系统对比与取舍：

维度一：训推资源调度模式 • 方案 A（同步 Colocate）：全卡同时做 Rollout，全部跑完再切 Trainer。长尾阶段 80% 显卡空等最后几条轨迹。

• 方案 C（Hybrid + Standalone 动态混部）：保留 64 卡常驻 Standalone，让 64 卡 Trainer 在空闲期变形为 Hybrid 推理副本助推采样。		 选定方案 C，并重点攻克模式切换损耗。
动态混部能够双向复用训练与推理空闲算力，主要难点在于 Hybrid 副本切回训练模式时的在途长尾请求处理。只有解决切换时的状态保存与源卡显存提前释放，动态混部才能在多轮长轨迹场景发挥最大收益。

  2. GRPO 样本组状态划分与完整性校验：切换发生时，一个 n=8 的组内各样本进度不一。HandoffManifest.validate() 强制校验：completed_members（已生成完）∪ checkpointed_trajectories（已保存快照待续跑）∪ pending_samples（尚未开始）必须严格等于下标集合 {0, 1, ..., 7} 且两两互斥。目标端 run_target() 直接复用 completed 记录，仅对后两类发起生成，全部完成后经 TransferQueue 读回对账才确认发布。
  3. Conductor 缓存感知路由（conductor_router.py）：通过非阻塞 ConductorHTTPClient（application/msgpack，超时上限 50ms）查询各 Standalone 副本的本地前缀命中层级与队列负载。路由层先过滤掉 cache_salt（内含 weight_version）不匹配或过载的副本，再对比预估恢复耗时与重算耗时，仅在长前缀有净收益时派发至命中副本。

class ConductorLoadBalancer(GlobalRequestLoadBalancer):
    @staticmethod
    def _local_score(hit: dict, prompt_length: int) -> tuple[int, int]:
        # 显式读取 Rank 0 的累积前缀命中数，校验单调性，仅取 (device, cpu_local) 本地两层作为优选依据
        rank = hit.get("rank_matches", {}).get("0", {})
        values = tuple(rank.get(key, 0) for key in ("device", "cpu_local", "cpu_share", "disk"))
        if values != tuple(sorted(values)):
            raise ValueError("non-cumulative prefix counts")
        return values[:2]

    def acquire_server(self, request_id: str, prompt_ids: list[int] | None = None, **extra):
        if self._updating:
            raise RuntimeError("No available servers in load balancer: weight publication pending")
        if not prompt_ids or len(prompt_ids) < self._min_tokens:
            return self._fallback(request_id, "short_prompt")
        # 负载均衡硬约束：仅在并发差距不超过 _load_gap 的副本集合内优选缓存命中，防止单副本热点排队
        minimum = min(self._inflight_requests.values())
        candidates = {sid for sid, count in self._inflight_requests.items()
                      if count <= minimum + self._load_gap and sid in self._instances}
        hits = self._client.query({**self._context, "token_ids": prompt_ids})
        scores = {sid: self._local_score(hits[self._instances[sid]], len(prompt_ids))
                  for sid in candidates if self._instances[sid] in hits}
        best = max(scores.values(), default=(0, 0))
        if best[1] < self._min_tokens:
            return self._fallback(request_id, "no_local_advantage")
        preferred = min(sid for sid, score in scores.items() if score == best)
        return preferred, self._servers[preferred]

模块五：跨权重更新轨迹的训练数值对齐（trainer_base.py & replay_buffer.py）

在异步训练中，一条长轨迹的前半段可能由参数版本 πθk−1 生成，经历一次参数同步后，后半段由 πθk 续写完成；同时推理引擎（SGLang）与训练引擎（FSDP2）底层的 Attention / MoE 算子实现存在数值精度差异（即训推 mismatch）。我们在训练侧通过三层机制保证梯度更新稳定：

  • 第一，分段权重版本号记录（Segment Weight Version）与 Staleness 淘汰：在 TrajectorySnapshot 中按生成片段记录对应的 weight_version 和采样时直接由 SGLang 输出的 rollout_log_probs；进入 ReplayBuffer 时检查样本组的最大版本滞后步数，超过 staleness_threshold 的过期样本组直接驱逐。
  • 第二，工具返回掩码严格对齐（response_mask）：多轮轨迹中包含大量由搜索/RAG 工具返回的 Observation Token，这部分 Token 并非模型采样生成，必须在 response_mask 中严格置 0，仅对模型实际生成的 Action/Reasoning Token 计算策略梯度与 KL 惩罚。
  • 第三，Decoupled PPO 重要性采样校正（compute_rollout_correction_and_add_to_batch）：在 trainer_base.py::_compute_advantage 中结合训练引擎重算的 old_log_probs 与采样时记录的 rollout_log_probs 计算重要性采样权重与截断（IS Clipping / Rejection Sampling），补偿跨步 off-policy 与训推算子差异带来的分布偏移。

模块六：基于强基线的分布式异步 Checkpoint 优化与全状态崩溃续训（async_checkpoint_batch.py & stage_and_publish.py）

在大规模 RL 训练中，容错 Checkpoint 属于与在线 Rollout 存储互补的冷/温持久化数据面。我们的优化起点并非单点聚合或未开启分片的原始配置，而是已开启分布式分片保存（use_dist_checkpointing=True）与异步保存（async_save=True）的社区最新强基线（团队此前已通过开启分片保存将早期单点导出耗时从 2000s+ 降至约 360s 级）。但在推进高频容错保存与断点续训时，分阶段打点暴露了三个跨框架耦合与共享存储层面的深层问题：

  • 问题一（跨层调用触发“伪异步”主线程阻塞）：VeRL v2（megatron_checkpoint_manager.py）为解耦产物目录，将同一步保存拆分为 model/dist_ckpt、optimizer/dist_ckpt、extra/dist_ckpt 三个独立的 AsyncRequest 依次调用 async_calls.schedule_async_request(req)。而在 Megatron-Core 持久化异步写入队列底层，调度下一个请求执行 preload_tensors 暂存前，会强制等待前一个请求在后台落盘完毕以限制主机内存。这导致前两项（占 99% 体积的模型与优化器分片）实际上同步阻塞在训练主线程中，使 async_save=True 失去重叠效果。
  • 问题二（容器 FUSE 共享存储单流瓶颈与 MDS 元数据风险）：Megatron 0.19.2 默认单 Rank 仅用 1 个写线程（且先同步写完最后一个分片再拉起其余线程），经容器 FUSE 挂载写入 DolphinFS / BeeGFS 时受网络 RTT 与 fsync 限制，单流吞吐仅 20～35 MB/s，导致数十 GB 主机暂存缓冲区长时间无法释放；但若在 MoE 专家并行（EP）下盲目按分片开满线程，百卡并发创建上千文件流又会直接冲击文件系统元数据服务（MDS）。
  • 问题三（异步崩溃半成品与 RL 多状态恢复错位）：异步后台写入中途若遇进程崩溃，目标目录会残留半截分片；同时 Megatron dp_reshardable 加载器在恢复原生 Adam 时存在覆盖参数组权威 step 计数及向 requires_grad=True 视图原地拷贝报错的缺陷，且 RL 续训必须同时对齐模型、优化器、LR Scheduler、RNG 与 TransferQueue 数据游标。

难点三：16K 长序列冷续写第 79 Token 分叉与 DCP 慢盘阻塞 ① 16K 序列从断点冷续写时，在剩余第 79 个 Token 处与不中断连续解码出现 Token 分叉；
② 多机保存分布式检查点（DCP）时偶发卡住数分钟甚至超时。		 ① 零缓存对照确认分叉并非缓存污染，而是“冷续写 Prefill+Decode”与“纯 Decode”走了不同 Batch Shape 的 CUDA Kernel，浮点归约顺序不同（Batch-Invariance 差异）叠加 Mamba 状态累积所致；

② DCP 改为先写本地内存文件系统（tmpfs）立即放行训练步，后台线程异步刷入远端存储。

【Situation & Task】“这个项目是在 128 张 H20 集群上落地 Qwen3.5-35B-A3B 多轮搜索 Agent 的异步 GRPO 训练。我们采用的是 64 卡常驻 Standalone 推理池加 64 卡 Trainer/Hybrid 动态混部池的架构——当样本队列还没攒够时，64 张 Trainer 卡会拉起 32 个 TP2 的 SGLang 副本协同参与 Rollout 采样；一旦样本水位达到 deactivate_ratio，这 64 张卡就要切回 FSDP2 做参数更新。但在多轮搜索场景下，一条轨迹要调 1 到 6 轮外部工具，生成长度上万 Token，最后 20% 的长尾样本占了单步一半以上的时间。每次 Hybrid 卡要切回训练时都面临两难：若阻塞等待长尾轨迹自然排空，64 张训练卡需闲置等待超过 50 秒，甚至因为原生 SGLang 停用时没拒绝迟到请求发生阻塞挂起；如果直接 abort 把半截轨迹扔回 Standalone 从第 0 轮重跑，前面调过的搜索工具和算好的几千 Token 全部作废并重新执行，而且 Qwen3.5-35B 里有 30 层 GDN 线性注意力，它的 Mamba 状态是原地递推覆盖的，没法像普通 KV 一样靠前缀切片补算。”

【Action - 选型与实现】“针对这个问题，我们调研对比了多版本权重并存（显存开销太大，35B 单份权重就要 72GB）和纯 Token 重算方案，最终选择从分层状态存储与两阶段显存回收切入，做了四块核心改造：
第一，设计了控制面与数据面分离的 Rollout 存储：用单写者 Ray Actor 管 Lease 和单调递增的 generation 号防止脑裂双写，用 Mooncake Store 存不可变的 TrajectorySnapshot（包含 Token、response_mask、Behavior Logprob 和工具结果，每组约 3.68MB，读写中位 21ms/20ms），并通过 HandoffManifest 把 n=8 的组严格切成已完成、半截快照和未开始三类，确保不丢不重地交付给 TransferQueue。
第二，我在 SGLang 实现了活跃请求原地中断和跨 TP Rank 状态导出（SGLang #45572），把 10 层 Full Attention KV、30 层 GDN 的卷积与递归状态以及解码游标一起导出，支持目标 Standalone 副本分配新 Mamba 槽位后零重算直接续写。
第三，我修复了 SGLang 副本下线忽略 reject_request 导致迟到请求阻塞超时的 Bug（VeRL #8387），并把切换改成两阶段协议：网关先摘流，Hybrid 卡把快照刷进 Mooncake 确认 quiesced 后，不等长尾跑完，15 秒内直接 sleep 把显存还给 FSDP2 开训；剩余轮次由 Conductor 缓存目录结合 cache_salt 和恢复成本选最优的 Standalone 副本在后台并行补齐，与 Actor 更新完全重叠。
第四，在训练端我们按分段记录跨步轨迹的 weight_version，配合 Staleness 过滤和 Decoupled PPO 重要性采样控制 off-policy 偏差，并同时定位并修复了 FSDP2 首次 Adam Step 惰性分配 OOM 和 NCCL 权重广播缺少流同步导致双缓冲踩踏的问题。”

追问 1（原理深挖）：追问 1（负载对比）：为什么单轮长思维链（如 235B 数学推理）通常只做 Token 级 Partial Rollout，而 35B 多轮工具 Agent 场景需要引入混合状态跨副本恢复与成本门控？
这正是基于工作负载特征（Workload Characterization）做的定量取舍。在 235B 纯单轮长推理（如数学 CoT，Prompt 仅几百 Token、Decode 长达 20K Token 耗时 400s）中，Prefill 仅占 10s，且单条 KV 高达 3.6GB，跨步权重变化后旧 KV 又不能给新权重用，因此单轮跨步场景只需复用已生成 Token/Logprob。但在我们的 35B 多轮搜索 Agent 场景中：① 发生中断的主要时刻是同一权重版本内 Hybrid 切回训练、将半截请求转交给同版本 Standalone 副本（此时权重并未改变，KV 完全合法可用）；② 多轮工具交互把前序上下文拉长到了 8K～16K Token，且 Qwen3.5-35B 含 30 层 GDN 线性注意力，不存 Mamba 状态就只能从第 0 个 Token 全量重算；③ 即便如此，我们也实测发现当上下文较短（低于平衡点 L*）或跨了权重版本时搬运 KV 不划算，所以专门设计了成本门控 + 分层恢复：同版本长上下文走 KV+Mamba 零重算恢复，短上下文或跨权重版本自动退化为仅恢复 Token 快照重算 Prefill。因此通过成本门控按序列长度和权重版本自适应分流，能够兼顾两类负载的最优效率。
追问 2（算法与系统交叉）：详细讲讲训推 mismatch 和异步 off-policy 偏差是怎么产生的？代码里怎么修的？
异步 RL 中存在两层分布偏差：
第一层是训推引擎算子数值偏差（Engine Mismatch）：Rollout 用 SGLang（FlashInfer / Triton 定制融合核、特定 TP 归约顺序），Trainer 用 FSDP2（FlashAttention / PyTorch 原生算子）。即便传入完全相同的权重 θ 和 Token 序列，两边算出的 Logits 和 Logprob 也会有微小差异（πrollout ≠ πtrain）。如果训练时只用训练引擎重算的 old_log_probs 当分母，就会忽略当时真正决定采样动作的其实是推理引擎的概率分布。
第二层是参数版本滞后（Policy Staleness）：异步模式下轨迹由旧版本 θt−k 采样（甚至 Partial Rollout 前后半段跨越了两个版本），却用来更新当前策略 θt。
我们的代码治理分三步：① 采样阶段强制保存 SGLang 采样阶段直接输出的行为策略概率 rollout_log_probs 及每段对应的 weight_version；② 在 ReplayBuffer 入口限制最大版本差（动态扣减已积压陈旧样本配额 num_staleness_sample，超限组直接淘汰）；③ 在 trainer_base.py::_compute_advantage 中启用 compute_rollout_correction_and_add_to_batch（Decoupled PPO 模式），利用保存的 rollout_log_probs 与稳定参考策略计算重要性采样修正系数与双边截断（Dual-Clip / Token-level TIS），防止极端重要性采样比率引发梯度发散。
追问 3（分布式容错细节）：如果 Standalone Worker 拉取了 HandoffManifest 正在续跑第 5 条样本时自己也宕机了，或者旧 Hybrid Worker 网络分区恢复后又发来一份结果，系统怎么处理？
靠 单调代际锁（Generation Fencing）+ 租约超时回收（Lease Expiration）+ 不可变载荷摘要校验 三个机制兜底：
1. 防旧 Worker 脑裂迟到写：源端发起交接时，RayTrajectoryCoordinator 原子递增该任务的 generation。旧 Hybrid Worker 持有的旧 lease_id / generation 立即失效，哪怕它因网络卡顿晚发来 commit_snapshot 请求，Coordinator 核对 expected_generation 不匹配会直接拒绝。
2. 防目标端接管后二次宕机：Standalone Worker 认领交接任务时会获取带 TTL 的新 TrajectoryOwnerLease 并定期心跳续租；若该 Worker 中途崩溃导致租约过期，且 Mooncake 上的原始快照对象是只读不可变的，其他存活的 Standalone Worker 会在下一轮扫描中重新认领该 Manifest，直接跳过已标记为 completed 的成员，仅重跑未完成的成员。
3. 防 TransferQueue 重复投递：在 agent_loop_tq.py 中，只有凑齐 8 条成员并通过 TransferQueue 读回校验确认数据落盘后才将任务状态置为 FINISHED；若发布中途出现网络未知错误，系统停止盲目自动重发，保持 RUNNING 待协调器幂等对账，杜绝同一组样本进两次优化器。

1. STAR 结构化速览与显存/耗时剖析

Situation（背景与集群拓扑）

服务于 AI Search 在线多轮 ReAct Agent 推理，主模型为 Qwen3-30B-A3B（48 层 GQA，KV Head 数为 4，Head Dim 为 128）。生产集群采用 32 张 H20（8 组 Prefill 实例 + 8 组 Decode 实例，每实例 TP2） 的 P/D 分离架构，并挂载 GPU HBM（L1）、Host DRAM（L2）与 Mooncake 共享存储（L3）三级缓存。线上会话上下文 P50 约 12.5K Token，超过 54% 的深度搜索请求包含多轮工具调用，其中搜索工具 search_pro_tool 占比 87%，每次调用外部等待窗口 P50 为 2.02s（P90/P99 约 2.18s）。

Task（核心瓶颈与挑战）

在 TP2 BF16 下，单 Token 的 KV 体积为 48 × 2 × 4 × 128 × 2B = 96 KiB（单 Rank 48 KiB），一条 8K 上下文占 768 MiB（16K 占 1.5 GiB）。在 2 秒工具等待窗口内面临三个核心问题：① 若将历史 KV 锁在 HBM 中，几十个并发挂起会话即可占满显存池；若直接释放走全局 LRU，2 秒后工具返回时历史页已被冲掉，被迫重算 8K Prefill 并跨网重传 800MB 数据；② 跨实例从 Mooncake 恢复时存在并发写半截数据、batch_get_into 短读脏页及单 Rank 失败引发的集合通信阻塞与 0 Token 截断；③ 恢复控制路径存在 77ms 跨 Rank 事件轮询等待，且无准入控制的盲目预取会挤占前台活跃请求。

Action（技术选型与优化方案）

① 分布式可靠恢复与 FP8 扩容：在 mooncake_store.py 实现按 Rank 隔离的 基于 generation 的两阶段 Manifest 索引 与字节长度强校验，TP 组内执行 all_reduce(MIN) 对齐连续命中前缀；打通 K-per-head / V-per-layer 静态 FP8 KV Scale 加载与 FlashInfer 消费链路，使单 Token KV 体积减半。
② 等待期软硬引用解耦与 DAG 淘汰：拆分 RadixCache 会话软引用（session_ref）与活跃请求硬锁（lock_ref），等待期保留 Host 完整副本并释放独占 GPU 页；按多分支工作流未来消费距离与共享分支数构建淘汰最小堆，支持页对齐叶子节点惰性切分。
③ 异步控制链与恢复成本门控：移除 77ms 跨 Rank 同步轮询，将生命周期提示放入每会话保序异步队列；结合工具预计返回时间、前台预留水位（foreground_reserve_tokens）与 Restore-vs-Recompute 成本门控执行预取准入。

Result（全链路量化收益）

① 单请求与控制链实测（4×H20 1P+1D 实机受控基准）：8K 会话续接 Prefill 侧重算输入由 8216 降至 34 Token（单对 HTTP TTFT 785.8 → 425.2ms，−45.9%）；25 次 Resume 的 ready→首 Token P50 延迟由 460.8ms 降至 215.8ms（−53.2%），有效 GPU KV 驻留积分下降 3.7%；512 Token 短前缀由成本门控自动切重算，TTFT 131.6 → 96.6ms（−26.6%）；FP8 异构粒度将 30B 模型 Attention MSE 降低 13.9%。
② 32×H20（8P+8D）高峰并发表现：集群整体 Resume 请求 TTFT P50 降低 25.7%、均值降低 13.2%，高峰 SLO 达标吞吐提升 12.9%。

2. Profiling 耗时拆解与技术选型对比

优化前我们使用 PyTorch Profiler、Nsight Systems（NSYS）以及 SGLang 内置的分阶段指标（sglang:storage_prefetch_phase_duration_seconds，细分为 lookup / queue / transfer / host_stage / h2d / install / scheduler_ready / sync 八个阶段）对 8K/16K 请求进行了逐阶段剖析：

  • 算力与搬运耗时锚点：在 TP2 H20 上，16K 冷 Prefill 的 Attention Kernel 累计耗时约 574ms / Rank（占 Kernel 总时间约 59%）；而通过 PCIe 执行 Host→GPU H2D 搬运的实测带宽为 38.4～49.5 GiB/s（单层 H2D 约 20ms，8K 前缀双卡共 768 MiB 的纯 H2D 传输耗时约 10～15ms）。这意味着长前缀从 Host/L3 恢复的理论硬件耗时远小于重新计算 Attention。
  • 为什么理论很快，早期实测恢复却不快？分阶段打点暴露了两个软件层开销：一是恢复路径在等待跨 TP Rank 状态确认时使用了带固定轮询间隔的非阻塞事件检查，额外引入了约 77ms；二是当上下文很短（如 512 Token，仅 48 MiB）时，原本重算 Prefill 只需 96.6ms，而走远端查找、队列调度、缓冲分配和写回却要花 131.6ms。
技术决策点备选方案对比选型结论与工程依据
决策一：工具等待期的显存驻留策略 • 策略 A（Pin 死 HBM）：工具执行期间保持 lock_ref > 0 不释放 GPU 页。高并发下 40 个挂起会话即耗尽 30GB+ 显存，新到达的前台首轮请求直接排队超时。
• 策略 B（纯原生 LRU 释放）：轮次一结束立即归零引用，与普通单轮请求混排淘汰。2 秒等待期内极易在等待期内被并发请求驱逐，且淘汰子任务后缀时会把父节点公共前缀一并回收。
• 策略 C（软硬引用分离 + Host 保底 + 工作流 DAG 最小堆 + 提前预取）：等待期降级为软引用优先让出 HBM，但强制保留 Host 副本，在工具返回前 200～300ms 择机预取回 HBM。		 选定策略 C。
兼顾了等待期 HBM 复用率（有效 GPU 驻留积分降低 3.7%）与 Resume 命中率（8K 重算从 8216 降至 34 Token），并通过页对齐叶子切分避免误删多分支共享主干。
决策二：恢复 vs 重算的触发机制 • 策略 A（凡命中必恢复）：只要 L2/L3 查到前缀就无条件发起拉取。缺点是短前缀（<1K Token）拉取开销大于重算，且高峰期密集 H2D 会挤占前台请求带宽与空闲页。
• 策略 B（Runtime Cost Gate + 前台水位保护）：在线对比预估恢复耗时与重算耗时，并检查扣减预取页后是否仍高于 foreground_reserve_tokens。		 选定策略 B。
512 Token 短前缀自动绕开无效拉取（TTFT 降低 26.6%），长前缀在保障前台活跃请求不退化的前提下执行预取。
决策三：KV Cache FP8 量化粒度 • 方案 A（Per-Layer 静态 FP8）：K 和 V 均按整层共用一个缩放因子（Scale）。实现最简单，但 Key 矩阵存在显著的 Head 间通道离群值（Outlier），按层量化精度损失大。
• 方案 B（Per-Token 动态 FP8）：每次在线计算每个 Token 的最大绝对值。跨节点传输需附带大量动态元数据，且增加在线归约开销。
• 方案 C（K-per-head / V-per-layer K-per-head / V-per-layer 静态 FP8）：针对 K 按注意力头校准静态 Scale，V 保持按层静态 Scale。		 选定方案 C。
逐层误差分解证实收益几乎全部来自 K 的细粒度缩放：K-per-head / V-per-layer 将 30B 模型 Attention 输出 MSE 降低 13.9%，而把 V 进一步细化到 per-head 无额外收益。静态 Scale 天然兼容 Mooncake 跨节点零拷贝复用与 FlashInfer FA3 内核。

模块一：Mooncake Commit-Last 代际写入与短读/多 Rank 对齐（mooncake_store.py）

交互细节：当 SGLang HiCacheController 将 Host 缓存页异步刷入 Mooncake 或从 Mooncake 恢复到 Host Staging Buffer 时，直接操作裸物理页会面临并发写撕裂与单 Rank 部分缺失问题。我们在 MooncakeStore 中实现了基于递增 generation 的两阶段 Manifest 发布与字节校验：

python/sglang/srt/mem_cache/storage/mooncake_store/mooncake_store.py:760按 Rank 隔离 Manifest + 字节级短读拦截
class MooncakeStore(HiCacheStorage, MooncakeBaseStore):
    def _manifest_key(self, logical_key: str) -> str:
        # 每个 TP/PP/CP Rank 拥有各自独立的 KV 分片，Manifest 必须按 Rank 坐标隔离，避免并发互覆
        rank_key = f"{self.local_rank}:{self.pp_rank}:{self.attn_cp_rank}"
        return self._tag_keys([f"__sglang_generation_manifest__:{rank_key}:{logical_key}"])[0]

    def _generation_key(self, logical_key: str, generation: str) -> str:
        return f"{logical_key}__sglang_generation__{generation}"

    def _write_manifest(self, logical_key: str, generation: str, members: List[str]) -> None:
        manifest = {"schema_version": 1, "logical_key": logical_key,
                    "generation": generation, "members": members}
        # 仅当该页全部成员物理键 put 返回 0 后，最后一步写入 Manifest 发布可见性；中途失败不发布 Manifest
        ret_code = self.store.put(self._manifest_key(logical_key),
                                  json.dumps(manifest, sort_keys=True, separators=(",", ":")).encode("utf-8"))
        if ret_code != 0:
            raise RuntimeError(f"Failed to publish Mooncake manifest for {logical_key}")

读取与跨 Rank 同步边界：读取时先校验 _read_manifest() 合法性，随后调用 batch_get_into。针对上游 _batch_postprocess 将任何正返回值视为成功（导致 256B 目标缓冲区仅读回 128B 时残留尾部脏数据）的问题，我们强制校验返回字节数严格等于目标页切片总长度，任何不完整页直接转为 Cache Miss。最后在 TP 组内对连续命中的页数执行 all_reduce(MIN)（若 _page_transfer_kv_batch 抛异常则记 0 页并继续发送 PrefetchAck），确保两个 Rank 在完全相同的连续前缀边界处进入 Prefill，杜绝单卡失败引发的 NCCL 集合通信阻塞。

模块二：会话生命周期状态机与 DAG 最小堆淘汰（streaming_session.py & unified_radix_cache.py）

交互细节：我们在 session_ref_tracker.py 与 unified_radix_cache.py 中引入了四态会话生命周期 SessionLifecycleState（ACTIVE、TOOL_WAITING、READY_SOON、COMPLETED）：

  • 软硬引用分离：请求在 GPU 上执行前向时持有硬锁 lock_ref > 0（不可淘汰）；当本轮解码结束进入 2 秒工具调用时，状态转为 TOOL_WAITING，释放 lock_ref 但保留会话软引用 session_ref，同时在 Host DRAM 池中 Pin 住完整历史页副本。
  • DAG 感知淘汰与惰性切分：当 HBM 不足触发 evict() 时，淘汰最小堆优先回收仅被 TOOL_WAITING 持有的节点，保护 ACTIVE 与 READY_SOON 节点。对于多子任务分支共享同一 8K 主干前缀的 DAG 工作流，结合分支共享数与未来消费距离排序；当某个子分支的尾部页需要被淘汰时，在页对齐边界处对 Radix 树叶子节点执行惰性切分（Split），仅释放子分支独占后缀页，保留公共父节点。

模块三：异步控制链改造与 Runtime Cost Gate

为了消除恢复路径上的控制面阻塞，我们将原本在主线程同步执行的生命周期信号（TOOL_WAITING / READY_SOON）改造为每工作流独立的后台保序 FIFO 队列，并移除恢复完成等待中的跨 Rank 轮询（省去 **77ms**）。在 mark_ready_soon() 触发 prefetch_from_storage() 前，执行两步准入检查：

  1. 显存安全水位准入：检查当前 GPU 空闲页扣除本次预取页后是否仍大于 foreground_reserve_tokens，防止后台预取把正在运行的前台请求或邻居会话的父节点挤出 HBM。
  2. 恢复 vs 重算成本门控（Cost Gate）：根据分阶段耗时模型对比预估恢复时间 Trestore(L) = Tlookup + Tqueue + L · Btoken / BWH2D 与重算时间 Trecompute(L)。对于 512 Token 短前缀（校准恢复约 119.9ms > 重算 99.8ms），门控直接拒绝远端恢复并走本地重算，实测单请求 TTFT 由 **131.6ms 降至 96.6ms（−26.6%）**；对于 8K/16K 长前缀则放行预取。

模块四：Dynamo Agent 感知 KV 路由与 SGLang P/D 会话桥接（agent_cache.rs & prefill_handler.py）

在 32×H20（8P+8D）在线推理集群中，网关路由层（NVIDIA Dynamo）不仅需要将多轮 Resume 请求路由到存有历史前缀的实例，还需要解决三个在线特有问题：① 命中同样长度的 8K 前缀时，驻留在 GPU HBM（Device）与驻留在主机内存（HostPinned）或远端存储（External）的恢复耗时相差数倍；② P/D 分离下 Prefill 与 Decode 两个 Worker 都需要感知同一个 Agent 会话标识以关联各自的软引用槽位；③ 开启 FP8 KV 后必须防止格式作用域（cache_scope）不兼容的 P/D 实例建立传输握手。

  • Rust 路由层二阶段有界决策（lib/kv-router/src/scheduling/agent_cache.rs）：我们在 Dynamo 的 KV Router 中扩展了 AgentCacheStatus 结构，Worker 按固定周期导出脱敏命名空间摘要、可复用 Token 数、当前所处存储层级（AgentCacheTier::Device / HostPinned / Disk / External）、会话状态（Active / ToolWaiting）、代际号 epoch 以及恢复开销参数（lookup_cost_blocks / restore_cost_blocks）。路由器在第一阶段前缀树匹配与队列负载筛选后，综合缓存层级恢复延迟与排队等待时间选出预计首字完成最早的 Worker，并严格保持“路由提示仅用于选实例，物理缓存安全仍由 SGLang 引擎独立校验”的边界。
  • P/D 双端被动 session_id 透传与 FP8 作用域门控（prefill_handler.py & decode_handler.py）：SGLang 支持两种会话参数：session_params.id 属于显式有状态会话，若未事先调用 open_session 会直接报错拒绝；而顶层请求字段 session_id 用于被动关联 RadixCache 会话归属与等待期生命周期。我们在 Dynamo 的 Prefill 和 Decode 处理器中从 agent_context.session_id 提取标识并透传至顶层 session_id 参数，并在发起 Decode Bootstrap 握手前前置校验双端 FP8 cache_scope 兼容性，不兼容时在建连前快速失败回退，避免传输阶段挂起。

04 · 异构向量检索与实时列存 · CUDA / C++ / Lucene / Spark

分布式搜索索引与 GPU 异构检索基础设施

1. STAR 结构化速览与技术选型对比

Situation（平台规模与业务特点）

平台管理 50+ 集群组、约 6400 节点，支撑主搜近 2 亿商品向量的实时检索、AI Search 多路召回以及高频商品价格/库存变更。本地生活检索具有两个鲜明特点：一是每次向量召回都伴随严格的城市、地理多边形配送范围、门店营业状态等标量过滤；二是商品改价与向量增删改极其频繁。

Task（三大性能与存储瓶颈）

① IVF 聚类桶倾斜导致 GPU 扫描长尾：真实商品分布极不均匀，热门类目单个 IVF 大桶包含 16.5 万条向量（约为中位桶的 10 倍），旧内核采用“一桶绑一个 CUDA Block”导致单个 SM 扫描耗时高达 30.87ms，其余 SM 空闲，且单 Query 下 8 个类目串行启动内核开销大（1.24ms）；
② 向量实时更新触发全量重建：静态 GPU 索引无法原地处理高频向量新增与删除；
③ Lucene 高频改价写放大：原生 Lucene Segment 不可变，修改 8 字节价格需执行整文档 Delete+Add，触发频繁 Segment Merge 与 JVM GC 抖动。

Action（架构选型与核心实现）

① CPU 前置过滤 + CUDA IVF 动态拆块与多类目合批：采用 CPU 倒排（IndexSort + RLE 与 dvTerms）前置严格过滤，仅跨 PCIe 上传 Query 与合法候选下标 idx_t；按命中桶候选规模动态拆分为多个 CUDA Block 并发扫描 FP16 向量，在 Shared Memory 内维护局部 TopK 后二级归并；将同 Query 下 8 个类目合并单次发射，配合 Pinned Memory 双缓冲与多 Stream 异步流水。
② Base + Delta 无锁实时向量索引：按 IVF 桶组织增量主槽位与溢出区，通过 Reserve → Write → Publish 快照协议、Revision 版本号与 Tombstone 位图实现读写无锁并发。
③ Lucene Codec/SPI mmap 原地改价：定制可写 DocValues 列存，通过堆外 LongIntHashMMap 主键字典与 mmap LongBuffer 按 DocID O(1) 覆写 8B 价格列，并适配 Segment Merge 重映射。

Result（实测性能与线上效果）

① H20 百万级 128 维向量基准下，IVF 大桶扫描内核耗时由 30.87ms 压降至 4.50ms（降低 85.4%），8 Query 批次自适应拆块核 P50 达 3.55ms；
② 单 Query 8 类目合批设备端执行耗时由 1.24ms 降至 0.82ms（加速 1.51x）；
③ Base + Delta 在同卡持续读写并发下，查询内核 P50/P99 为 2.61ms / 4.31ms，单批写入从提交至可见 P50 仅 0.71ms；
④ Lucene 价格变更摆脱整文档重写放大，实现秒级查询可见。

选型问题备选方案对比最终选型与技术依据
问题一：标量过滤与 GPU 向量计算如何分工？ • 方案 A（GPU 后过滤 Post-Filter）：先在 GPU 搜全局 TopK，再回 CPU 过滤营业状态与配送范围。缺点是当过滤率极高（如仅 1% 门店可配送）时，TopK 被全部滤空导致召回为 0。
• 方案 B（全量标量上 GPU）：把几十个动态业务字段全拷进 GPU。缺点是显存占用大且字符串/多边形判断在 GPU Warp 内造成严重分支发散（Warp Divergence）。
• 方案 C（CPU 倒排前置严格过滤 + 仅传候选下标上 GPU 算 FP16 距离）：CPU 跑 get_index_ids，GPU 常驻紧凑 FP16 向量矩阵。		 选定方案 C。
CPU 最擅长跳表与位图布尔求交，过滤后仅剩数千至数万个 4/8 字节整数下标，跨 PCIe 异步拷贝耗时不足 0.1ms；GPU 只做最擅长的规整 FP16 向量距离计算与规约，消除零召回与 Warp 发散。
问题二：为什么线上用 IVF-Flat (FP16) / IVF-PQ，而不是全放 HNSW 图索引？ • HNSW 图索引：无过滤时查询极快，但：① 图邻接表内存开销极大；② 结合高选择率前置过滤时，图游走路径上的中间节点大量被标量条件剪断，极易断路掉召回；③ GPU 上随机图遍历属于非合并访存（Uncoalesced Memory Access），带宽利用率低。
• IVF 分桶 + 桶内连续内存扫描：命中桶内候选连续排布，天然契合前置过滤与 GPU 高带宽合并访存。		 选定 IVF 架构 + 动态拆 Block（超大规模冷库辅以 M=16 IVF-PQ 14.5x 压缩粗筛）。
既保证了严格业务过滤下的 100% 桶内精确召回，同时充分释放 H20 的 HBM 顺序访存带宽。

追问 1：Base + Delta 实时向量索引在后台全量重建（Compaction）切换的一瞬间，如果有新的增量写入和删除进来，怎么保证不丢更新且不读到旧版本？
通过单调递增的全局 Revision（修订版本号）+ 双写过渡窗口 + 代际校验保证。每条写入或删除都携带严格递增的 Revision。当后台线程在时间点 T0（对应水位 Rev_0）拉起快照构建新一代 Base_{new} 时，在线新到达的增量（Rev > Rev_0）继续写入活跃 Delta 区。当 Base_{new} 物化进 GPU 准备切换时，保留所有 Rev > Rev_0 的 Delta 记录与 Tombstone 位图；查询时若同一个向量 ID 同时出现在 Base_{new} 和保留的 Delta 区中，内核按最高 Revision 胜出（若最高版本为 Tombstone 则直接过滤），从而彻底防止后台旧快照覆盖切换期间的新写入。

2. 分布式训练、通信与推理系统原理追问库

广度题 1（训练显存与通信账本）：FSDP2（ZeRO-3）下训练一个参数量为 Ψ 的混合精度（BF16 参数 + FP32 AdamW 状态）模型，静态显存怎么算？每步通信量是多少？为什么你们在 Step 1 会遇到 OOM？
1. 静态显存公式（总量为 16Ψ 字节，按 N 张卡分片）：
• BF16 参数（2B）+ BF16 梯度（2B）+ FP32 主权重 Master Weights（4B）+ FP32 AdamW 一阶动量 exp_avg（4B）+ 二阶动量 exp_avg_sq（4B）= 16Ψ Bytes。对于 35B（Ψ ≈ 35 × 109）模型，总静态状态约 560 GB，在 64 张卡 FSDP 全分片下每张卡静态分片仅占约 8.75 GB。
2. 为什么实际单卡会飙到 70~80GB 甚至在 Step 1 OOM？
因为除了静态分片外，显存大头在于：① AllGather 临时完整层参数与梯度缓冲区（FSDP 在前向/反向计算某一层或某个模块组时，需把该层分片 AllGather 成完整参数，特别是 MoE 大专家层）；② 长序列（8K~16K）激活值（Activations），即便开了 Activation Checkpointing（重计算），仍需保存层间边界激活；③ 首次 optimizer.step() 瞬态峰值：PyTorch AdamW 默认在第一次 step() 时才遍历参数分配 8Ψ / N 的动量张量，此时反向传播刚结束，预留的梯度通信 Bucket 尚未释放，叠加 Python/CUDA 缓存分配器块对齐碎片，极易冲破 96GB HBM 红线。通过启动时预初始化优化器状态（Pre-allocate States）、限制 FSDP Prefetch Bucket 数量并配合 expandable_segments:True 可稳定解决。
3. 通信量公式：前向每层一次 AllGather（通信量 Ψ），反向每层一次 AllGather（Ψ，若开启重计算）加一次 ReduceScatter 聚合梯度（Ψ），单步总通信量约为 3Ψ。
广度题 2（网络与集群排障）：百卡训练或 Mooncake RDMA 传输中遇到 NCCL Timeout 或 IB 报错，你们的标准排查 SOP 是什么？
严格遵循“先区分计算卡死还是网络故障，再定位具体物理节点”的四步法：
1. 查日志错误码定位故障类型：在训练或传输日志中搜索 ibv_modify_qp 或 completion error。如果看到 RDMA error 12（IBV_WC_RETRY_EXC_ERR，重传次数耗尽），说明本机网卡发包后对端无响应。
2. 从 Peer IP 反查对端物理节点：从报错连接信息中提取对端 Peer IP，映射到具体物理机与 Rank 号，而不是盲目重启报错的当前节点。
3. 检查对端节点状态：登录对端物理机检查 dmesg（是否有 Xid 硬件错误如 Xid 79 掉卡、Xid 31/43 非法访存）、检查进程是否僵死在 CPU I/O（如慢盘读写、分布式检查点 all_gather_object 阻塞）或单 Rank 缓存分支不一致（如一卡走恢复、一卡走重算导致集合通信顺序错位）。
4. 带宽降级排查：若连接正常但 RDMA 吞吐远低于线速（如 IB 理论 50GB/s 实测掉到十几 GB/s），核查 GDR（GPUDirect RDMA / nvidia_peermem）是否加载生效、PCIe ACS 是否关闭、以及 Mooncake 分片传输粒度（如调整 MC_SLICE_SIZE 与队列深度）是否过小导致小包门铃（Doorbell）开销主导。
广度题 3（推理引擎对比）：SGLang 和 vLLM 在 KV Cache 管理与调度上的核心区别是什么？为什么你们选 SGLang + HiCache + Mooncake？
1. 前缀缓存数据结构不同：vLLM 的 Automatic Prefix Caching（APC）基于固定大小 Block 的扁平哈希表管理；SGLang 核心采用 RadixAttention（基数树 RadixCache），将共享前缀组织成树形节点，天然契合多轮 Agent 对话、多分支工具调用（DAG）和 GRPO 同 Prompt 多采样（n=8）的树状前缀共享与按子树裁剪。
2. 多级存储与异步预取扩展性（HiCache）：SGLang 的 HiCache 架构将 L1 GPU Pool、L2 Host Tensor Pool 与 L3 外部存储后端（HiCacheStorage 接口，原生对接 Mooncake Store）做成统一分层控制器，并支持 Overlap Scheduler（将 CPU 调度与 GPU Kernel 异步重叠），非常适合我们在工具等待间隙插入 TOOL_WAITING / READY_SOON 生命周期钩子与跨节点零拷贝恢复。
广度题 4（RL 算法基础）：GRPO 相较于标准 PPO 省掉了什么？在百卡训推中这带来了什么系统架构优势？
标准 PPO 需要同时维护四个模型：Actor（策略模型）、Critic（价值模型 Value Network，通常与 Actor 同规模）、Reference Model（参考模型）和 Reward Model。其中 Critic 需要独立做前向和反向参数更新，显存和算力开销几乎翻倍。
GRPO（Group Relative Policy Optimization） 对同一个 Prompt 采样一组输出 {o1, o2, …, oG}（我们线上设 G = 8），直接用组内奖励的均值和标准差归一化计算相对优势：Ai = (ri − mean(r)) / std(r)，从而彻底省掉了庞大 Critic 模型的显存占用、前反向计算与优化器状态。反映到系统架构上，省下一整套 35B Critic 的训练显存后，64 张训练卡才能在不开启极重度 Offload 的情况下高效跑通 FSDP2 更新，但代价是训练端消费单位变成了“必须凑齐同 Prompt 的全部 G = 8 条轨迹才能算 Advantage”——这也正是为什么单个慢工具长尾样本会卡住整组交付，以及我们必须做 HandoffManifest 组完整性接管的根本原因。
