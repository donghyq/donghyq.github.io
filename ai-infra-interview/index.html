0.1 所有性能题先套“四类瓶颈”#

图 18｜四类瓶颈最终统一到一张图

性能优化先不要急着背工具或技巧。先问：现在到底是“算不动、搬不动、等太久，还是 GPU 根本没活干”？ 四类瓶颈对应四种完全不同的优化方向。

瓶颈典型现象本质常用优化
Compute-bound（计算受限）Tensor Core / CUDA Core 接近饱和数据已经喂得上，但计算单元算不过来低精度、改善 MMA tile / pipeline、减少非矩阵 FLOPs
Memory-bound（存储带宽受限）HBM / L2 / SMEM 某层接近带宽上限，而计算利用率不高算力在等数据Tiling、data reuse、fusion、量化、layout / coalescing
Latency-bound（延迟受限）带宽和算力都没满，但 warp 经常 stall、eligible warp 少单次访问或依赖太慢，又没有足够并行工作把等待藏起来提高并行度、减少依赖、控制 register pressure、double buffering、async pipeline
System-bound（系统受限）NSYS timeline 出现 GPU 空洞问题不在单个 Kernel，而在 CPU、通信、调度或并行策略CUDA Graph、减少同步、通信计算 overlap、batching、消除 pipeline bubble / straggler

四类优化分别在“优化什么”

1. Compute-bound（计算受限）：让单位时间算得更多。 MMA tile 是调整矩阵分块，让 Tensor Core（张量计算核心） 吃得更满，但 tile 太大又会增加寄存器和 Shared Memory 压力；低精度（如 BF16（16 位脑浮点数格式，动态范围接近 FP32）→FP8（8 位浮点格式，用于降低存储与计算开销）/FP4（4 位浮点格式，通常需要更细的缩放策略））既可能提高 Tensor Core 吞吐，也会减少数据量；减少非矩阵 FLOPs 是因为 GEMM 越来越快以后，Softmax（指数归一化，把分数转成概率权重）、Norm、激活函数、地址计算等非 Tensor Core 工作反而可能成为新瓶颈，FA4 优化 Exp 就是典型例子。

2. Memory-bound（存储带宽受限）：少搬数据，并让搬来的数据多用几次。 Arithmetic Intensity（算术强度）表示每搬 1 Byte 能做多少 FLOPs；data reuse（数据复用）是把 HBM 数据搬到 SMEM / Register 后重复利用；fusion（算子融合）让中间结果不必反复写回 HBM，同时减少 Kernel Launch；量化直接减少 Weight / Activation / KV 的字节数；layout（数据布局）则让 global memory 访问更 coalesced、Shared Memory 少 bank conflict，并匹配 Tensor Core 所需的 tile。

3. Latency-bound（延迟受限）：把“等待”藏起来。 依赖链过长时，后一条指令必须等前一条结果；memory latency高时，需要其他 ready warp 接替执行；register pressure（寄存器压力）过高会减少一个 SM 能同时驻留的 warp，严重时还会 spill；eligible warp是真正已经准备好、当前可以被 scheduler 发射的 warp。常见方法是增加可并行工作、software pipelining、double buffering，以及 cp.async / TMA 这类异步数据搬运。

4. System-bound（系统级开销受限）：让 GPU 持续有活干。 CPU（中央处理器，主要承担主机端控制与调度） launch慢会让短 Kernel 之间出现空洞；同步如 cudaDeviceSynchronize、频繁 D2H 或 .item() 会强迫 CPU/GPU 互等；NCCL overlap是把 AllReduce / AllToAll 等通信尽量藏在计算后面；pipeline bubble常来自 PP 的填充/排空和 microbatch 不足；straggler是某个 rank 更慢导致其他 rank 在 collective/barrier 等待；Serving 中还要检查 scheduler 是否造成小 batch、负载不均或频繁切换。

第一原则：MFU 低不等于 Kernel 差，先定位是哪一层。优化也不是一次结束：Memory-bound 被解决后，瓶颈可能迁移到 SMEM、Softmax/SFU 或计算单元。

S1. End-to-End 性能诊断#

1.1 MFU#

Model FLOPs Utilization（模型 FLOPs 利用率）粗略表示模型有效 FLOPs / GPU 理论峰值 FLOPs。它低可能因为 GPU 根本没在算，也可能因为通信、数据、调度或 hot kernel 本身低效。

30 秒面试答案#

我会先确认 MFU 的计算口径和 precision peak 是否正确，然后 top-down profiling。先用 torch.profiler / Nsight Systems 看端到端 timeline，区分 GPU bubble、CPU 同步、通信暴露、pipeline bubble、负载不均，还是 GPU 一直 busy。如果时间集中在少数 hot kernel，再用 Nsight Compute 下钻，先用 Roofline 判断 compute-bound 还是 memory-bound，再看 Tensor Core、HBM/L2/SMEM、occupancy、eligible warp、stall reason、register spill 和 bank conflict。优化后必须回到端到端 workload 验证 wall-clock/MFU，而不是只看 microbenchmark。

import torch
from torch.profiler import profile, ProfilerActivity, record_function
x = torch.randn(2048,2048,device="cuda",dtype=torch.float16)
w = torch.randn(2048,2048,device="cuda",dtype=torch.float16)
for _ in range(10): y = x @ w  # warmup
with profile(activities=[ProfilerActivity.CPU,ProfilerActivity.CUDA],
             record_shapes=True,profile_memory=True) as p:
    with record_function("gemm"):
        for _ in range(10): y = x @ w
    torch.cuda.synchronize()
print(p.key_averages().table(sort_by="self_cuda_time_total",row_limit=10))
p.export_chrome_trace("trace.json")

1.3 Roofline Model（屋顶线模型）#

Arithmetic Intensity = FLOPs / Bytes moved

Performance <= min(Peak Compute, Memory Bandwidth × Arithmetic Intensity)

AI 小更可能 memory-bound；AI 大更可能 compute-bound。大 batch GEMM 常更偏 compute-bound；LLM Decode 的 GEMV/小 GEMM、KV 读取常更偏 memory-bound。

Q：Occupancy 越高越好吗？ 不是。Occupancy 是 latency hiding 的手段，不是 KPI。为了提高 occupancy 而缩小 tile、降低 reuse，可能更慢；真正看是否有足够 eligible warps 隐藏延迟。

1.4 Roofline 反推 Matmul 的最佳输入长度

S 级 · 知识点 → 计算/实现 → 追问

从硬件 Roofline 反推最小高效 GEMM M（示意）
硬件P：有效计算吞吐；BW：有效带宽
模型A[M,K] × W[K,N]
瓶颈AI = FLOPs / Bytes
求解AI ≈ P/BW 处的 M，再实测

这是简化的 bandwidth/compute 交叉点，不能直接当作真实最佳 batch。

设 GEMM A[M,K]×W[K,N]，权重为 b_w Byte/元素，激活与输出为 b_a Byte/元素；粗略假设 W 从 HBM 读取一次，A/C 各访问一次，忽略 cache/tile/临时 buffer：

FLOPs ≈ 2 M K N ； Bytes ≈ K N b_w + M (K + N) b_a
AI(M) = 2 M K N / [K N b_w + M (K+N) b_a]

令 R = 有效计算吞吐 P / 有效带宽 BW（FLOPs/Byte），交叉点近似为：

M_cross ≈ R K N b_w / [2 K N - R (K+N) b_a]

只有分母为正，才存在这个简单模型下可进入 compute-bound 的 M。比如假设 K=7168、N=2048、权重/激活均 BF16、R=200 FLOPs/Byte，解得 M_cross≈229。这个数字仅为示例，并非 DeepSeek 的推荐 Expert Batch（批次，一次并行处理的样本或请求集合）。

真正最佳 M 还受 Tensor Core Tile 对齐、Group GEMM、Kernel Launch、SM Occupancy、量化 scale、Cache 复用和 Router（路由器，决定 Token 或请求交给哪个 Expert/实例） token 分布影响。面试官问“最佳输入大小”，要先说明目标是吞吐最大、单次延迟最小、还是 SLO（服务级目标） 下的最小批量，然后用 benchmark 对 8/16/32/64/128/256 等 M 做扫点。

追问：给定 GPU 标称 600 TFLOPS 和 3 TB/s，为什么不能直接宣称 R=200 后得到最佳 M？
标称峰值不是 workload 的可持续计算吞吐，理论 HBM 带宽也不是所有访存层级的有效带宽。精度、频率、功耗、MMA tile、L2/SMEM、launch overhead 都改变有效 R；先作为粗略下界/拐点，再实测。
面试 30 秒： 先定义 GEMM 的形状和数据类型，写 FLOPs 与 Bytes，利用 Roofline 求算力/带宽交叉 M；再检查 Tile、Occupancy 和 Grouped GEMM，最后对目标 Batch 做实测。不能仅凭 GPU 理论峰值给出“唯一最佳 token 数”。

S2. GPU 执行模型#

CTA 被调度到 SM（Streaming Multiprocessor，流式多处理器）；warp 是核心调度执行粒度之一。

2.1 SIMT 与 Warp Divergence#

图 1｜GPU 执行层级

SIMT（Single Instruction, Multiple Threads，单指令多线程）：warp 内线程执行同一指令流，但有独立状态。线程走不同分支时出现 divergence（分支发散），不同路径需分别执行并 mask。

2.2 Latency Hiding#

图 2｜Latency Hiding：GPU 如何隐藏长内存延迟

先抓住一个反直觉点：GPU 并不是靠“单次访存延迟很低”获得高性能，而是靠大量并发工作把延迟藏起来。一个 warp 发出 HBM load 后可能要等很久；只要 SM 上还有别的 ready warp，scheduler 就切过去继续发射指令。

所以 Latency Hiding（延迟隐藏） 的关键不是“驻留 warp 越多越好”，而是等待发生时有没有足够的 eligible warp（可发射 warp） 或独立异步工作可执行。

  • Resident warp：已驻留 SM；
  • Eligible warp：依赖满足、可执行；
  • Issued warp：本周期真正发射；
  • Occupancy：resident warp 相对硬件上限比例。

3.3 Padding#

float tile[32][32] 按列访问时 stride=32，线程可能全落同一 bank。改为 tile[32][33]，33 mod 32=1，bank 被打散。

3.4 Swizzle / XOR Swizzle#

Padding（填充） 改 stride；Swizzle（地址重排）改变 logical → physical layout。简化为 physical_col = col XOR f(row)：把参与 bank index 的低位与更高维坐标混合，打散规则冲突。Tensor Core tile 访问高度规则，所以 layout 是性能核心之一。

手撕 bank conflict#

  1. 地址转 word index；2. bank=word%32；3. 按 bank + distinct word 分组；4. broadcast 特判；5. 统计最大序列化程度。

3.5 GPU 全局内存、进程共享、Constant Memory 与虚拟地址

GPU 存储与地址空间：程序所见的地址不等于物理 HBM 位置
SM 内Register / Shared Memory / L1；Local Memory 可能落显存
GPU 全局L2 + Device Global Memory / HBM
只读常量__constant__ 区 + Constant Cache；参数也可能用 Constant 路径
虚拟地址每进程地址空间；GPU MMU/TLB → 物理显存

常量到底放在哪里？ CUDA 的 __constant__ 全局变量位于 Device Constant Memory，适合 Warp 内相同地址的广播读取。编译期标量常量可以作为立即数或常量参数处理；Kernel Arguments、只读纹理等有不同访存路径，不能一口咬定“所有 const 参数都在 Constant Memory”。

两个进程能访问同一 Global Memory（GM）物理页吗？默认不能拿进程 A 的 GPU 指针直接在进程 B 解引用；可通过 CUDA IPC 或 VMM 显式建立跨进程共享映射，访问共享 buffer 时再考虑同步/原子与生命周期。UVA（统一虚拟寻址）也不意味着随意跨进程解引用相同地址。

CUDA 官方：IPC、Unified Virtual Address Space、Constant Memory。

追问：同一 GPU 的两个进程同时对同一 buffer 写入会怎样？
若通过 IPC/VMM 映射为共享内存，必须有明确同步；没有同步的竞争写入结果不确定。Atomic 能保证单次读改写原子性，但并不保证并行更新次序确定，也不自动提供业务层一致性。
追问：什么情况下一个核上两个线程比一个线程更快？
先澄清“核”指 CPU 物理核还是 GPU SM：CPU 的 SMT 可在一个线程遇到缓存未命中时用另一线程填补执行空隙；GPU 单 SM 可调度多个 Warp 隐藏访存延迟，同一 Warp 多个 Lane 可同时处理独立元素。两线程并不保证更快，资源争用与同步也可能变慢。

S4. GEMM：Kernel 优化母题#

C[M,N] = A[M,K] × B[K,N]。

Naive GEMM 反复从 HBM 读 A/B，复用差。Tiling（分块）把 A/B tile 搬到 Shared Memory；Register Blocking（寄存器分块）再让每个 thread/warp 维护小 accumulator tile。

更大 tile 提高 reuse，但增加 SMEM/register pressure，可能降低 occupancy；这是经典 trade-off。

为什么 GEMM 是 GPU Kernel 的“母题”？
LLM 里 Linear、QKV projection、Attention 的 QK/PV、MoE（混合专家模型） Expert，本质上大量时间都落在矩阵乘。把 GEMM 学透，其实是在学习 GPU 优化最核心的三件事：数据怎么分块、数据在哪里复用、计算与搬运怎么重叠。

4.0 从 Naive GEMM 推到高性能 GEMM

图 5｜GEMM Tiling：为什么 Data Reuse 是核心

  1. Naive：每个线程算一个 C 元素，不断从 HBM 重新读 A/B。问题不是乘加本身慢，而是同一数据被反复搬运。
  2. CTA Tiling：一整个 thread block 协作把 A/B 的 tile 搬进 Shared Memory，一次 HBM load 服务很多乘加，提高 Arithmetic Intensity。
  3. Register Blocking：warp/thread 再把热点 operand 放进 register，并维护多个 accumulator，继续增加 reuse。
  4. Tensor Core MMA：不再让 CUDA Core 一条条做 scalar FMA，而用专门矩阵乘单元完成 tile-level MMA。
  5. Pipeline：当前 tile 在 Tensor Core 计算时，异步预取下一 tile。最终目标不是“某一步最快”，而是让 Tensor Core 尽量不停。

4.1 Double Buffer / Pipeline#

图 6｜Double Buffer / Software Pipeline

朴素：Load0 → Compute0 → Load1 → Compute1。 流水：Compute0 时预取 Load1。

Tensor Core 执行 MMA（Matrix Multiply-Accumulate，矩阵乘累加）。架构演进的重要主线就是：更高效地搬 operand、持续喂饱 MMA、管理 accumulator，并与 softmax/epilogue 等非 MMA 工作重叠。

S5. Ampere → Hopper → Blackwell#

核心不是背功能表，而是理解：数据搬运、地址生成、矩阵计算和 accumulator 管理逐渐交给专用硬件；Kernel 从“所有 warp 都做所有事”变成异步 producer-consumer pipeline。

5.1 Ampere：cp.async#

cp.async 支持 global → shared 异步拷贝，使 load 与 compute 更容易 overlap。但 thread/warp 仍承担较多数据移动与流水管理。

为什么这是一个转折点？传统路径常近似为 global → register → shared，搬数据本身占用线程指令和 register。cp.async 让 global→shared 更直接，并允许“算当前 tile 的同时搬下一 tile”。但地址计算、拷贝指令发射和 pipeline bookkeeping 仍主要由普通线程负责，这正是 Hopper TMA 继续优化的地方。

5.2 Hopper：TMA + WGMMA + Warp Specialization#

图 7｜Hopper：TMA + WGMMA + Warp Specialization

TMA（Tensor Memory Accelerator，张量内存加速器）#

TMA 是数据搬运引擎，不是 Tensor Memory。少量线程描述多维 tensor transfer，硬件负责地址生成和 global↔shared 搬运。价值：减少大量线程做 load/store/address calculation，让数据移动更容易和计算重叠。

从 cp.async 到 TMA 的本质：不是简单“拷贝更快”，而是把 tensor 地址生成 + 多维搬运 从大量 CUDA thread 中卸载给专用硬件。这样 producer 只需发起描述符式传输，更多线程/register 可以留给计算。

WGMMA（Warpgroup Matrix Multiply-Accumulate，Warp 组矩阵乘累加）#

Hopper 的 wgmma.mma_async 由 warpgroup（典型 4 warps / 128 threads）协作执行异步 MMA。相比传统 warp-level MMA，更适合大 tile 和异步 pipeline。

Warp Specialization（Warp 专职化）#

不再每个 warp 都 load+compute，而是：

不同 warp 承担不同角色，形成 producer-consumer pipeline。

为什么专职反而更快？如果每个 warp 都同时负责 load、地址计算、MMA、softmax，它们需要携带所有状态，控制流和 register pressure 都更复杂。专职化后 producer 重点维持数据流水，consumer 重点喂 Tensor Core；二者通过 barrier/async transaction 协作，更容易把不同硬件 pipeline 同时跑起来。

Thread Block Cluster / DSMEM / Multicast#

Hopper 增加 Thread Block Cluster（线程块集群）。Cluster 内 CTA 可协作，并通过 Distributed Shared Memory（分布式共享内存）访问 peer CTA 的 shared memory。TMA multicast 可以把一份 global data 分发到 cluster 内多个 CTA 的 SMEM，减少重复 HBM 流量。

5.3 Blackwell：TMEM + tcgen05 + 2-CTA MMA#

TMA ≠ TMEM#

  • TMA：Hopper 已有的数据搬运 engine；
  • TMEM / Tensor Memory（张量内存）：Blackwell 为 Tensor Core 数据/accumulator 引入的专用片上存储。

意义：减少 MMA accumulator 对普通 register file 的压力，让 Tensor Core pipeline 与 CUDA core / epilogue 更解耦。

为什么 accumulator 会成为问题？大 MMA tile 会产生大量中间累加值。如果这些值长期占普通 register，单个 CTA/warpgroup 的 register footprint 会膨胀，限制 resident CTA/warp 数，也让 epilogue 与 Tensor Core 争夺 register file。TMEM 相当于给 Tensor Core 增加专门的“中间结果工作区”，所以 Blackwell 的优化不能只理解成 FLOPS 变高。

tcgen05#

Blackwell 第五代 Tensor Core 的 PTX 指令族，如 tcgen05.mma、load/store/copy 等。面试不要把它回答成一种数据类型。

2-CTA / 2-SM MMA#

两个 peer CTA / SM 协作完成更大的 MMA tile，可扩大数据复用范围、减少部分 SMEM traffic/reduction 开销。理解“为什么跨 SM 合作可能有价值”比背指令参数重要。

5.4 架构演进一句话#

图 8｜Ampere → Hopper → Blackwell

  • Ampere：让 load 更异步；
  • Hopper：把 tensor 搬运和大 MMA 专门化，并用 warp specialization 做流水；
  • Blackwell：继续把 accumulator/矩阵数据放入专用 TMEM，并扩大 Tensor Core 协作范围。

5.5 IEEE754、AtomicAdd 与 Kernel 数值可复现性

数值误差的因果链
IEEE754 FP3224 bit 有效精度（含隐藏位），约 7 位十进制有效数字
大数与小数当小数远小于当前 ULP，减法会被舍入掉
并行归约求和顺序变化，浮点加法非结合
原子操作AtomicAdd 次序变化 → 末位可能不同
FP32: float32(9.9 × 10⁹) = 9,900,000,256；当前相邻浮点数间隔 ULP = 1024

因此 float32(9.9e9) - float32(1e-9) 的结果不溢出，舍入后仍等于输入的 FP32 大数。这里是精度丢失，不是 Overflow（上溢）。9.9e9 本身也并不能在 FP32 中精确表示。

import numpy as np
x = np.float32(9.9e9)
y = np.float32(1e-9)
print(int(x))       # 9900000256
print(np.spacing(x))# 1024.0
print(x - y == x)   # True

相同输入也可能出现不同末位：并行归约、AtomicAdd、不同 Kernel/Tensor Core Precision 模式可改变舍入路径。生产验收应定义 bitwise equality（逐位一致）还是数值容忍误差（abs/rel tolerance），对生成模型还要考虑排序接近时的小误差如何改变采样/路由路径。

参考：PyTorch Numerical Accuracy。

追问：AtomicAdd 是原子的，为什么仍可能不确定？
原子保证单次操作不可被其他线程拆开，但多个线程对同一地址的到达顺序仍可能变化；FP32 加法非结合，更新次序不同导致舍入末位差异。

S6. Attention → FlashAttention 1~4#

6.1 普通 Attention#

S = QK^T，P = softmax(S)，O = PV。

朴素实现最大的系统问题之一是中间 N×N attention matrix 反复写入/读取 HBM。

6.2 FA1：IO-Aware#

图 9｜FlashAttention：为什么不再落完整 N² 矩阵

FlashAttention（闪存注意力算法） 1 的核心不是近似 Attention，而是 tiling + online softmax（在线 Softmax），在 SRAM/SMEM 内处理 block，避免 materialize 整个 attention matrix 到 HBM。

关键词：减少 HBM IO。

为什么 Online Softmax（在线 Softmax） 是关键？如果按普通 softmax，必须先看到整行 score 才知道全局 max 和归一化分母；这似乎迫使我们保存完整 QK^T。Online Softmax 用 running max / running sum 在 block 间增量合并统计量，因此可以“一块算完就消费”，不必把整个 N×N score 矩阵落到 HBM。FlashAttention 的核心因此是改变 IO 复杂度，而不是近似 attention。

6.3 FA2：更好的并行划分#

FA1 已经减少 IO，但 GPU work partition 仍可优化。FA2 改进 block/warp 任务划分，减少 non-matmul FLOPs 和 warp 间通信，提高并行度。

关键词：更好的 work partition。

6.4 FA3：吃满 Hopper#

利用 TMA、WGMMA、异步 pipeline、warp specialization，让：

关键词：algorithm pipeline → hardware pipeline。

FA3 的思维重点不是“用了 Hopper 新指令”这么简单，而是把 Attention 拆成不同硬件可以并行推进的阶段：TMA 搬 K/V、Tensor Core 做 QK/PV、CUDA/SFU pipeline 做 softmax。Warp Specialization（Warp 职责专门化） 再把这些阶段分配给不同角色。算法依赖链仍然存在，但硬件空闲时间被更充分地填掉。

6.5 FA4：为什么 Blackwell 又出现新瓶颈#

图 10｜FA1 → FA2 → FA3 → FA4：瓶颈一直在迁移

Tensor Core 变得更快后，非 MMA 部分的相对占比上升：Shared Memory traffic、Softmax reduction、Exp/SFU 可能成为瓶颈。这叫 Asymmetric Hardware Scaling（非对称硬件扩展）。

因此 FA4 类优化会关注：TMEM、2-CTA MMA、减少 SMEM traffic，以及 Softmax/Exp 的执行成本。

为什么优化 Exp#

Softmax 的 exp 不走 Tensor Core，而依赖特殊函数/普通算术 pipeline。当 MMA 大幅加速后，exp 可能跟不上。优化思想包括用 polynomial approximation（多项式近似）把部分工作转移到更空闲的 FMA pipeline。

Delayed / Conditional Rescaling#

Online softmax 维护 running max。max 更新时旧 accumulator 需要乘 exp(old_max-new_max) 重缩放。如果 max 变化很小，可减少/延迟部分 rescale bookkeeping，从而降低非 MMA 工作。

面试重点不是背近似系数，而是解释：Tensor Core 太快后，为什么 Softmax 变成相对瓶颈。

6.6 Flash-Decoding：短 Q、长 KV 的并行化

S 级 · 知识点 → 计算/实现 → 追问

FlashDecoding：短 Q、长 KV 时沿 KV 序列维增加并行
Q：一个 TokenQuery 长度≈1，单头 CTA 数可能不足
切 KV历史 128K 拆成多个 KV Chunk
并行不同 CTA 分别算局部 Softmax 统计
合并局部 max / sum / numerator 精确归并

与 FlashAttention 减少 N² 中间 IO 的动机不同：Flash-Decoding 主要解决短 Q 下的 GPU 并行度不足。

每个 KV Chunk j 计算局部三元组 (m_j, l_j, u_j)：分块 score 最大值、指数和、加权 V 分子。跨块精确合并：

m = max_j(m_j)； L = Σ_j exp(m_j-m) l_j； O = [Σ_j exp(m_j-m) u_j] / L

当 Batch×Head 很小、历史上下文很长时有利；当历史 KV 较短或 Batch 已足够大，分块带来的额外归并、同步和 workspace 反而可能抵消收益。它与 Speculative Decoding（推测解码） 是两条不同方向：前者提高单次 Attention 的并行度，后者减少串行 Target（目标模型，负责验证候选 Token 的大模型） Step。

来源：PyTorch Flash-Decoding 官方博客。

追问：为什么不能简单给每个 Q head 一个 CTA？
在 Decode 的 Q≈1、小 Batch 下，可并行 CTA 数≈batch×heads，可能远低于 GPU 的 SM 数；把 KV 进一步切块并行，最后使用 log-sum-exp 稳定归并，可以填充更多 SM。

S7. MHA → GQA → MLA 与 KV Cache#

7.1 为什么 KV Cache 会大#

图 11｜MHA → GQA → MLA：都在减少历史状态成本

MHA（Multi-Head Attention，多头注意力）Decode 时每个历史 token 都需要保存 K/V。KV 大小近似随 layers × seq_len × kv_heads × head_dim × dtype × 2(K,V) 增长。

7.2 MQA / GQA#

  • MQA（Multi-Query Attention，多查询注意力）：多个 Q head 共享一组 K/V；
  • GQA（Grouped-Query Attention，分组查询注意力）：若干 Q heads 共享一个 KV head。

目的：显著降低 KV Cache 与 Decode memory bandwidth，同时比 MQA 保留更多表达能力。

7.2.1 MHA/MQA/GQA/MLA：Decode 的计算访存比怎么变？

核心矛盾：Decode 每次仅计算很短的 Q，却反复读取长历史 KV
MHA每个 Q head 对应独立 KV head → 历史 KV 最多
GQA/MQA多个 Q head 共享较少 KV heads → 减少历史读取
MLA缓存 latent + RoPE 部分；吸收式还改变计算路径

假设 B 个 Decode Tokens、历史长度 T、Query Heads=Hq、KV Heads=Hkv、Head Dim=D、精度 b Byte，忽略 Projection（线性投影，把向量映射到另一维度）/Softmax/Cache Hit：Attention FLOPs≈4·B·Hq·T·D；KV Bytes≈2·B·Hkv·T·D·b。因此粗略算术强度：AI≈2Hq/(Hkv·b)，说明 GQA/MQA 通过更少的 KV Heads 提升每字节历史读取对应的计算量。

特别注意：这个简化式假设同一次计算没有跨 Batch 复用 KV，也忽略 Q/O、Projection、SMEM traffic 和 KV Cache 的块访问。MLA 使用不同的 latent 与位置维度、Weight Absorption、Group 计算路径，不能把 Hkv=1 直接带入这个 GQA 式子。

追问：为什么 MQA KV 减少很多，但某些模型未必比 GQA 更好？
MQA 让更多 Query Heads 共享同一 K/V，降低带宽但可能损失表达能力。工程上还要考虑 Head 数、Tensor Core Tile、Attention Kernel、TP 复制与调度；必须兼顾模型质量和吞吐。

7.3 MLA（Multi-head Latent Attention，多头潜在注意力）#

MLA 进一步对 KV 做 latent compression（潜变量压缩）。简化理解：

c_KV = x W_DKV，其中 latent 维度远小于完整 K/V；需要时再通过 up projection 参与 attention。

因此 Decode 不必为每个历史 token 存完整多头 K/V，而可主要保存压缩 latent 和位置相关部分。

把 MHA → GQA → MLA 看成同一条演进线：
MHA 为每个 Q head 保存独立 K/V；GQA 让多个 Q head 共享 KV head；MLA 更进一步，不只是“共享 head”，而是让历史信息主要以低维 latent 形式缓存。它们都在解决 Decode 阶段同一个核心矛盾：每生成 1 个 token，都要反复读取越来越长的历史状态。

7.4 Decoupled RoPE（解耦旋转位置编码）#

图 12｜MLA Decode：为什么要 Decoupled RoPE + Weight Absorption

RoPE 给 K/Q 注入位置依赖。如果直接把所有 K 都低秩吸收，会与位置旋转耦合。因此 MLA 将 content part 与 RoPE part 分开处理，使 content projection 可被吸收/压缩，同时保留必要位置表示。

7.5 Weight Absorption（权重吸收）直觉#

Decode 阶段希望避免“先把 latent 展开成巨大 K/V，再做 attention”。利用矩阵乘结合律，把某些 up-projection 权重吸收到 Q projection / output projection 一侧，使计算直接围绕 latent 进行，从而同时省 KV 容量和 memory traffic。

手撕 MLA 最低要求#

必须能写出并解释：

  1. Q projection；
  2. KV down projection 得 latent；
  3. content / RoPE 拆分；
  4. score；
  5. softmax；
  6. latent/value path；
  7. output projection。

追问重点：Prefill 与 Decode 为什么可能使用不同实现？ Prefill 矩阵更大、compute reuse 高；Decode 更受 KV bandwidth、batch shape、cache layout 影响，最佳 kernel/data path 不同。

7.6 MLA Chunked Prefill：KV Load 后 Projection 的激活问题

S 级 · 知识点 → 计算/实现 → 追问

MLA Chunked Prefill（分块预填充）：区分两种“激活很大”
空间很大KV latent → up projection 产生完整 K/V 临时 Tensor
数值很大低精度 Projection 存在 Outlier/溢出/饱和风险
空间优化Tile 化 Load+Projection+Attention；避免全量物化
数值优化Scale 粒度、BF16/FP32 累积、校准和饱和统计

如果问题指Activation Tensor 占用很大，优化思路是不要先为整个 Chunk 构造 [T, heads, head_dim] 完整 K/V；而是沿序列和 Head 维 Tiling，把 KV load → up projection → attention 尽可能在一个流水中分块处理，减少临时 HBM 峰值；吸收式与非吸收式路径要根据 Prefill 的 GEMM shape 选择。

如果问题指Activation 数值范围很大，则应检查低精度 E4M3 量化是否饱和、投影后的 Outlier、Scale 粒度、Reduction/Accumulation 精度和 RoPE 位置分量，不能只用 Chunk Size 解决数值问题。

追问：Chunk Size 一味减小为什么也不好？
虽然临时 activation 和 TTFT tail interference 可能下降，但 GEMM Tile 变小、launch/scheduler overhead 增大、算术强度下降；必须考虑 Prefill 的 GPU 利用率与 Decode SLO。

S8. LLM Serving 基础#

长上下文分布式推理：TP / PCP / DCP / MLA / Flux（新增 S 级）

这一章承接 MLA/KV Cache，专门回答多卡长上下文推理的核心问题：每个 rank 保存什么、通信什么、如何降低峰值显存、为何真实 Serving 负载与单轮 benchmark 不同。以下容量和通信例子是教学假设，不是任何特定模型的实测。

1. TP、PCP、DCP：先看 8 卡怎么分

TP（Tensor Parallel，张量并行）把矩阵权重及对应计算分配给不同 rank；PCP（Prefill Context Parallel，预填充上下文并行）分割 Prefill 的序列维；DCP（Decode Context Parallel，解码上下文并行）使 Decode 的历史 KV 分布到多个 rank。不同引擎中 CP 的通信组和 KV owner 规则可能不同，不能只根据 TP×CP 乘积猜每卡数据量。

追问：TP=8 的每卡 KV 一定是 1/8 吗？不一定。GQA 的 KV head 数、是否复制 KV head、MLA latent 是否共享、DCP 的 ownership 都会改变结论。PCP/DCP 的名称和实现尤其要按具体 vLLM/SGLang 版本核实。

2. KV 显存：从公式推到真实峰值

普通 MHA/GQA 的理想 KV payload：

KV_bytes = 2 × layers × seq_len × kv_heads × head_dim × bytes_per_elem

例：32 层、8 个 KV heads、head_dim=128、128K token、BF16，则总 KV payload = 16 GiB。如果 KV heads 真正均匀分到 8 个 rank，每 rank 约 2 GiB；若存在复制，不能这样除。实际 HBM 还要计入 page/block 内碎片、权重、workspace、CUDA Graph、并发请求与临时通信 buffer。

MLA 要改用实际缓存的 c_kv latent 和 k_rope 维度计算，不能套用普通 GQA 的 KV-head 公式。Absorbed（吸收式）通常避免在 Decode 显式展开完整 content K/V，但是否保留逻辑 head 维、如何切 TP，需要区分数学结构和实际物理布局。

3. MLA：吸收、非吸收与 TP 如何关联

TP 切分要从矩阵维度出发：Q/O 投影通常分别对应 column/row parallel；GQA 的 K/V head 可按 head 分片或复制；MLA 的低秩 latent 与 up/down projection 切分更依赖具体实现。面试回答时必须先给张量 shape、分片轴，再谈通信，不能说“一个 KV head 就无法 TP”。

4. Ring Attention：长序列为什么要搬 K/V

对长 Q 的 Prefill，局部 QK 计算足够大，通信有机会被覆盖；对 Decode 或短 Q，矩阵计算很小，传输和同步可能占主导。替代/补充方向包括针对短 Q 的 KV owner-local 计算与局部归约、减少参与 rank、分层 CP、专门的 Decode CP 策略。不能笼统声称某一种方案永远优于 Ring。

CP：AG KV、AG Q / Pass-KV、Pass-Q 怎么选择？

S 级 · 画图 / 公式 / 追问

AG KV / Pass-KV 与 AG Q / Pass-Q 的核心区别
Query owner自己算本地 Q Chunk
Pass-KV把各 rank 的 KV 送到 Query owner，计算全部上下文
Pass-Q把 Q 送给 KV owner，在 KV 所在 rank 局部计算
归并Pass-Q 还要合并 partial Softmax 的 max/sum/output

AG：AllGather（全收集）；Pass-KV/Pass-Q 是更一般的交换策略，不能简单认为每种实现都会全量 AllGather。

最基础的通信量比较取决于 Query 长度 Tq、历史 KV 长度 Tk、实际缓存布局和并行组 P。以 MHA/GQA 为例，完整 Q 字节数约 B × Tq × Hq × Dq × b；完整 KV 字节数约 B × Tk × Hkv × Dkv × 2b。AllGather 的粗略总接收量为本地之外的 (P−1)/P 份完整张量；如果采用 Ring streaming，每步峰值缓存可更小。

Comm_AG-Q ∝ B · Tq · Hq · Dq · b × (P−1)/P + partial-output 归并
Comm_AG-KV ∝ B · Tk · Hkv · Dkv · 2b × (P−1)/P

长会话 Decode：Tq≈1、Tk 非常长，Pass-Q/AG-Q 往往更符合“Q 小、KV 大”的通信特征，KV 留在 owner 上计算后用稳定的 softmax statistics 聚合。长 Prefill：Tq≈Tk 且计算强，Pass-KV 的流水可能更容易让计算覆盖通信；但如果 KV 太大，必须考虑 Ring 分块与显存峰值。

MLA 特例：缓存的可能是每 token 512 维 latent + 64 维 RoPE 部分，而不是展开后的所有 heads K/V；“KV 比 Q 大多少”要以实际发送的物理张量算。随着 CP 的缓存命中与 Agent 多轮复用提高，反复搬动长历史 KV 通常更不划算。

参考：Context Parallelism for Scalable Million-Token Inference（Pass-Q 与 Pass-KV）、vLLM CP Deployment。

追问：为什么 AG Q 后不能把各 rank 的 output 简单求平均？
各 KV shard 的 attention logits 最大值和归一化分母不同。必须合并局部 max、exp-sum 和加权输出，使用 log-sum-exp 的正确归并公式；直接平均会改变注意力概率分布。

5. AllGather：通信量和峰值显存怎么手算

若每个 rank 原有 S bytes 的 shard，P 个 rank 做 AllGather，最终每 rank 得到 P×S bytes。In-place 且能复用输入时，相对原本 S bytes，额外空间约 (P−1)S；另开完整输出缓冲区时，输入和输出可同时占用 (P+1)S（忽略 Workspace），额外分配则是 P×S。Ring AllGather 的每 rank 发送量和接收量各为 (P−1)S 的量级，不能把发送单方向、双向总量与整个集群网络流量混为一谈。

例：P=8，单 rank shard=256 MiB
Gather 后每 rank 完整结果=2 GiB
in-place 复用输入的新增空间≈1.75 GiB
另开输出 buffer：输入 0.25 GiB + 输出 2 GiB ≈2.25 GiB
Ring 每 rank 发送≈1.75 GiB，接收≈1.75 GiB（不计协议额外开销）

6. Python 双流、NCCL overlap、Flux：区别在哪里

Flux 的关键不是“把两个函数写在一起”，而是使数据 tile 的可用性成为 GEMM tile 的执行依赖，减少等待完整 collective 结束的时间。需要讨论 GPU 内同步、SM 资源争用、通信拓扑、tile 粒度以及何时 overlap 反而更慢。

7. 工业场景：多轮、Prefix 命中、SLO、P/D

必须区分 Prefix hit rate（按请求、token 还是可复用计算量统计）、TTFT SLO（P50/P95/P99 与具体负载）、Prefill batch size、chunk size、会话长度分布、KV 保留策略。TTFT 可拆成排队、prefix lookup/restore、剩余 prefill、调度与首个 decode；单轮全量 Prefill benchmark 无法代表高复用的多轮 Agent 服务。

8. DeepSeek 稀疏注意力版本与硬件适配

版本警戒：NSA（Native Sparse Attention）与 DeepSeek V3.2-Exp 中的 DSA（DeepSeek Sparse Attention）不是同一个名称；不要把 V3.1 默认描述成“已经采用 NSA”。不同发布版本、论文和具体 checkpoint 应分别核实。

Ascend 910C 的具体 SKU、单卡/双 die 形态、HBM 容量与 vLLM Ascend 支持情况属于版本和硬件型号敏感信息。面试时应以实际机器 npu-smi info、驱动和部署配置为准，不要背一个无条件适用的显存数字。

8.1 Prefill vs Decode#

  • Prefill：一次处理 prompt，多 token 并行，通常大 GEMM，compute-intensive；
  • Decode：每轮生成少量 token，读取历史 KV，常更 memory/latency-sensitive。

8.2 指标#

  • TTFT（Time To First Token，首 Token 延迟）；
  • TPOT（Time Per Output Token，每输出 Token 时间）；
  • ITL（Inter-Token Latency，Token 间延迟）；
  • Throughput（吞吐）；
  • Goodput（满足 SLO 的有效吞吐）。

不要只说“延迟”。不同优化可能 TTFT 与 TPOT 一升一降。

8.2.1 Prefix Cache 与 KV Cache：区别、索引和多轮复用

S 级 · 画图 / 公式 / 追问

KV Cache 与 Prefix Cache 是“物理状态”和“可复用索引”的关系
KV Cache保存已经计算的 Key/Value 或 MLA latent
Prefix Cache为历史 token blocks 建索引、标记可复用
请求进入Prefix Hash + 模型/模板/租户元数据校验
命中Reuse blocks，只计算新增后缀

KV Cache 是 Attention 需要的历史中间状态；Prefix Cache（前缀缓存） 是“如何在不同请求/轮次查找和复用这些状态”的管理机制。vLLM 使用 block hash、parent hash、block tokens 和额外元数据组织命中；缓存需要 ref_count、Free Block List、Eviction、租户隔离与不同 KV 格式/模型版本兼容性校验。

追问：Prefix 命中 90% 为什么 TTFT 可能没降低 90%？
命中口径可能是请求而非 token；还有 lookup、排队、KV install、剩余 Prefill、Decode First Token、流式输出等成本。高并发还可能把瓶颈转移到 KV 读与调度。

8.3 Paged KV Cache#

将 KV 逻辑序列映射到固定大小 page/block，避免为最大长度连续预留大块显存，降低 fragmentation，并支持动态 batch/sequence 生命周期管理。

8.4 Continuous Batching（连续批处理）#

请求不必等待整个 batch 全部结束；每个 decoding iteration 可加入新请求、移除完成请求，提高 GPU 利用率。但 batch shape 持续变化，scheduler、KV allocation、CUDA Graph 捕获都会更复杂。

8.5 Chunked Prefill（分块 Prefill）#

长 Prefill 切成 chunk，与 Decode 更灵活地调度，避免一个超长 prompt 长时间阻塞 decode；代价是调度/中间状态管理复杂度上升。

8.6 CUDA Graph#

将稳定的 CUDA launch sequence 捕获并重放，降低 CPU launch overhead。挑战是动态 shape、动态 batch、KV address 等会破坏 graph 稳定性，因此 serving engine 常设计固定 batch/token bucket 或 padding 策略。

8.7 P/D Disaggregation（Prefill/Decode 分离）#

Prefill 与 Decode 的资源特征不同：前者偏 compute，后者偏 memory/latency。分离后可独立扩缩容和调度，但引入 KV transfer、路由、跨实例恢复、故障语义等新问题。

8.9 Agent 长 Prefix 下的 P/D 边界与容量配比

S 级 · 画图 / 公式 / 追问

P/D 分离不是免费午餐
同实例复用Prefix 本就在 Decode HBM；只需追加少量 Token
分离实例P 计算/恢复后要把 KV 送到 D
Transfer + Install额外网络、Host（主机端）/H2D、跨 rank 同步和排队
决策与 D 本地追加 Prefill + SLO 进行成本比较

Agent 多轮请求经常是“巨大共享前缀 + 少量新工具返回”。如果后续轮次长期留在 D 实例且 KV 仍驻留，P/D 分离会引入额外 KV 传输成本；如果 P/D 的隔离能够显著降低首轮 TTFT 或长 Prefill 对 Decode 的 P99 干扰，也可能值得支付这些成本。

T_same = Queue_D + Lookup_D + Prefill_miss_D + Decode_first
T_PD = Queue_P + Prefill_miss_P + KV_transfer + KV_install + Queue_D + Decode_first

N_P ≳ λ E[prompt_miss_tokens] / (u_P · P_effective_tokens/s)
N_D ≳ λ E[output_tokens] / (u_D · D_effective_tokens/s)

Decode Batch Size（批次大小，一次处理的样本或 Token 数） 如何选？在每卡可用 HBM 下先给出上限：B_max ≈ Free_KV_Bytes / E[KV_Bytes_Per_Active_Request]（实际按会话分布和最大风险长度留余量）。再扫描 B 对应的 Tokens/s、ITL/P99、NVLink/网络利用率，取满足 SLO 且 Goodput 最高的区间；不应直接套固定的 B=16/32。

这是平均负载的必要容量估算，不是充分的 SLO 保障：D 的有效 Tokens/s 随 Batch 与输出长度分布变化，KV HBM 可用量及 Agent 长尾请求会限制并发，P99 必须通过负载回放验证。Little 定律 Active ≈ λ × average residence time 能进一步估算 Decode 在途会话数。

示例（假设数据）：λ=5 req/s、平均剩余 Prefill=800 tokens、P 每实例持续 10k token/s、目标利用率 70%，NP 至少 1；每请求 Decode 平均 400 tokens、D 每实例 SLO-safe 500 token/s、目标利用率 70%，ND 至少 6。实际还要算 KV 驻留、TTFT 排队和请求长尾。

追问：Decode 输出很长，为什么单纯按轮询分流不够？
长输出请求在 Decode 实例占据 KV 与时隙更久，轮询容易出现一台多长会话、另一台轻载。应看预计剩余 Tokens、KV bytes、队列、SLO slack，考虑 token-budget 公平调度、准入、迁移成本门槛和实例亲和性。

8.10 Agent KV Cache 不够：分四层做成本约束

Agent 的典型负载是：长历史、多轮工具调用、等待时间长、再次访问概率不均。这类问题不要直接回答“把 KV 全部放 CPU/NVMe”，应该先画容量账本和每轮复用概率。

容量治理决策树
① 减少每 Token 字节GQA/MLA、KV FP8、精度/Scale 校准
② 提高可复用率Prefix Cache、Session Affinity、Radix/Hash 共享
③ 优化保留/淘汰HBM Cache Admission、LRU/价值预测、Tool-Gap Signals
④ 分层与迁移Host/NVMe/Remote KV、Prefetch、Restore-vs-Recompute、故障 Safe Miss

并发和生成 Token 增长时，保存所有 KV 通常不可持续；能否删除/降精度需满足正确性或质量边界。

保留 KV 的粗略收益 ≈ P(未来复用) × 重算节省时延 − 持有/迁移/预热成本

实际要增加 HBM byte-seconds（驻留容量积分）、TTFT/TPOT/P99、同实例命中、跨实例 Restore 成功率、失败率与后端流量。对于长等待 Tool Gap，是否 Prefetch 应由实际等待分布和恢复耗时决定；提前搬入 HBM 但随后请求未发生，会白占宝贵缓存。

项目关联：跨实例 KV Restore 的重点是 rank ownership、ABI、manifest/generation 一致性、部分 Restore 失败时 Safe Miss，以及能否在高 Prefix 命中负载下真正获得端到端收益。之前单轮全量 Prefill 测试不能替代真实 Agent Trace 回放；生命周期整体收益尚未证明时，不应在简历中宣称已优化成功。

8.11 Decode 长输出：如何处理 Straggler 和 KV 不均衡？

请求 Output 长度具有明显长尾；如果只按 Request 数轮询，同一实例可能碰巧同时持有几个几千 Token 的长会话。更合理的做法是综合 running decode tokens、KV pages、SLO slack、预计剩余长度 与 GPU Batch Efficiency 建立调度评分。

  • 准入与路由：按在途 KV / Token Budget / 实例负载做 Request Admission，同时对高 Prefix 命中会话维持亲和性。
  • Continuous Batching（连续批处理）：按每轮 Token Budget 调度，防止超长请求长期排挤小请求；维护公平性与尾延迟。
  • 迁移与弹性：如果要跨实例迁移，需比较 KV Transfer + Sync 成本与继续本地排队成本；低收益时宁可维持本地亲和。
  • 容量与失败：KV Page 用尽时可以暂停/抢占、卸载、重算或限流，但要保证状态一致性和恢复可用。
追问：每次新请求优先路由到最空闲 GPU，是否最优？
不一定。KV / Prefix 已驻留的实例可免除 Prefill/Transfer，最空闲可能导致大量恢复成本；更适合做 KV-aware routing：负载、cache locality、长输出尾延迟一起权衡。

8.12 TikTok 高频：RSI、Skill、Agentic RL 的关系与 Infra 成本 S

RSI（Recursive Self-Improvement，递归自我改进）是更宏观的改进循环：Agent 通过实验、评估和修改自身策略、代码、技能或工作流，形成下一轮更强的 Agent。Skill（可复用技能）是可加载的过程性知识，常由说明、脚本、参考资料组成；它降低重复探索和上下文成本。Agentic RL（智能体强化学习）则通过与工具/环境的交互轨迹和奖励优化 Policy。三者可以关联，但并非互为同义词，也不是每个 RSI 系统都一定通过 RL 实现。

A9. Speculative Decoding（推测解码）#

9.1 基本原理#

Target Model 很贵，但一次 forward 可以并行验证多个位置。用便宜 Draft（候选生成） Model 先提出多个候选 token，再由 Target 一次验证，若平均每次 target forward 接受多个 token，就减少串行 decode step 数。

收益取决于： 有效加速 ≈ accepted tokens / (draft cost + verify cost + scheduling/KV overhead)。

所以 acceptance rate 高不等于线上一定快。

9.2 Rejection Sampling（拒绝采样）#

Draft 分布 q，Target 分布 p。候选 x 的经典接受概率： min(1, p(x)/q(x))。

拒绝后不能简单重新从 p 采样，否则最终分布可能改变；需从校正后的 residual distribution 采样。核心性质：在正确算法下，加速后保持 Target 原始 sampling distribution。

Greedy decoding 下验证规则更简单；sampling 场景必须理解概率校正。

9.3 为什么 Hidden State 有用#

只给 Draft token embedding，相当于让小模型重新理解整个上下文。Target hidden state 已包含 Target 对上下文的高层表示；把它作为 Draft feature，可以降低 Draft 学习难度，提高候选与 Target 的一致性。

但不是 hidden state 越多越好：

  • 取更深/更多层可能信息更强；
  • feature 搬运、融合和 Draft 结构成本也上升；
  • 不同层包含局部/语义/预测信息不同；
  • 最终应以 acceptance length 与 end-to-end latency 的消融决定。

9.5 为什么 Spec Decode 还要关注 TTFT#

它主要减少 Decode 的串行步数，但线上链路还有 scheduler、Prefill、KV allocation、Continuous Batching、Draft Model 初始化/权重、CUDA Graph bucket 等。若为 speculative path 增加排队、资源竞争或改变 batching，TTFT 可能变差。

同时 Spec Decode 会改变每轮“逻辑 token 数”和物理 KV 写入/回滚方式，可能影响：

  • KV page allocation；
  • batch composition；
  • memory footprint；
  • verify kernel shape；
  • continuous batching fairness。

9.6 动态 Draft Length 的本质#

Draft 太短：Target forward 减少不够；Draft 太长：后半段容易被拒绝，浪费 Draft/Verify（候选验证） 计算。因此 scheduler 可根据历史 acceptance、request 状态、batch pressure 等动态决定 draft token 数。面试时先讲这个 cost model，再讲具体 vLLM 版本实现。

9.7 MTP 在高并发下要不要默认开？ S

MTP（Multi-Token Prediction，多 Token 预测）通常指 Target 模型附带原生多 Token 预测能力，并通过 Draft + Target Verify 实现推测解码。它与单独加载一个大 Draft Model 不完全相同；具体 Draft 结构取决于模型。不能简单把“接受率高”等同于“整体吞吐提升”。

图｜低并发与高并发时，MTP 解决的问题可能不同
较低并发：Decode latency 敏感Target 每轮有效 Token 太少，MTP 提高一次 Target 验证的产出；Draft 较便宜时容易降低 TPOT。
高并发：Batch 已较饱满Continuous Batching 已让 Target 的 GEMM 更高效；Draft+Verify 扩大 Token Budget，可能挤占 KV / HBM / 计算资源，吞吐不一定提升。
Speedup_spec ≈ (E[accepted_tokens_per_cycle] × T_base_per_token) / (T_draft + T_verify + T_accept + T_scheduler) 约束：上述时间必须在相同并发、相同延迟分位与请求分布下测。

需要同时看 acceptance length、proposed/accepted/verified tokens、Draft Time、Verify Time、Token Budget、Batch Size、KV 峰值、TPOT、TTFT、P99、Goodput。答案通常是按 QPS（每秒请求量，用于衡量服务流量）/上下文/输出长度分桶、动态选择 Spec Depth，不能宣布一条固定全局开关。

追问：接受率越高就一定越快吗？
否。假如多生成一个 Draft Token 要花 0.6ms，但它给 Target 平均只带来 0.4ms 的有效计算节省，那么接受长度增加也可能变慢。若需要为它增加验证 Batch、Graph Bucket 或显存保留，负收益会更明显。必须使用实际接受长度除以整轮 Draft + Verify + Scheduling 总耗时的口径。

vLLM 官方 Speculative Decoding 文档明确要求按 QPS 与负载验证，支持 MTP、EAGLE、Dynamic Speculation 等多种路线。

9.8 六组优化组合：为什么 1+1 有时大于 2，有时互相抵消？ S

先确定每项优化究竟改变的是哪一个成本项：CPU Launch、GPU Compute、HBM Bytes、KV Capacity、Prefill/Decode 隔离、请求排队。两个优化如果消除了不同的关键路径成本，容易互补；如果都消除了同一段成本，会出现收益重叠；如果共同增加了新的资源竞争，就可能回退。

④ Quantization + MTP

可能协同：较低精度让 Target Verify 更便宜、KV 占用下降。可能抵消：Target/Draft 分布发生变化使 Acceptance Length 下降，或量化反量化 Kernel 吃掉收益；应以量化后的 Target 为正确性基准。

⑤ P/D 分离 + CUDA Graph

可能协同：Decode Shape 较稳，更容易捕获并重放 Graph；减少 CPU 提交开销。可能抵消：高并发动态 shape、KV 地址管理、Graph pool 占 HBM，影响 Decode 可承载请求量。

⑥ P/D 分离 + Chunked Prefill

可能协同：P 阶段按内存预算切块/流式搬 KV；同时 D 与 P 隔离。可能重叠：若 Chunking 的唯一目的就是防 Prefill 阻塞 Decode，P/D 已隔离后此收益减弱。

五项全部开启，为什么可能更慢？

优化组合改变的不只是算子耗时，还会改变 排队模型、Batch Shape 分布、KV 分配、Graph Capture 命中、H2D/RDMA 带宽、SM 争用。单个功能可能都在原基线上有效，但组合后系统的主瓶颈已经迁移到别处，因此必须重新 Profile。不要把各功能的单测 Speedup 直接相乘作为线上性能预测。

S10. Quantization（量化）#

10.1 先区分量化对象#

图 17｜量化：同样叫“低 bit”，收益来源可能完全不同

  • Weight Quantization：省模型权重容量/带宽；
  • Activation Quantization：让 W×A 进入低精度 Tensor Core fast path，但动态范围更难；
  • KV Cache Quantization：省 HBM capacity / bandwidth / 跨节点传输，但误差会贯穿后续所有 decode step。

10.2 FP8 E4M3 / E5M2#

E4M3：更多 mantissa、较高精度、较小动态范围；E5M2：更大 exponent range、精度更低。具体选择取决于数据分布和训练/推理路径。

10.3 Scale Granularity#

从粗到细：per-tensor → per-channel/per-head → group/block。粒度越细通常越能隔离 outlier、降低误差，但 scale metadata、量化/反量化和 kernel/layout 复杂度上升。

10.4 AWQ#

AWQ（Activation-aware Weight Quantization，激活感知权重量化）不是“W4A16”的同义词；核心是利用 activation 统计识别/保护重要 weight channel，并通过 scaling 等降低低比特 weight quantization error。经典部署常见 W4A16。

10.5 为什么 W4A16 不一定比 FP8 W8A8 更快#

W4A16 更省 weight bandwidth，但可能需要 dequant 后做 FP16/BF16 compute；FP8 W8A8 虽位宽更高，却可直接使用高吞吐 native FP8 Tensor Core。最终取决于 batch shape、memory-bound/compute-bound、dequant overhead、kernel 支持。

10.6 MXFP8 / MXFP4 / NVFP4#

Microscaling（微缩放）的思想：小 block 共享一个 scale，兼顾低位宽和局部动态范围。理解重点：

  • block 越小，outlier 隔离通常越好；
  • 但 scale metadata / layout / kernel 复杂度更高；
  • Blackwell 对 block-scaled low precision 提供更直接的硬件支持。

不要把 MXFP4 与 NVFP4 当同一个格式；它们的 block size、scale 表达和数值设计不同。

10.7 Attention 哪些地方更敏感#

线性 projection 常较适合量化；Softmax、Norm、reduction 等数值敏感部分通常保留较高精度。KV 量化需要特别关注长上下文误差累积、K/V 分布差异、scale granularity 和 cache/transfer 收益。

10.8 MoE：为什么 Expert 可量化而 Router/Gate 更敏感#

Expert GEMM 的小量化误差通常表现为连续数值扰动；Router/Gate 的微小 logit 误差可能让 Top-K 排序翻转，直接把 token 发给不同 expert，是离散决策改变。因此 Router 常保留 BF16/FP32，而大规模 Expert GEMM 是 FP8/FP4 的高收益区域。

MoE 继续追问：Grouped GEMM、variable M、token permutation、load imbalance、Expert Parallelism、All-to-All。

10.9 量化 + MTP：为什么计算更便宜，接受率反而可能变差？

量化可以减少 Target Verify 和 Draft 的模型权重流量，也可能改变两者的 Logits、Hidden State 与 Token 排名，从而改变 Acceptance Length。对于 Greedy 验证，某个位置的 Top-1 发生翻转会让后续 Draft 全部作废；对于正确的采样验证，结果应与量化后的 Target 分布一致，但不保证它与原 BF16 模型的输出质量一致。

混元深挖专题：MLA、Speculative Decoding 与量化

按“为什么出现 → 算法怎么做 → 系统为什么可能不快 → 面试怎么追”补齐。重点不是背论文名，而是建立性能推理链。

MLA 手撕：从 MHA 的 KV Cache 问题推出来

MHA（Multi-Head Attention，多头注意力）在 Decode 时需要保存历史 token 的 K/V。序列越长，KV Cache 容量和读取流量线性增长；Decode 又常常是 memory-bound，因此减少历史状态本身就有直接系统价值。

c_kv = X @ W_DKV          # down projection：压缩
K_c  = c_kv @ W_UK        # content K
V    = c_kv @ W_UV
q_c  = X @ W_QC
q_r  = RoPE(X @ W_QR)     # positional part
k_r  = RoPE(X @ W_KR)
score = q_c @ K_c.T + q_r @ k_r.T
P = softmax(score)
O = P @ V

为什么拆 RoPE？ RoPE 会引入位置相关旋转，不能像普通固定线性映射一样简单吸收到权重里。因此 MLA 将 content part（内容部分）与 RoPE part（位置部分）解耦：大块内容状态可以压缩/吸收，较小的位置状态单独处理。

30 秒：MLA 的系统价值是把 Decode 需要读取的历史 KV 状态从完整多头 K/V 压缩成 latent KV，再把 RoPE 相关的位置分量单独处理，从而减少 KV Cache 容量和 HBM 读取。手撕重点是 down projection、RoPE 解耦、score 和 value 路径。

Weight Absorption（权重吸收）

如果 Decode 每步先把 latent 显式展开成完整 K/V，会重新引入计算和中间数据。利用矩阵乘法结合律，可把部分 up-projection 与 Q/O projection 预先组合，让计算尽量直接围绕 latent 进行。直觉：固定线性变换能提前合并，就不要每个 token 重建完整 K/V。 Prefill 和 Decode 的最佳实现可能不同：前者偏大 GEMM，后者更看 KV bytes 和小 batch 效率。

Speculative Decoding：EAGLE-3 → DFlash → DSpark

Speculative Decoding（推测解码）先让便宜的 drafter 提议多个 token，再由 Target 一次并行验证。收益不能只看接受长度：

有效收益 ≈ 一次 Target verification 接受的 token 数
           -------------------------------------
           draft + verify + scheduler/KV 额外成本

真正的矛盾是 Draft latency × Draft quality × Verification waste。

为什么使用 Target Hidden State？

只给 drafter token id，相当于让小模型重新理解上下文；Target hidden state 已包含大模型形成的语义表征。把这些 feature（特征）给 drafter，相当于让小模型站在 Target 已完成的表征上预测未来。但层越多、feature 越宽，融合与训练成本也越高。“取哪几层”应区分论文、开源 checkpoint 与线上版本，并通过 acceptance、draft latency、feature overhead 做消融，而不是背一个永恒的层号。

DSpark 为什么做 Confidence Scheduling？

这解释了为什么线上不能只看单请求 acceptance：高并发时，低成功率 speculative tokens 会占 verification batch capacity。

Rejection Sampling（拒绝采样）

设 draft 分布 q(x)，Target 分布 p(x)，候选 token 接受概率为 min(1, p(x)/q(x))；拒绝后从与 max(0,p-q) 成比例的修正分布采样。目的不是提高接受率，而是保证最终 sampling distribution 与直接使用 Target 一致，即 lossless speculation（无损推测）。

系统视角：Spec Decode 把“多次低算术强度的小 Decode”换成“Draft + 更大的并行 Verify”，提高 Target Decode 的有效 arithmetic intensity；但 Draft、被拒 Verify、额外 KV slots、调度和 batch-shape 成本都可能吃掉收益。因此 TPOT 下降不代表 TTFT、P99 和吞吐都会改善。

Quantization：从瓶颈而不是 bit 数开始

量化有三个不同目标：省容量、降带宽、提高低精度 Tensor Core 吞吐。

为什么 W4A16 不一定比 W8A8 FP8 快？

bit 更少只意味着 payload 更小。速度还取决于硬件原生 fast path、dequant 是否融合、shape/batch 和 Tensor Core 利用率。若 W8A8 可直接走原生 FP8 Tensor Core，而 W4A16 需要复杂 unpack/dequant，compute-heavy 场景下 FP8 完全可能更快。

Attention / MoE 哪些地方更敏感？

Expert 量化通常产生连续数值扰动；Router 的微小误差却可能让 Expert 排名翻转，直接改变后续计算路径，因此 Router/Gate 往往更保守。

Scale Granularity（缩放粒度）

粒度越细，局部 outlier 越不容易拖累整组 scale，但要支付更多 metadata 与 kernel 成本。MXFP8/MXFP4 的 microscaling（微缩放）就是硬件友好的 block scaling。

与你的 FP8 KV 项目：K-head/V-layer 本质上是在问“K 的不同 head 动态范围差异，是否值得支付更细 scale 的 metadata/kernel 成本”。质量、payload、可缓存 token、跨节点传输和端到端延迟必须分开报告。

把三块串成一道系统题

AI Infra 面试里不要把 MLA、Spec Decode、Quantization 当三个孤立算法：它们都在重新分配 Decode 阶段的计算、访存与调度成本。

11.1 四种并行先会说代价#

  • TP（Tensor Parallelism，张量并行）：层内矩阵切分；频繁 collective，低延迟互联重要。

  • EP（Expert Parallelism，专家并行）：MoE experts 分布到设备；核心代价常是 token dispatch 的 All-to-All 和负载不均。

专家为什么负载不均？

Router 决定哪些 Expert 接收 Token，分布通常不均匀，并且随请求领域、Token 位置和 batch 变化。即使 Top-K 固定，每个 Expert 收到的 Token 数也不相同；一轮 MoE 的等待时间接近最慢 Rank 的完成时间。

mean_tokens_per_expert = B_global × top_k / E_total T_MoE ≈ T_router + T_dispatch + max_rank(T_expert_compute) + T_combine

优化从低到高可以分成：监控每 Expert Token 分布 → 重新放置 Expert → 热门 Expert 复制 → 针对动态负载做路由/副本调整 → 通算 overlap。复制热门 Expert 需要额外权重显存，不能把复制视为免费的计算扩容；优化后还要看跨节点 A2A 与搬迁成本。

30 秒答案： MoE 选并行策略先看模型权重是否容得下。可复制时 DP 通信最少；Expert 太大可以考虑 TP；专家数量多时 EP 分散权重，但引入 Dispatch/Combine A2A。EP 的收益取决于每 Expert 是否有足够 Token 填满 Grouped GEMM，以及 Router 热点会不会造成 Straggler。线上主要结合 Expert 复制与拓扑感知放置做均衡，不能无限增加 EP。
追问：为什么大 EP 不一定快？
EP 增大后每张卡保存的 Expert 减少，但相同全局 Batch 下每 Expert 接收的 Token 总量不一定增加；本地 GEMM 可能仍然很小，A2A 参与节点和跨机网络开销却增加。负载不均时，最慢 Rank 还会让其他 GPU 等待。应扫 EP×DP×并发的二维矩阵，以 Goodput 和 P99 为准。

11A.2 DDP：梯度同步与模型更新是两回事

DDP（Distributed Data Parallel，分布式数据并行）最容易产生的误解是“每轮训练只在 Rank 0 更新参数”。典型 PyTorch DDP 会在各 Rank 反向传播时协调梯度归约，然后每个 Rank 在本地执行相同的 Optimizer Step。它不自动保证不同 Rank 的 Optimizer 状态、数据、代码路径永远一致。

为什么仍会出现 Replica Divergence（副本发散）？只要模型初始化、Optimizer State（优化器状态）、AMP Skip Step、学习率或自定义更新逻辑在 Rank 间不同，即便 AllReduce 返回一致的梯度，不同副本仍可能更新出不同的参数。

现实还有一个细节：DDP 通常按 Rank 归约梯度；如果不同 Rank 的样本数不同，且每 Rank 用 Mean Loss，则“等权平均各 Rank 梯度”未必等于“按所有样本全局求平均”。需要明确 Loss Reduction、样本权重、Gradient Accumulation（梯度累积） 的口径。

# 核心训练步骤（完整运行示例见章末双进程实验）
optimizer.zero_grad(set_to_none=True)
loss = criterion(ddp_model(x), target)
loss.backward()       # DDP reducer 协调梯度同步
optimizer.step()      # 每个 Rank 本地更新
面试追问：既然梯度同步了，为什么还要验证参数一致性？
梯度同步只是必要条件之一。优化器动量、Adam 二阶矩、初始参数、混合精度 overflow/skip、随机状态、某些模型 Buffer（缓冲区，用于暂存传输或计算中间结果） 以及实际参与更新的参数集合，也必须符合约定。验证时只比较同一个逻辑副本的相同分片，而不是拿 TP/FSDP 不同分片做逐字节比较。

面试追问：两个 Rank 的 Loss 不同，说明训练错误吗？
不说明。不同 Rank 处理不同 Batch，局部 Loss 本来可能不同。应在固定输入、对应权重和相同精度设置下比较输出或梯度；如果要记录全局 Loss，需要正确按样本数做权重归约，而不能简单对不等 Batch 的本地均值取平均。

11A.4 大模型放不下：TP / PP / DP / CP / EP / FSDP

假设训练一个 70B 参数模型，仅 BF16 权重约 70e9×2 = 140 GB（十进制），尚不包括训练时的梯度、优化器动量、Master Weights（主权重）、激活值与通信 Buffer。如果使用一个示意的混合精度 Adam 配置：2B 权重 + 2B 梯度 + 4B 主权重 + 8B 一、二阶矩 = 每参数 16B，总计约 1.12 TB，具体配置还可能是 18B、20B 或其他口径。

所以必须同时解决两类问题：模型状态如何放得下，以及 计算任务如何切分得足够快。

11A.6 数值正确性：AMP、Grad Norm、Optimizer 一致性

训练的 Loss Spike 可能来自坏数据、Grad Overflow、Optimizer 更新、参数污染或者正常数值不稳定。必须区分损失统计、梯度统计与参数状态，不能只看一个 loss.isfinite()。

Gradient Clipping（梯度裁剪）：对于梯度 g=(3,4)，L2 Norm=5。最大 Norm 为 1 时，乘 1/5 后得到 (0.6,0.8)；大于阈值时只缩小幅度，方向保持不变。

PyTorch DCP（Distributed Checkpoint，分布式快照）支持多 Rank 并行保存/加载分片状态，并可在支持的情形下 Load-time Resharding（加载时重新分片）；但它不会替用户凭空保存所有 DataLoader、环境状态或业务版本。这些必须由训练程序明确定义并纳入快照。

与 KV Restore 的联系：你熟悉的 generation-specific key、Manifest、Fencing、Safe Miss 和跨 Rank 原子恢复，可以直接借鉴其代际隔离与提交协议思想。但训练 Checkpoint 多了 Optimizer、LR、Sampler、RNG，且故障后可以从上一个完整 Step 重算，不是“有个 KV block 就能恢复”。

面试追问：torchrun 重新拉起 Worker，算不算已经实现了训练恢复？
不算。torchrun/Elastic 主要负责 Worker Group 的生命周期；失败时通常重启 Worker。要真正接续训练，应用还必须找到最后完整的 Checkpoint、恢复所有关键状态、重新建立通信组/分片映射，并处理新 Rank 与 World Size。未保存或保存不一致的状态不会因为进程重启而自动恢复。

11A.9 训练环境可信与可复现：别只记录 Git Commit

即便训练代码 Git Commit 一样，实际运行的容器镜像、PyTorch 二进制、CUDA/NCCL、数据文件、模型初始化权重都可能不同。排障和实验复现都应保存：代码 Commit、容器 Digest、依赖 Lockfile、配置/参数 Hash、模型/数据 Artifact Hash、CUDA/NCCL/驱动版本、训练生成 ID、关键权限变更记录。

Checkpoint 属于需要审慎加载的输入：优先使用可信来源、校验元数据与摘要，能用时采取权重安全加载路径；不要把未知来源的通用 Python 对象反序列化当作普通读取权重。

资料报告中的具体责任归属与事实细节存在来源限制；工程知识点来自可独立验证的 PyTorch/NCCL/FSDP/Checkpoint 机制。面试中应围绕可观测性、隔离、恢复，而不是复述未经核实的事件结论。

12. 高频面试题：30 秒答案索引#

S1. MFU 低怎么排查？#

先确认口径；torch profiler/NSYS 看系统 timeline，区分 bubble、CPU、通信、PP、straggler；若 GPU busy，再 NCU 下钻 hot kernel，用 Roofline + memory/compute/warp stall/register/bank conflict 分类；最后端到端回归。

S2. Shared Memory bank conflict 是什么？#

Shared Memory 分 bank 并行服务。一个 warp 同周期访问同 bank 的不同 word 会序列化；Padding 改 stride，Swizzle 改物理 layout。相同 word 的 broadcast 要特判。

S3. Hopper 比 Ampere 核心变化？#

从 cp.async 的 thread/warp 协作搬运进一步走向 TMA 专用 tensor 搬运；WGMMA 提供 warpgroup 异步 MMA；配合 warp specialization 做 producer-consumer pipeline；Cluster/DSMEM/Multicast 扩展 CTA 间数据复用。

S4. Blackwell 比 Hopper 核心变化？#

第五代 Tensor Core 引入 tcgen05 编程模型和 TMEM，减少 accumulator 对普通 register file 的压力，并支持更强的跨 CTA Tensor Core 协作/2-CTA MMA；同时强化 block-scaled 低精度计算。

S5. FA1~4 怎么一句话区分？#

FA1 解决 HBM IO；FA2 改 work partition、提高并行度；FA3 映射到 Hopper TMA/WGMMA/warp specialization；FA4 面对 Blackwell Tensor Core 过快后暴露的 SMEM/Softmax/Exp 等新瓶颈，并利用 TMEM/2-CTA 等能力。

S6. 为什么 MLA 省 KV？#

不是为每个历史 token 保存完整多头 K/V，而保存低维 KV latent + 必要位置表示；配合 decoupled RoPE 和 weight absorption，Decode 可直接围绕 latent 计算，降低 cache capacity 和 memory traffic。

S7. Spec Decode 为什么可能线上不加速？#

Acceptance 只是收益一半；还要付 Draft、Verify、scheduler、KV、batch shape、CUDA Graph 等成本。低 batch/高 acceptance 可能很好，高并发下 Draft 还可能抢 Target 的 GPU 资源，因此必须看 end-to-end TPOT/throughput/goodput。

S8. Router 为什么不轻易量化？#

Expert 的误差多是连续数值扰动；Router 的微小误差可能翻转 Top-K，改变离散 expert 路由，误差后果更剧烈。

手撕 2：稳定 Softmax 与 Online Softmax

def safe_softmax(x, dim=-1):
    m = x.max(dim=dim, keepdim=True).values
    e = torch.exp(x - m)
    return e / e.sum(dim=dim, keepdim=True)

手撕 3：MHA —— 先写数学正确版

def mha(q, k, v, causal=True):
    # [B, H, T, D]
    scale = q.shape[-1] ** -0.5
    score = q @ k.transpose(-1, -2) * scale
    if causal:
        Tq, Tk = score.shape[-2:]
        mask = torch.ones((Tq, Tk), device=q.device, dtype=torch.bool).triu(1)
        score = score.masked_fill(mask, float("-inf"))
    p = torch.softmax(score, dim=-1)
    return p @ v

写完必须主动说：这个版本会显式产生 [B,H,T,T] score/probability，中长上下文 HBM traffic 和显存爆炸；FlashAttention 的目标就是 tile 化 Q/K/V 并结合 online softmax，避免完整 N² 中间矩阵落 HBM。

手撕 4：MLA —— 面试可写的简化版

def mla(x, W_dkv, W_uk, W_uv, W_qc, W_qr, W_kr):
    c_kv = x @ W_dkv               # compressed latent KV
    k_c  = c_kv @ W_uk
    v    = c_kv @ W_uv

    q_c  = x @ W_qc
    q_r  = apply_rope(x @ W_qr)
    k_r  = apply_rope(x @ W_kr)

    score = q_c @ k_c.transpose(-1, -2)
    score += q_r @ k_r.transpose(-1, -2)
    p = torch.softmax(score / math.sqrt(q_c.shape[-1]), dim=-1)
    return p @ v

这不是生产 DeepSeek MLA kernel，而是面试时展示你理解latent compression + decoupled RoPE。接下来主动补：Decode 实现还会做 weight absorption，避免每 token 显式展开完整 K/V；真实 kernel 还涉及 cache layout、GEMM shape 和 fused attention。

int count[32] = {0};
for (int tid = 0; tid < 32; ++tid) {
    int word = addr[tid] / 4;

Profile Case：看到指标怎么推瓶颈

固定顺序：先系统、再 Kernel；先现象、再假设；最后用下一组指标证伪。

Case 1：MFU 低，但 GPU utilization 也低

GPU util: 45%
Tensor Core util: 30%
NSYS: kernel 之间大量空白
CPU thread: frequent cuda synchronize

判断：先不要优化 GEMM。第一嫌疑是 System-bound：CPU launch/sync 导致 GPU starvation。

下一步：在 NSYS 找同步 API、.item()、D2H、Python gap；若大量短 kernel，再考虑 CUDA Graph / fusion。只有 timeline 被填满后才值得下钻 NCU。

Case 2：GPU 一直忙，HBM 接近峰值，Tensor Core 很低

GPU busy: ~100%
HBM throughput: 90% peak
Tensor Core: 25%
Arithmetic intensity: low

判断：典型 Memory-bound。继续提高 Tensor Core 理论峰值没有意义。

优化：减少 bytes：fusion、quantization、提高 reuse、改善 cache/layout；LLM Decode 中尤其考虑 batching、KV bytes、weight bytes。Roofline 上要做的是把点向右移动，而不是只抬屋顶。

Case 3：HBM 50%，Tensor Core 45%，但 Warp Stall 很高

HBM: 50%
Tensor Core: 45%
occupancy: 25%
registers/thread: high
eligible warps/cycle: low
long scoreboard stalls: high

判断：更像 Latency-bound，而不是 bandwidth-bound。Register pressure 导致 resident warps 少，memory/dependency latency 没有足够 warp 隐藏。

优化：检查 tile 是否过大、临时变量生命周期、register spilling；在 reuse 与 occupancy 间重新取舍，并考虑 async pipeline / double buffering。

Case 4：单卡很快，多卡 MFU 暴跌

1 GPU: MFU 55%
8 GPU: MFU 31%
NSYS: GEMM 后存在长 NCCL AllReduce
NCCL 与 compute 几乎不重叠

判断：Distributed/System-bound，不是单卡 kernel 问题。

下一步：确认是 TP/DP 哪类 collective，检查消息粒度、NVLink/NVSwitch/跨节点拓扑；再看 ReduceScatter/AllGather 是否可替代部分 AllReduce、通信是否能提前发起并与后续计算 overlap。

Case 5：Attention 优化后 HBM 降了，但速度没继续涨

Before: HBM 92%, Tensor Core 40%
After : HBM 55%, Tensor Core 75%
        SMEM 90%, MUFU/exp high

判断：这是“瓶颈迁移”的标准案例：最初 HBM-bound；减少 IO 后，SMEM / Softmax exp 成为新瓶颈。FA3→FA4 的演进就应该用这种思维理解。

Case 6：Spec Decode acceptance 很高，但线上吞吐下降

accepted length: ↑
draft GPU time: ↑↑
verification batch tokens: ↑
P99: ↑
throughput: ↓

判断：算法 acceptance 指标不能代表系统收益。Draft/verification 占用 GPU 与 batch capacity，低价值 speculative tokens 还可能挤压正常请求。

17.1 const 指针与指针交换

const int* A;  // A 指向 const int；允许 A 改指向，不允许通过 A 改值
int const* B;  // 完全相同的类型
int* const C = some_ptr; // 指针 C 自身不能重新赋值，所指值可改

17.2 深拷贝 / Rule of Five / RAII

拷贝构造是 T(const T&)；浅拷贝若复制拥有资源的裸指针，会导致 Double Free 或悬空引用；深拷贝分配独立资源。现代工程首选 RAII（资源获取即初始化）、std::vector/std::unique_ptr 和 Rule of Zero，而不是手写裸指针资源管理。

class Buffer {
    std::unique_ptr<int[]> data_;
    size_t n_;
public:
    explicit Buffer(size_t n) : data_(std::make_unique<int[]>(n)), n_(n) {}
    Buffer(const Buffer& rhs) : Buffer(rhs.n_) {
        std::copy(rhs.data_.get(), rhs.data_.get()+n_, data_.get());
    }
    Buffer& operator=(Buffer rhs) noexcept { swap(rhs); return *this; }
    void swap(Buffer& rhs) noexcept {
        data_.swap(rhs.data_);
        std::swap(n_,rhs.n_);
    }
};

还要能说 Rule of Three/Five 与虚析构。如果使用 Base* 删除派生对象，基类通常应有 virtual ~Base()。

虚函数和 sizeof：许多 ABI 使用 vptr/vtable，但 C++ 标准并不规定必须存在 vptr，也不规定其精确布局；多重继承/虚继承可能产生额外指针、偏移与对齐填充。计算对象大小时应明确编译器/ABI/平台指针宽度，不能死背“有虚函数就固定加 8 Byte”。

18. 数学手撕：投影、Sigmoid、Softmax

向量投影：令 d=B−A，C 到直线 AB 的垂足 C′ 为 A+t·d，其中 t=((C−A)·d)/(d·d)。当 A=B 时方向向量为 0，需要单独处理；若求线段 AB 上最近点，则将 t 裁剪到 [0,1]。

C′ = A + [((C−A)·(B−A)) / ||B−A||²] · (B−A)

Sigmoid： σ(x)=1/(1+exp(−x))，导数是 σ(x)[1−σ(x)]，极端大/小时梯度接近 0，容易出现梯度饱和。

σ′(x) = σ(x)(1−σ(x))

Softmax： pᵢ=exp(xᵢ−m)/Σⱼexp(xⱼ−m)，m=maxⱼxⱼ。减最大值不会改变 Softmax 输出，却能防止 exp 上溢。

∂pᵢ/∂xⱼ = pᵢ · (δᵢⱼ − pⱼ)；J = diag(p)−p pᵀ
# Numerical stable softmax in PyTorch
m = x.max(dim=-1,keepdim=True).values
p = (x-m).exp()
p /= p.sum(dim=-1,keepdim=True)
追问：Softmax CrossEntropy 的 logits 梯度为什么是 p−y？
交叉熵 L=−Σ yᵢ log pᵢ，利用 softmax 雅可比展开；当 y 是概率分布且 Σyᵢ=1，∂L/∂xᵢ=pᵢ−yᵢ。

19. 算法手撕：7 道题的解题模型与边界

算法题按“能写出正确解 + 能解释复杂度 + 会处理边界”准备。下面给出问题形式和最短正确思路，详细模板可以作为 LeetCode 练习题使用。

19.1 BST 同分数节点替换

BST 同分数替换：先澄清“分数相同”是替换节点附带的信息，还是要在树中保留多个相同 score。若规定 score 唯一，则查找到同分数节点后只替换 payload，不能直接改树指针破坏 BST；若允许同分数，使用 (score, id) 复合 key，保证全序。查找平均 O(log n)，退化 O(n)。

19.2 copyRandomList

LeetCode 138 copyRandomList：HashMap 原节点→新节点，两遍构建，O(n) 时间/O(n) 空间；或者 interleaving 三遍法（原链表每节点后插复制节点→设置 random→拆链），O(n) 时间/O(1) 辅助空间。

def copyRandomList(head):
    if not head: return None
    p=head
    while p:
        node=Node(p.val,p.next)
        p.next=node
        p=node.next
    p=head
    while p:
        p.next.random = p.random.next if p.random else None
        p=p.next.next
    dummy=Node(0); tail=dummy; p=head
    while p:
        q=p.next
        p.next=q.next
        tail.next=q; tail=q
        p=p.next
    return dummy.next

19.3 汽水瓶兑换

汽水瓶：一元一瓶、两个空瓶换一瓶，N 元可先喝 N 瓶。每次换喝以后空瓶净减少 1，直到只剩 1 个空瓶，若不允许借瓶，N≥1 时总计 2N−1 瓶；若允许借一个空瓶并必须归还，答案可变为 2N。先确认兑换规则与 N=0 的边界。

19.4 任务调度：N 项任务如何分 K 核

任务长度 1..N、K 核并行：若 K 固定且任务不可拆分，目标是最小化 Makespan（最大核负载）。理论下界 max(N, ceil(N(N+1)/(2K)))；常见实践可用 LPT（按任务时长从大到小分配给当前最空闲的核）获得较好近似。若 K 可无限增加且只求时延，则 K=N 达到理论下界 N，题目必须加核成本或空泡约束才有真正优化意义。

# LPT 贪心近似：最小堆维护当前每核负载
import heapq
loads = [(0, i) for i in range(K)]
heapq.heapify(loads)
for duration in range(N,0,-1):
    used, i=heapq.heappop(loads)
    heapq.heappush(loads,(used+duration,i))
answer=max(x for x,i in loads)

19.5 LC 2712

LeetCode 2712 Minimum Cost to Make All Characters Equal：在相邻位发生变化的边界 i（1-based）处，选择翻转左侧前缀或右侧后缀，最小代价为 min(i, n−i)。因此扫描字符串求和即可，O(n)/O(1)；也可以先从前后缀 DP 的最小代价推导，再压缩到这个边界公式。

def minimumCost(s):
    n=len(s)
    return sum(min(i,n-i) for i in range(1,n) if s[i]!=s[i-1])

19.6 LC 1383

LeetCode 1383 Maximum Performance of a Team：按 efficiency 从大到小排序，把当前 efficiency 视为选中集合的最小值，维护最多 k 人的 speed 之和。最小堆保存较大的 k 个 speed，每一步更新乘积，时间 O(n log k)（加排序 O(n log n)）。

import heapq
people=sorted(zip(efficiency,speed),reverse=True)
heap=[]; speed_sum=0; ans=0
for eff, spd in people:
    heapq.heappush(heap,spd); speed_sum+=spd
    if len(heap)>k: speed_sum-=heapq.heappop(heap)
    ans=max(ans,speed_sum*eff)

19.7 数字字符串任意加号求和

数字字符串任意位置插入加号，求所有表达式值之和：遍历时维护三个状态：S=所有表达式总和、L=所有表达式末尾数之和、C=当前表达式数。读入新数字 d 后分“插加号”和“不插加号”两类：

S_new = 2S + 9L + 2C·d；L_new = 10L + 2C·d；C_new=2C

初始第一个数字 d₀ 时 S=L=d₀、C=1。例如 "123" 产生 123, 12+3, 1+23, 1+2+3，总和 168；O(n)/O(1)，注意整数上限/取模问题。
