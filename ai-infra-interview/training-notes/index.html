01 · GPU 执行模型与内存层次

1.1 GPU 到底怎样运行一个 Kernel？

一个 CUDA Kernel 会启动一组线程（Grid，线程网格）。Grid 由多个 Thread Block（线程块）组成，每个 Block 再包含多个 Thread（线程）。在 NVIDIA GPU 上，Warp（线程束）通常是 32 个线程，是执行指令和调度的基本分组。Block 会被调度到某个 SM（Streaming Multiprocessor，流式多处理器）上，SM 内的 Warp Scheduler 选择可执行的 Warp 发射指令。

以向量加法为例，N=1,000,000、blockDim.x=256，需要 ceil(N/256)=3907 个 Block。每个线程处理一个下标：

__global__ void vec_add(const float* a, const float* b, float* c, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) c[i] = a[i] + b[i];
}

int threads = 256;
int blocks = (n + threads - 1) / threads;
vec_add<<<blocks, threads>>>(a, b, c, n);

这里有三层约束：线程够不够多决定并行度，每线程寄存器/每 Block Shared Memory影响 SM 能驻留多少 Warp，访存模式与运算类型决定实际吞吐。

Occupancy（占用率）是驻留的活跃 Warp 相对于架构上限的比例。提高 Occupancy 可以帮助隐藏访存延迟，但寄存器压力、访存事务和 Tensor Core 利用率通常更值得结合 Profile 一起看。Occupancy 高并不自动意味着 Kernel 快。

1.2 GPU 存储层级：谁存什么、谁访问？

存储位置 作用域 / 生命周期 典型用途 需要警惕
Register（寄存器） 每线程私有，SM 内 累加器、地址、临时标量 寄存器溢出后访问 Local Memory，可能落入显存层级
Shared Memory（共享内存） 同一 Block 线程共享，SM 内 Tiling、数据复用、归约 Bank Conflict、容量挤占 Occupancy
L1 Cache 通常为 SM 级缓存 缓存局部数据访问 缓存命中率、访存策略
L2 Cache 全 GPU 共享缓存 跨 SM 数据复用、HBM 缓冲 容量和流量争用
HBM / Global Memory GPU 全局可访问 模型参数、激活、梯度 带宽有限、延迟高于片上存储
Host RAM / Pinned Memory CPU 内存 数据加载、异步 DMA 传输 PCIe/NVLink 带宽、固定页成本

理解 matmul 的出发点是：从 HBM 读入 Tile 到 Shared Memory，复用多次后再写回。一次 M×K @ K×N 的 FLOPs 约为 2MNK；每个元素被重复利用的次数越多，同样的 HBM 流量能完成越多乘加。

Coalescing（合并访存）

连续 32 个线程分别读取 x[lane]，可以让相邻地址的内存请求合并成少量 Memory Transaction。若每个线程读 x[lane * 32]，访问跨度大，事务数量和浪费的传输字节数可能明显增加。

对按行连续存储的 [B,S,H] 张量，最后一维 H 通常最适合让相邻线程连续访问。tensor.stride() 比只看 shape 更能说明真实访存位置：

x = torch.randn(2, 128, 1024)
print(x.stride())          # (131072, 1024, 1)
y = x.transpose(1, 2)
print(y.shape, y.stride()) # (2, 1024, 128), stride 变了
# y.contiguous() 会为连续排布复制数据；它也有时间/显存开销。

Bank Conflict：Shared Memory 的经典面试题

Ampere 等 NVIDIA 架构常用 32 个 Shared Memory Bank（按 32-bit 字映射）。假设声明 float tile[32][32]，Warp 的 32 个 Lane 同时按列读取不同 Row：

__shared__ float tile[32][32];
// lane 0..31 分别访问 tile[lane][column]
// bank = (lane * 32 + column) % 32 = column
// 32 个 lane 命中同一个 Bank 的不同地址 → 可能发生 32-way conflict

__shared__ float padded[32][33];
// bank = (lane * 33 + column) % 32 = (lane + column) % 32
// 每个 lane 对应不同 Bank → 典型的 Padding 解法

进阶还要掌握 Swizzle（地址重排）/ XOR 映射，通过改变不同 Warp/Lane 的片上数据布局减少冲突。Hopper 的 TMA / WGMMA 引入了更复杂的 Tile 组织与流水线，面试时通常会从这个 Padding 例子继续追问。

1.3 Roofline（屋顶线模型）：算力与带宽的分界

定义 Arithmetic Intensity（计算强度）：

I=FLOPsBytes transferredI = \frac{\text{FLOPs}}{\text{Bytes transferred}}

粗略性能上限：

P≤min(Ppeak,BWHBM⋅I)P \leq \min(P_{\mathrm{peak}},\; BW_{\mathrm{HBM}}\cdot I)

向量加法 c=a+b，每个 float32 元素读两个、写一个：1 FLOP / 12 B = 0.083 FLOP/B，容易受 HBM 带宽限制。大矩阵乘法能复用数据，往往更接近 Tensor Core 的计算峰值。相同运算换成小 Batch、小矩阵、非对齐 Shape 后，又可能出现利用率下降和 Launch Overhead（启动开销）。

本章自测：给定 float tile[32][32]，说清每个 Lane 访问的地址、Bank 编号，以及为何 32→33 能消除这类列访问冲突；再解释寄存器使用过多为什么可能降低性能。

02 · CPU/GPU 异步执行与多 Stream

2.1 CPU 提交任务，GPU 排队执行

cudaLaunchKernel / PyTorch GPU 算子通常在 CPU 侧异步提交。CPU 函数返回，不代表 GPU 已经完成。CUDA Stream（CUDA 执行流）是顺序提交队列：同一 Stream 内按顺序执行，多个 Stream 的任务在依赖和资源允许时能够并发。

常见同步点：torch.cuda.synchronize() 等待设备当前未完成任务；stream.synchronize() 等待某条 Stream；tensor.item() 把 GPU 标量送回 CPU，可能导致 Host 等待。性能测量时，别把这些同步开销无意间加在每个训练 Microbatch 里。

2.2 一段正确管理依赖的 PyTorch 代码

cpu_batch = torch.randn(1_000_000).pin_memory()
copy_stream = torch.cuda.Stream()
compute_stream = torch.cuda.current_stream()

with torch.cuda.stream(copy_stream):
    gpu_batch = cpu_batch.to('cuda', non_blocking=True)
    ready = torch.cuda.Event()
    ready.record(copy_stream)

compute_stream.wait_event(ready)  # 让 GPU 等待数据就绪；CPU 不必阻塞
gpu_batch.record_stream(compute_stream)  # 告诉分配器另一个 stream 也会用它
result = gpu_batch.square().sum()

pin_memory() 可帮助 CPU→GPU DMA（直接存储器访问）异步传输。non_blocking=True、独立 Copy Engine、可交叠的 Kernel 和满足条件的硬件拓扑共同决定是否真实重叠。Event 决定正确依赖，record_stream 还关系到缓存分配器能否安全复用内存。

CUDA 时间为什么不能只用 time.time()？

start = torch.cuda.Event(enable_timing=True)
end = torch.cuda.Event(enable_timing=True)
start.record()
y = x @ w
end.record()
end.synchronize()
print('GPU elapsed ms:', start.elapsed_time(end))

CUDA Event 测 GPU Stream 上的执行区间；使用 CPU 计时器测端到端 Step 时，需要在起止位置明确同步，否则测到的可能主要是 Host 提交速度。

本章自测：画出 DataLoader、H2D、Forward 三条时间线，指出 Event 应放在哪里，并解释为什么两个 Stream 不一定比一个快。

03 · PyTorch 训练过程与 Autograd

3.1 一轮 Step 的执行过程

训练循环的七步：读取 Batch → Forward（前向）→ Loss → Backward（反向）→ 分布式同步梯度 → Optimizer Step（更新）→ LR Scheduler（学习率调度）。optimizer.zero_grad(set_to_none=True) 一般放在当前梯度累积周期开始前。

model.train()
for tokens, labels in loader:
    tokens, labels = tokens.cuda(non_blocking=True), labels.cuda(non_blocking=True)
    optimizer.zero_grad(set_to_none=True)
    with torch.autocast('cuda', dtype=torch.bfloat16):
        logits = model(tokens)
        loss = F.cross_entropy(logits.float().flatten(0, 1), labels.reshape(-1))
    loss.backward()                # autograd 计算参数梯度
    torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)
    optimizer.step()               # 更新模型参数
    scheduler.step()               # 一次 optimizer step 对应一次 scheduler step

本项目的完整可运行版本在 examples/train_tiny_gpt.py，包括 AdamW、Cosine + Warmup、BF16、DDP、Gradient Accumulation 和 Profiler。

3.2 Autograd 动态计算图如何产生？

PyTorch Eager Mode（即时执行模式）在前向计算时为可微算子记录反向关系。例如 y = (x @ w).relu() 依次创建矩阵乘法和 ReLU 的求导节点；loss.backward() 从 Loss 沿着反向依赖传播梯度，最终累积到叶子参数的 .grad。对于一个矩阵乘法 Y=XW：

∂L∂X=∂L∂YWT,∂L∂W=XT∂L∂Y\frac{\partial L}{\partial X} = \frac{\partial L}{\partial Y}W^T,\qquad \frac{\partial L}{\partial W}=X^T\frac{\partial L}{\partial Y}

为了算这些导数，框架会保存部分前向张量。Activation（激活值）显存正是这样产生的。Activation Checkpointing（激活重计算）只保留部分检查点，反向时重新计算需要的激活值，用额外 FLOPs 换显存。

torch.no_grad() 适合无需计算梯度的前向；torch.inference_mode() 进一步关闭部分 Tensor 追踪机制。训练循环的模型前向必须保留梯度记录。

3.3 Gradient Accumulation（梯度累积）

当显存只允许每卡 Batch=1，却想要有效 Batch=64，可以连续做多个 Microbatch 的 Forward/Backward，最后调用一次 optimizer.step()。一个全局有效 Batch 的定义：

Bglobal=Bmicro×Ngrad_accum×NDPB_{global}=B_{micro}\times N_{grad\_accum}\times N_{DP}

（若还使用 PP，需要同时考虑流水线 Microbatch 的定义；上式适合常规 DP/FSDP 训练批次口径。）

optimizer.zero_grad(set_to_none=True)
for micro in range(accum_steps):
    with (model.no_sync() if distributed and micro < accum_steps - 1 else nullcontext()):
        loss = calc_loss(model, next_batch()) / accum_steps
        loss.backward()
optimizer.step()
scheduler.step()

DDP.no_sync() 可避免每个 Microbatch 都发一次梯度 AllReduce。应确保 Forward 和 Backward 都在该上下文内。对实际任务要留意最后一个不满 Batch、不同长度 Token Loss 权重等问题；简单除以 accum_steps 适合各 Microbatch 等权的设定。

3.4 Tensor Layout（张量排布）会影响 Kernel

对 B=2,S=2048,H=4096 的 BF16 激活 x[B,S,H]，数据量：2×2048×4096×2 B ≈ 32 MiB。transpose 多半只改变 stride；后续执行 contiguous() 可能引入完整拷贝。训练时算子融合、Tensor Parallel（张量并行）、FlashAttention 都需要精确识别 Shape、Stride、Dtype 和布局转换。

本章自测：用 torch.autograd.grad 对 x @ w 求导，与手工推导的 dX、dW 比较；打开/关闭重计算，记录 max_memory_allocated 和 Step Time。

04 · Decoder-only Transformer 与 Attention 变体

4.1 从张量看一层 Transformer

以 Pre-Norm Decoder 为例（现代模型常见的结构），一层主要是两块：RMSNorm → Attention → Residual 和 RMSNorm → FFN/MoE → Residual。堆叠多层后，末端经过 LM Head 投影到词表 V，用 Next-token Cross Entropy 训练。

设 B=2, S=4096, H=4096, n_q=32, d=128, n_kv=8：

张量 Shape 说明
Hidden States [B,S,H] 每个 Token 的表示
Q [B,32,S,128] Query 投影后分 Head
K / V [B,8,S,128] GQA 的 KV Head 数小于 Query Head
Attention Output [B,32,S,128] 按 Head 计算再合并成 [B,S,H]
SwiGLU 中间激活 [B,S,H_ff]（两支） 门控分支和 Value 分支
Logits [B,S,V] 词表可能极大，Loss 计算需关注显存

这份笔记以 Decoder-only 为主。Encoder-only 典型用于双向编码，Encoder–Decoder 常用于条件生成；文本生成式 LLM 的训练基础可以优先围绕 Causal Decoder 学习。

4.2 MHA、GQA、MLA：KV 为什么越来越少？

标准 Attention 的公式：

Attention(Q,K,V)=softmax(QKTd+M)V\mathrm{Attention}(Q,K,V)=\mathrm{softmax}\left(\frac{QK^T}{\sqrt{d}}+M\right)V

  • MHA（Multi-Head Attention，多头注意力）：Query/K/V 的 Head 数相同。每个 Query Head 有一组 KV。
  • GQA（Grouped-Query Attention，分组查询注意力）：多个 Query Head 共用一组 KV。若 n_q=32, n_kv=8，4 个 Q Head 共享一组 KV。KV Cache 相比 MHA 的 Head 部分理论上缩至 1/4。
  • MLA（Multi-head Latent Attention，多头潜在注意力）：把 KV 的信息编码到较低维潜空间，再配合投影还原 Attention 所需的表示；通常还要考虑解耦 RoPE 等结构细节。压缩显著影响推理 KV 占用，也改变训练侧的矩阵乘、Projection（投影）和 Attention 实现路径。

GQA 对训练的直接收益常来自 QKV Projection 中 KV 部分的参数与计算减少，也可能减少与 KV 相关的通信；Self-Attention 的 QK/AV 主体计算并未因此按相同比例下降。MLA 在训练上还会增加或改变某些 Projection 计算，因此一定要结合端到端 Profiling 判断。

PyTorch 示例（[B,H,S,D]）：

q = torch.randn(B, 32, S, 128, device='cuda', dtype=torch.bfloat16)
k = torch.randn(B, 8,  S, 128, device='cuda', dtype=torch.bfloat16)
v = torch.randn(B, 8,  S, 128, device='cuda', dtype=torch.bfloat16)
y = F.scaled_dot_product_attention(q, k, v, is_causal=True, enable_gqa=True)

实际可用后端和 GQA 支持范围受设备、PyTorch 版本和 Tensor Shape 影响，Profiler 中要确认调用了什么内核。

4.3 Dense 与 MoE 的计算差异

Dense（稠密模型）的每个 Token 都经过同一套 FFN。MoE（Mixture of Experts，混合专家模型）在每层由 Router 选择 Top-K Experts，每个 Token 仅运行被选中的 Expert。关键张量路径为：

Hidden [N,H] → Router Logits [N,E] → TopK(ids,weights) → Dispatch → Expert GEMM → Combine。

训练 MoE 时，总参数量与每 Token 激活参数量不同。计算量估算应优先按每 Token 实际激活的 Experts 统计；显存则取决于每卡持有哪些 Experts、优化器分片以及 Token Dispatch 缓冲。

本章自测：在纸上写出 32 个 Q Head、8 个 KV Head 的 GQA 映射；解释为什么“推理 KV 降到 1/4”并不意味着训练耗时降到 1/4。

05 · 训练显存账本：从 7B 手算到 FSDP

5.1 先确定优化器实现，再算每参数字节

训练显存至少由 模型参数、梯度、优化器状态、激活、临时通信/算子缓冲 组成。以 AdamW 为例，常见账本有两种；二者都很常用，区别在是否单独保存 FP32 Master Weights（主权重）。

项目 BF16 参数 + FP32 Adam moments 再额外保留 FP32 Master Weights
模型参数（BF16） 2 B/参数 2 B/参数

记住估算方法：先列出存在的 Tensor，再乘元素大小。 “7B 必须 16 B/参数”不是通用硬件规律。

5.2 Activation：为什么序列长度会使 OOM 更明显

单个 [B,S,H] 激活的 BF16 体积：

Mact,one=B⋅S⋅H⋅2bytesM_{act,one}=B\cdot S\cdot H\cdot 2\ \mathrm{bytes}

假设 B=1,S=8192,H=4096，一个这样的激活就是 64 MiB。一层内可能保存多份 Q/K/V、Attention 输出、FFN 中间量、归一化输入等；堆叠多层后会迅速增加。朴素 Attention 如果显式保存 [B,n_h,S,S] Score / Probability，空间随着 S² 增长；FlashAttention 类实现通过 Tiling 与重计算减少 HBM 中间量。

OOM 时建议按实际诊断顺序检查：Step 峰值显存发生在前向、反向还是 Optimizer；激活与参数分片各占多少；通信 All-Gather 的瞬时完整参数缓冲是否过大；是否发生不必要的 contiguous() / 输出 Logits 物化。

5.3 7B 放到 8 GPU：分片后还剩什么？

以带 FP32 Master 权重的 16 B/参数账本为例，若 FSDP 理想地把静态状态均匀分到 8 卡：

Mstatic,GPU≈7×109×168=14GB/GPUM_{static,GPU}\approx\frac{7\times10^9\times16}{8}=14\ \mathrm{GB/GPU}

这个值是静态状态基线。FSDP 会临时 All-Gather 当前 Module 的参数，反向期间保存激活，还可能需要通信 Bucket、CUDA Context 和算子 Workspace。单卡 40GB A100 上能否训练，主要看 FSDP Wrap Granularity（分片模块粒度）、序列长度、Microbatch、激活重计算和具体配置。

06 · 分布式通信原语与 NCCL

6.1 一张表区分四种最常用的 Collective

NCCL（NVIDIA Collective Communications Library，NVIDIA 集合通信库）能在 NVLink / NVSwitch、PCIe 和 InfiniBand / RoCE 上执行 GPU 之间的数据交换。分布式训练中的“切分策略”，最终几乎都能归结为几种通信原语。

原语 2 Rank 输入 → 输出示意 训练中出现的位置
Broadcast A / _ → A / A 初始化模型参数、控制状态
All-Reduce（AR） A / B → A+B / A+B DDP 聚合并平均梯度
All-Gather（AG） A / B → [A,B] / [A,B] FSDP 临时聚合完整参数；部分 TP/CP
Reduce-Scatter（RS） [a0,a1] / [b0,b1] → a0+b0 / a1+b1 FSDP 梯度聚合并分片
All-to-All（A2A） 各 Rank 向其他 Rank 发不同 Chunk MoE Token Dispatch / Ulysses 布局转换
Point-to-Point（P2P） Rank i → Rank j PP Activation / Gradient、Ring KV

经典 Ring All-Reduce 可以分为 Reduce-Scatter + All-Gather 两阶段。设每 Rank 待同步梯度为 M 字节，P 为通信 Rank 数，忽略启动延迟和拓扑因素时，每 Rank 数据发送量近似为：

BytesringAR≈2P−1PM\mathrm{Bytes}_{ring\ AR} \approx 2\frac{P-1}{P}M

这个公式说明：增加 GPU 数后，梯度同步字节数不会简单变成 M/P。集群规模越大，还需关心链路带宽、拓扑、异构慢 Rank 与 Kernel 计算时间能否遮蔽通信。

6.2 Process Group 与 Rank Mapping

  • World Size：总进程数。常见单 GPU 对应一个进程。
  • Global Rank：全局进程编号；Local Rank：本机进程编号。
  • Process Group：一组需要彼此通信的 Rank。N-D 并行会建立不同 Group。
  • Rank Mapping：决定哪些 Rank 组成 TP/DP/CP/EP Group，它影响 NVLink、PCIe 和跨机网络上的实际通信代价。

# 07 · DDP、ZeRO 与 FSDP2
## 7.1 DDP：每张 GPU 训练不同数据、持有完整模型
DDP（Distributed Data Parallel，分布式数据并行）复制参数、梯度和优化器状态。假设 2 GPU，各自得到不同 Batch。GPU0 和 GPU1 独立做 Forward/Backward；梯度 Bucket（梯度桶）就绪时，DDP 发起 All-Reduce，将梯度聚合为一致值，再分别更新本地参数。
text Global Batch / \ Batch 0 Batch 1 GPU 0 GPU 1 full weights full weights forward/back forward/back grads -- All-Reduce -- grads AdamW update AdamW update W(t+1) W(t+1)
通信时间能否隐藏取决于反向计算剩余工作量、Bucket 大小和互联带宽。DDP 反向过程中一个 Bucket Ready 就可以进入通信 Stream，因此在 Nsight 上通常能看到 NCCL 与其他 Backward Kernel 重叠。
DDP 的典型限制：每卡需要容纳完整模型和优化器状态。7B 用 AdamW 时，仅静态状态就可能超出单张 80GB 的容量，因此训练 7B 更常先用参数/优化器分片方案。
## 7.2 ZeRO：按什么顺序切分训练状态？
ZeRO（Zero Redundancy Optimizer，零冗余优化器）消除 DP 组内的训练状态重复。设模型静态状态使用上一章的 16 B/参数账本，P 个 Rank：
| 方法 | 每 Rank 主要持有的静态状态（概念估算） | 通信特点 | |—|—|—| | DDP | 2P + 2P + 12P = 16P 字节 | 反向梯度 All-Reduce | | ZeRO-1 | 2P + 2P + 12P/N | 优化器状态分片，更新后同步参数 | | ZeRO-2 | 2P + (2P+12P)/N | 梯度 RS、更新后参数同步 | | ZeRO-3 | 16P/N | 前向/反向需要聚合参数，梯度 RS |
表中 P 代表参数总数，N 代表 DP 分片数量。它展示的是状态分片的主体，没有算激活、临时参数 All-Gather、通信缓存；具体 dtype/实现变化会影响系数。
## 7.3 FSDP2：按模块 All-Gather 参数、Reduce-Scatter 梯度
FSDP2（Fully Sharded Data Parallel v2，第二代完全分片数据并行）通过 PyTorch fully_shard，将模型参数按 Device Mesh（设备网格）拆成 DTensor（分布式张量）。每个 Rank 长期保存自己的参数与优化器分片；当前模块运行前恢复所需的参数，计算后释放完整参数缓冲；梯度则 Reduce-Scatter 回各 Rank。
以连续两层 Block0、Block1 为例：
text Compute Stream: [Block0 FWD] [Block1 FWD] ... [Block1 BWD] [Block0 BWD] NCCL Stream: [AG Block0] [AG Block1] ... [AG for BWD] [RS Block1] [RS Block0] ↑ ↑ ↑ 计算前数据就绪 预取下一层 梯度已产生
关键变量是 Wrap Granularity（分片粒度）：若整个 7B 模型只看作一个大分片单元，一次性聚合的参数缓冲可能非常大；按 Transformer Block 分片，显存峰值更容易控制，也为 Prefetch（预取）和通信重叠创造空间。粒度太细则会增加 Collective 启动数量。
PyTorch FSDP2 风格片段：
```python from torch.distributed.fsdp import fully_shard
# 通常在模型构建并完成相应的设备/mesh 配置后执行： for block in model.blocks: fully_shard(block, mesh=dp_mesh) fully_shard(model, mesh=dp_mesh) # optimizer 应在 sharding 后基于 model.parameters() 构建 ```
选型依据：模型能完整放进每卡且需要吞吐扩展，优先 DDP；参数/优化器状态限制了 Microbatch、序列长度或模型规模，则考虑 FSDP/ZeRO；模型单层计算本身也太大、All-Gather 代价很高时，再考虑 TP/PP 配合。

08 · TP、SP 与 PP：模型并行如何切

8.1 TP：把一个大矩阵乘法分给多张 GPU

TP（Tensor Parallelism，张量并行）按张量维度切分层内权重，以典型 FFN 的两层矩阵乘法为例：

             W1 [H,4H]       W2 [4H,H]
X [B,S,H] ── Column TP ──→ A0 / A1 ── Row TP ──→ Y0 + Y1
             （按输出列）       （按输入行）      All-Reduce

TP=2：
GPU0: W1[:, :2H], W2[:2H, :] → Y0 [B,S,H]
GPU1: W1[:, 2H:], W2[2H:, :] → Y1 [B,S,H]
最终 Y=Y0+Y1

第一层 W1 按输出维度切分，两 GPU 各自输出一部分 FFN 通道，暂时无需合并。第二层 W2 按输入维度切分，各自算出一个完整 H 维输出的 Partial Sum，最后 All-Reduce 求和。

TP 也用于 QKV/O Projection。典型设计下，把 Head 分给各 GPU，减少每卡权重和中间计算，但每层会出现至少一次集体通信；具体算子、并行布局、是否采用 SP 会改变通信原语及次数。

对高速互联，TP 可以把大 GEMM 切成更适合每张 GPU 的尺寸；切分过度则可能令单卡 GEMM 变小、Tensor Core 利用率降低、通信占比提高。TP 的最优 Degree 要结合矩阵形状、拓扑和 Profile 确定。

8.2 SP：为什么 TP 之后还要切序列？

Megatron 风格的 SP（Sequence Parallelism，序列并行）与 TP 配套，主要在 LayerNorm、Dropout 和残差等部分按 S 维分片，减少这些中间激活在 TP Group 内的重复存储。

一个典型 Forward 边界：

[S/TP, B, H] → All-Gather(sequence) → TP GEMM → Reduce-Scatter(sequence) → [S/TP, B, H]。

需要掌握的转换位置：在哪个算子前必须恢复完整序列或特征布局，哪个算子后可以继续切分？ 例如 TP 的 Column/Row Parallel Linear 和 SP 的 All-Gather/Reduce-Scatter 可以协同设计，使通信发生在更有利的位置。不要把 SP 和 CP 混成一种方案；CP 在 Attention 计算本身也保持序列分片。

8.3 PP：每卡负责不同 Transformer 层

PP（Pipeline Parallelism，流水线并行）沿网络深度切。例如 32 层模型，PP4 每个 Stage 负责 8 层。Forward 时把 [B,S,H] Activation 传给下一 Stage；Backward 时再把对应梯度传回上一个 Stage。为充分利用所有 Stage，会把 Batch 切成多个 Microbatch（微批次）。

时间 →
Stage 0:  F0   F1   F2   F3   B0   B1   B2   B3
Stage 1:   ·   F0   F1   F2   B0   B1   B2   ·
Stage 2:   ·    ·   F0   F1   B0   B1   ·    ·
Stage 3:   ·    ·    ·   F0   B0   ·    ·    ·

F: Forward，B: Backward；示意图仅表达 fill/drain，并非严格的 1F1B 调度表。

Pipeline Bubble（流水线气泡）来自开始时 Stage 尚未填满、结束时部分 Stage 已空闲。对于等时 Stage 的理想简化流水线，常用 (p-1)/(m+p-1) 量级估算 Bubble 占比，其中 p 为 Stage 数，m 为 Microbatch 数。真实 1F1B（One-Forward-One-Backward）还需考虑不同阶段前反向耗时、通信、权重版本、激活保留及调度表。

PP 的优点是每卡放更少的网络层；代价包括 Activation/Gradient P2P 传输、Bubble、跨 Stage 负载不均，以及多阶段 Checkpoint、容错的工程复杂度。

09 · CP、EP 与 MoE 训练

9.1 CP：一个 32K 上下文分给多卡计算

CP（Context Parallelism，上下文并行）沿序列维切分整个 Decoder Layer 中的激活。例如 S=32768, CP=4，各卡本地只有 8192 个 Token 的 Q/中间激活。问题出现在 Attention：本地 Query 必须看到因果掩码允许范围内的其他 Token 的 KV，因此需要在 CP Group 中交换 KV。

两类典型路径：

  1. Ring / P2P KV Exchange：每张卡保持自己 Sequence Chunk 的 Q，通过 Ring 逐步交换其他卡的 K/V Chunk，配合 Online Softmax 累积输出。通信可以与部分 Attention 计算重叠。
  2. Ulysses / A2A Layout Transpose：各卡先持有部分序列、完整 Head，经 All-to-All 变换成完整序列的一部分 Heads，完成 Attention 后再 A2A 恢复原布局。可并行度受 Head 数（GQA 时尤其关注 KV Head）和实现约束影响。

Megatron 的 CP 通常采用 KV All-Gather / Ring P2P 等方式；经典 Megatron SP 主要节省非 Attention 部分激活。CP 切整个序列计算，SP 与 TP 配套切部分激活，这是面试里最重要的区别。

CP 后每卡计算 Token 数减少，但 Ring KV 或 A2A 有额外通信，长序列下通常更容易体现价值。GQA/MLA 改变传输中的 KV 形状，CP 性能因此也受 Attention 架构影响。

9.2 EP：Experts 分卡，Token 按 Router 调度

EP（Expert Parallelism，专家并行）把不同 Experts 分到多个 Rank。MoE Block 的一次 Forward 包括 Router 选择 Top-K、Dispatch Tokens 到目标 Expert 所在 Rank、运行 Grouped GEMM / Expert FFN、Combine 回原 Token 顺序并加权。

以 E=8 experts、top_k=2、EP=2 为例，GPU0 持 Expert 0–3，GPU1 持 Expert 4–7。如果一个 Token 选择 Experts 2 和 6，两个分支分别发送到两卡执行，再把输出按 Routing Weight 合并。训练反向时也要恢复对应梯度路径。

三个关键问题：

  • Load Imbalance（负载不均）：Router 使某些 Experts 收到更多 Tokens，最慢 Expert 决定该层完成时间。考察 tokens_per_expert 分布、Padding / Capacity、辅助平衡损失、Dropless 路径。
  • 通信开销：Dispatch/Combine 常对应 All-to-All，传输的是 Token Hidden States（加必要的路由索引），不是把完整 Expert 权重来回发送。
  • Grouped GEMM：各 Expert 收到不同大小的 Token Bucket，小矩阵太多可能使 Tensor Core 利用率下降；Grouped GEMM 和输入重排可改善执行效率。

DeepEP 面向 MoE 的高性能 Expert Parallel 通信，可在训练/Prefill 场景使用高吞吐 Dispatch/Combine 路径，也提供适配低延迟场景的实现。需要把它理解为 EP 的数据搬运优化，并结合 Router、Grouped GEMM、负载分布一起评估。

9.3 N-D 并行：不同 Group 不是随便相乘

8 GPU 的一个 Dense 模型布局可以是 TP=2 × FSDP=4；每两个 GPU 构成 TP Group，四组之间对应的 TP Slice 再组成 FSDP Group。一个物理 GPU 属于多个逻辑通信组，每个组的维度和成员不同。

MoE 中 EP 往往会与 Expert Data Parallel（专家数据并行）和 Dense 层的 DP/TP 采用不同映射，不能机械地把所有字母的 Degree 都当成独立的乘法因子。标准的 Dense 训练常用 DP × TP × PP × CP = world_size 表示正交的逻辑维度；具体到 EP，需结合框架的 Process Mesh 定义。

10 · 核心性能优化：FlashAttention、混合精度、重计算

10.1 FlashAttention：减少 HBM 中间量和 IO

普通 Attention 若显式产生 S=QKᵀ 和 P=softmax(S)，中间矩阵的 Shape 为 [B,H,S,S]。对 B=1,H=32,S=8192，仅一个 BF16 的 S×S 张量就是 4 GiB 量级（32×8192²×2 B = 4 GiB）。训练反向还需要相关中间量，进一步放大显存压力。

FlashAttention（闪存注意力算法）把 Q/K/V 分 Tile 加载到片上存储，在 Tile 内做 Matmul，使用 Online Softmax（在线归一化）维护每行的最大值 m 和指数和 l，无需把整个 S×S Attention Matrix 写回 HBM。

对于一个 Query 行，新旧 Tile 的数值稳定更新可写为：

m′=max(m,maxjsj)m'=\max(m,\max_j s_j)

l′=em−m′l+∑jesj−m′l'=e^{m-m'}l + \sum_j e^{s_j-m'}

设旧归一化输出为 o，则：

o′=em−m′l⋅o+∑jesj−m′Vjl′o'=\frac{e^{m-m'}l\cdot o+\sum_j e^{s_j-m'}V_j}{l'}

关键点：完整 Attention 的算术量仍主要是 O(S²d)，但 HBM 中间数据 IO 和激活保存量大幅下降。反向计算可根据必要统计量重算部分 Attention 中间量。FlashAttention-2 改进了线程块工作分配、并行度和非 Matmul 计算占比。是否提升端到端训练吞吐，取决于序列长度、Head Dim、Batch 以及后端 Kernel。

对应学习路径：先看 Safe Softmax → Online Softmax → 共享内存 Tiling → FlashAttention V1/V2；可以通过 PyTorch 的 F.scaled_dot_product_attention 调用当前可用的优化后端，再用 Profiler 验证。

10.2 BF16、FP16 与 FP8

精度 主要特点 训练中的用法
FP32 动态范围和精度较高，存储开销大 优化器 Moments、部分归一化/归约
FP16 5 位指数，10 位尾数 Tensor Core 加速，训练常需 Grad Scaling
BF16 8 位指数，7 位尾数 动态范围接近 FP32，常用于模型主计算
FP8 E4M3/E5M2 更低存储与传输开销，需要 Scale 量化 GEMM/激活/梯度等场景，要求硬件与数值方案支持

autocast(dtype=torch.bfloat16) 让框架针对算子选择适用 dtype；部分归约与 Loss 在 FP32 更稳定。若使用 FP16，通常结合 GradScaler 防止微小梯度 Underflow（下溢）；BF16 经常无需 Loss Scaling。

对硬件要有准确边界：A100（Ampere）支持 BF16 Tensor Core，但没有 Hopper 那类原生 FP8 Tensor Core 能力。FP8 训练的完整性能消融优先在 H100/H200/更新架构上开展，并核对 Transformer Engine 或训练框架后端支持情况。

10.3 Activation Checkpointing 与 Offload

Activation Checkpointing（激活重计算）：前向只保存特定节点的输入/输出，反向时重放相关前向计算，减少保存的激活体积。大模型训练常按 Transformer Block 设置检查点，以增加反向计算换取更大序列或 Microbatch。

from torch.utils.checkpoint import checkpoint
x = checkpoint(decoder_block, x, use_reentrant=False)

Offload（卸载）可以把部分参数、梯度、优化器状态或激活移到 CPU/NVMe，降低 GPU 驻留显存，但增加 H2D/D2H 与 PCIe/网络 IO，需通过 Prefetch 和 Asynchronous Transfer 尽量隐藏代价。

实践中的优化顺序建议由 Profile 决定：先确定显存瓶颈来自参数状态还是激活；再比较 FSDP、重计算与 Offload 的代价，观察是吞吐提升、峰值显存降低，还是仅仅能够把实验跑起来。

本章自测：解释 FlashAttention 为什么减少 IO 仍保持 Attention 的 O(S²) 算术复杂度；说出 BF16 vs FP16 的指数/尾数区别；比较重计算和 CPU Offload 的性能代价。

11 · 性能分析：从一份 Trace 找到训练瓶颈

11.1 先统一性能指标的定义

指标 计算方式 / 口径 常用来判断
Step Time 完成一次 optimizer.step() 所用的墙钟时间 最直观的总体性能
Global Tokens/s 有效 global_batch × seq_len / step_time 吞吐；变长场景要排除 Padding
Peak Allocated Memory PyTorch 实际存活 Tensor 所分配的 CUDA 内存峰值 张量内存压力
Peak Reserved Memory PyTorch Caching Allocator 从设备保留的显存峰值 分配器缓存、碎片等
MFU（Model FLOPs Utilization，模型算力利用率） 有效模型 FLOPs / GPU 理论峰值 FLOPs 模型计算效率估算
NCCL Wait / Overlap 通信耗时、暴露在关键路径上的等待时间 分布式扩展瓶颈

针对 Dense Decoder 的常见粗估：

MFU≈6N⋅Ttokens/sG⋅Fpeak\mathrm{MFU}\approx \frac{6N\cdot T_{tokens/s}}{G\cdot F_{peak}}

其中 N 为参数量、G 为 GPU 数量、F_peak 为该硬件在对应 dtype/稀疏假设下的理论 FLOPs/s。精确计算应纳入长序列 Attention 的额外 FLOPs、Embedding/LM Head、Gradient Checkpointing、MoE 的激活参数量等，并注明 FLOP 估算口径。MFU 是模型工作量与峰值算力的比值；它不是 GPU Utilization 指标。

    activities=[ProfilerActivity.CPU, ProfilerActivity.CUDA],

11.3 Nsight Systems：看 CPU 和多 Stream 的时间线

# 例：只采集短时间窗口，避免 Trace 过大
nsys profile \
  --trace=cuda,nvtx,osrt \
  --sample=none --cpuctxsw=none \
  --delay=5 --duration=15 \
  -o train_profile \
  python examples/train_tiny_gpt.py --steps 100

打开 .nsys-rep 时从以下顺序读：CPU 线程有没有长时间等待？Kernel Launch 之间有无可观的空洞？不同 CUDA Stream 的计算、Memcpy、NCCL 是否重叠？哪个 Rank 的 NCCL 先进入、最后完成？为了让时间线更易读，可在 Python 中用 torch.cuda.nvtx.range_push/pop 或训练框架已有的 NVTX 标记 Forward、Backward、Optimizer。

Nsight Compute（ncu）进一步分析热点 Kernel 的 Roofline、Memory Transaction、Register Usage、SM Occupancy、Tensor Core 指标。它与 Nsight Systems 的区别可以理解为：Systems 负责定位哪里卡住，Compute 负责解释某个 Kernel 为什么慢。

11.4 一个可复用的定位流程

具体观察方式：

A. GPU 空洞很多：看 DataLoader/H2D、Python Launch、loss.item()、动态 Shape、隐式同步。优先比较预取、Pinned Memory、torch.compile 或 CUDA Graph 是否适用。

B. GPU 一直很忙但 Tokens/s 低：查 Kernel 时间聚合、实际 GEMM Shape、Tensor Core 利用率、Memory Bandwidth、Bank Conflict、寄存器溢出。

C. NCCL 占比很大：查 DP/TP/CP/EP 的 Group Mapping，Gradient Bucket，通信等待是否暴露在 Critical Path（关键路径），以及同步/Overlap 条件。

D. 显存紧张：区分静态状态、激活、通信缓冲和 Caching Allocator 预留；按前向/反向/更新不同阶段记录峰值，再针对性试 FSDP、重计算、Offload、序列分片。

本章自测：截一张 Nsight Systems 时间线，用箭头标注三处：CPU 空洞、Kernel 计算、NCCL 等待。对每处给出一个可以验证的假设，不要直接把 GPU Utilization 当作 MFU。

13 · 面试速查：把知识组织成可讲述的答案

面试问题 60 秒回答的核心抓手
CUDA Stream 和 CPU 异步如何工作？ CPU 只提交任务；同 Stream 顺序；跨 Stream 用 Event；Event/同步决定依赖与可见性
为什么两个 Stream 没有加速？ 无独立资源、依赖链、隐式同步、H2D 未 Pin、Kernel 资源已占满
Warp 和 Block 的区别？ Warp 为 32 线程执行组；Block 为共享 Memory/同步边界；Block 被调度到 SM
Shared Memory Bank Conflict 如何解决？ 按 Lane 推导 Bank 编号；Padding 33、Swizzle/XOR；检查 ncu 指标
PyTorch Autograd 如何保存激活？ Forward 记录算子反向节点与所需 Tensor；Backward 依赖反向执行；Checkpoint 重算
BF16 和 FP16 区别？ 相同 16 位；BF16 指数范围大、有效位少；FP16 常配合 Loss Scaling
7B 训练需要多少显存？ 先确认 dtype/optimizer；常见 12/16 B 每参数，再加激活、通信缓冲
DDP 为什么不同卡参数仍一致？ 相同初始权重、聚合平均梯度、相同优化器规则；关注随机性与同步时序
DDP Gradient Bucket 有什么用？ 分 Bucket 梯度就绪立刻通信，与剩余 Backward 重叠
ZeRO-1/2/3 分别切什么？ 优化器；再加梯度；再加参数；通信与内存成本逐级改变
FSDP 为什么 Forward 要 All-Gather？ 本地长期只有参数 Shard；运行当前层需要完整参数计算
TP 的 Column/Row Linear 如何通信？ 列切输出通道；行切输入通道并聚合 Partial Output
SP 和 CP 区别？ SP 与 TP 协同切非 Attention 激活；CP 切全序列并需跨卡交换 Attention KV
PP Bubble 如何降低？ 更多 Microbatch、1F1B、Interleaving、Stage 负载均衡，权衡激活与调度复杂度
MoE EP 的两次 All-to-All 在做什么？ Dispatch Token Hidden State 到 Expert；Combine 输出回 Token 原位置
FlashAttention 为什么快？ IO-Aware Tiling 与 Online Softmax，省 S² HBM 中间量，算术量仍大体不变
MFU 如何计算？ 明确模型有效 FLOPs、总 Tokens/s、GPU 个数与峰值算力精度，修正长序列/MoE
Nsight Systems、Compute、Profiler 怎么分工？ Systems 时间线；Compute 单算子硬件计数；Profiler 算子、调用栈与 Tensor Memory
8 卡 A100 用哪种并行？ 先看每卡 40/80GB、模型状态/激活、拓扑；FSDP 作为 7B 起点，再评估 TP/CP
为什么多卡训练吞吐不线性？ 通信、同步、慢 Rank、TP 切小 GEMM、PP Bubble、数据加载和实际 Batch 不匹配
